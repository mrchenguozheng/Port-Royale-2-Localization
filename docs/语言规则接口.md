# 语言规则接口（三段式）

`lang_rules` 里每种语言只做一件事：声明一份 `LangSpec`。
「标点」「分词」「补空格」是三件互相独立的事，混在一个 `normalize()` 里会导致
新语言必须同时改 `engine_text`、`apply_*_rules`、`normalize_text` 三处。

代码：`src/tools/text/lang_rules/spec.py`。

---

## 1. 三个部件

### 标点 `Punctuation`

```python
class Punctuation:
    normalize(text, date_format=False) -> str
    tables            # 只用来看：open/close/single/runs/cjk
```

纯函数，只改标点：半角→全角、单标点后一格、成对标点外侧空格、占位符两侧、
`<n>` 去空格。它**不碰**分词，也**不补**排版空格，所以 `normalize_text.py`
可以安全地把它写回译文层。

机制仍在 `base.py`：`make_fmt` / `fix_ascii_punct` / `fix_vars` / `clean_n`。

占位符正则只有 `base.VAR` 一份是全语言口径：中文的 `zh_space.TAG` 与
`zh_pipeline.SPLIT_RX` 都由它拼出（各多一段 `<...>` 前缀），日文的 `ja.SPLIT_RX`
故意更宽（`%[0-9A-Za-z]+`、`@X$…$`），单独保留。校验用的 `shared/core/validate.py`
是独立契约，不从 `base.VAR` 派生。

### 分词器 `Segmenter`

```python
class Segmenter:
    name                       # "spacy" / "janome" / "fugashi" / "none"
    prepare(texts) -> ctx      # 批量准备；不需要就 None
    tag(text) -> [(surface, pos)]   # 不支持词性就 None
```

`prepare` 必须批量：中文要一次把所有待切片段交给子进程，日文要复用同一个
tagger。逐条准备会让构建从几十秒变成几十分钟，也会反复建模型。
`tag` 只给需要词性的语言用（日语判「名詞+助詞」），中文只取 `surface`。

没有分词器就声明 `NullSegmenter()`，`name="none"`，补空格策略自己决定降级。

### 补空格 `Spacing`

```python
class Spacing:
    mode                       # "none" / "group" / "particle"
    setup(doc)                 # 整份译文准备一次（中文建人名表）
    pre_punct(text) -> str     # 标点规范化之前（日语助词空格）
    before(text) -> (str, meta)  # 标点之后、分词之前（中文连词/人名/数字标签）
    prepare(texts, segmenter) -> ctx
    apply(text, ctx) -> str
    report()                   # 收尾提示
```

三种模式的含义：

| mode | 给谁 | 做法 |
|---|---|---|
| `none` | 词间本来就有空格的语言（英、法、德、韩……） | 原样返回，就是原来的 `else` 分支 |
| `group` | 中文式（词间不空格） | 分词后按字数成组，组间一格；每组上限 `max_chars`（10 字） |
| `particle` | 日式 | 形态素判助词，助词后一格 |

`particle` 用 `pre_punct`：**必须先于标点**。标点自己会加空格，顺序反了会和
标点空格互相干扰。`group` 用 `before` + `prepare` + `apply` 的两遍流程
（第一遍到「分词前」，第二遍批量切词后成组）。

## 2. 执行顺序

```python
out, stats, seg_name = spec.build_texts(spec, doc, order)
```

1. `spacing.setup(doc)` —— 整份译文准备一次；
2. 逐条：`spacing.pre_punct()` → `punct.normalize()` → `spacing.before()`；
3. `spacing.prepare(所有中间文本, segmenter)` —— 批量分词；
4. 逐条 `spacing.apply()`；
5. `spacing.report()`。

`engine_text.build(lang, doc, order)` 就是 `build_texts(get_spec(lang), …)`，
里面没有任何 `if lang == …` 的分派。

## 3. 中文 / 日文落在哪，法文为什么不在这里

| 段 | 中文 | 日文 | 法文 |
|---|---|---|---|
| 标点 | `lang_rules/zh.normalize` | `lang_rules/ja.normalize_punct` | 无（排版写在译文里） |
| 分词 | `ZhSegmenter`（`zh_space.segment`：只用 spaCy） | `JaSegmenter`（`_Tagger`：janome → fugashi） | `NullSegmenter` |
| 补空格 | `ZhGroupSpacing`（`zh_pipeline.pre_space` + `zh_space.spaced`） | `JaParticleSpacing`（`space_particles_analyzer`） | `NoSpacing`（词间本来有空格） |

中文的连词、人名、数字/破折号/`<n><n>` 三步在 `zh_pipeline.py`：它们靠
「旁边是不是汉字」判断，只有中文用得上，所以不放进 `base.py`。

### 法文：不加工，也不引入特殊空白

法语排版在 `? ! ; :` 前、`%` 前要留一格。本项目的口径是：**这一格保留译文作者写的
普通空格**，既不换成 U+00A0（不换行空格），也不换成窄空格、零宽空格。

* 不换的理由是口径本身：不许引进非 U+0020 的空白字符；
* 已知副作用，明确接受：普通空格是引擎的断行点，窄框里 `Vraiment ?` 的问号可能
  单独落到下一行。这个代价不用构建期规则去绕；
* 守卫是内容层复核 `text_lint --lang fr` 的 `fr_space_checks`（E 级）：谁把 U+00A0
  （或 U+202F / U+2009 / U+200B 等）写回 `fr.toml`，复核直接失败；
* `lang_rules/fr.py` 因此是显式透传模块，`SKIP` 写清「不加工、不引入」。

实测：`fr.toml` 里 U+00A0 0 处、其它非 U+0020 空白 0 处；`engine_text --lang fr`
标点改动 0，成品与译文逐字一致。

### 不加工的语言：显式声明

`de` / `es` / `ru` / `ko` 都有模块，`spec()` 返回透传，模块里用 `SKIP` 常量与注释
写清「为什么不处理」——让「不处理」是一份可审的声明，而不是一个没有文件的空白：

| 语言 | 为什么不需要规则 |
|---|---|
| de | 空格分词、标点无前置空格、无 CJK 语境 |
| es | 同上；句首 `¿` `¡` 属内容层，`es_checks` 已在 W 级报 |
| ru | 同上；`«»` 两侧本来就带空格 |
| ko | 语节空格分词、标点无前置空格；大面积未翻译属内容层 |

## 4. 加一种语言

以法语为例，只写一个文件 `lang_rules/fr.py`：

```python
LANG = "fr"

def normalize_punct(text, date_format=False):
    ...

def spec():
    return S.LangSpec(code=LANG,
                      punct=S.Punctuation(normalize_punct, {"lang": LANG}),
                      segmenter=S.NullSegmenter(),
                      spacing=S.NoSpacing())   # 词间本来有空格
```

再在 `lang_rules/__init__.py` 的 `REGISTRY` 加 `"fr"` 就完事：
`engine_text.py`、`apply_*_rules.py`、`normalize_text.py` 一行都不用改。

**不需要加工的语言也要建模块并登记**（`de`/`es`/`ru`/`ko` 就是这么做的），
文件头写理由、暴露 `SKIP` 常量。`tests/test_rules.py` 的
`test_skip_languages_are_declared` 会替你把这条守住：模块在、理由非空、
行为是恒等透传。

如果是不按词空格的语言，把 `spacing` 换成自己的 `Spacing` 实现，
`mode` 取 `group`（按字数成组）或新写一种；接口不规定组内细节。

## 5. 验收口径（改接口不能改行为）

- `python src\tools\text\engine_text.py --lang zh --check` / `--lang ja --check`
  必须打印「一致。」；
- 两个语言包重新编译后，SHA-256 与改接口前相同
  （`build/runtime/PR2Localization/packs/zh.txt`、`ja.txt`，3548 条）；
- `python tests\test_rules.py`、`tests\test_validate.py`、
  `python src\tools\check.py` 全绿。

`engine_text.py` 是唯一的构建入口（`--lang zh|ja`，`--check` 对比，`--stats` 打印各阶段
条数，`--diff` 逐条打印差异）。中文旧名仍可在 `apply_zh_rules` 里调到（`fix_conj`、
`space_tokens`、`build_names`、`find_names`、`pad_names`、`generate_doc`），它现在只是
兼容门面；`apply_ja_rules.py` 已删除，日文直接用 `engine_text --lang ja`。
`zh.normalize` / `ja.normalize(particles=)` 也保留为兼容 shim。

## 6. 中文补空格（实现细节）

中文按词插空格，是因为引擎只按空格断行；不插空格时，一串汉字会被当成一个超宽
token，超出控件就**整条丢弃**，屏幕上是空白。

数据流：

```
src/translations/zh.toml          干净译文，唯一手改层
        │ engine_text.py          排版规则总入口
        ▼
build/preview/engine_text/zh.toml 引擎文本
        │ compile_pack.py         占位符校验
        ▼
build/runtime/PR2Localization/packs/zh.txt
```

中文三段分别落在：

1. `lang_rules/zh.normalize()`（`Punctuation`）：半角标点全角化、标点后空格；
2. `zh_pipeline.pre_space()`（`Spacing.before`）：连词 `fix_conj()` →
   人名 `find_names()/pad_names()`（引号里的船名、书名不动）→
   `space_tokens()`：数字、破折号、省略号、`<n><n>` 两侧补空格；
3. `zh_space.compact()`（`Spacing(mode="compact")`）：按「距上一个空格」的预算补空格，
   句中停顿标点后强制断一刀（`_break_after_punct()`），最后连续空格归一。
   `zh_space.spaced()`（`mode="group"`）保留为旧路径。

**成组标准是字数，不是像素**：预算为 `zh_space.MAX_CHARS`（13），即连续 13 个字
之内必有一刀，组内不加空格，组间加一个。控件宽度没有在游戏里实测，早期按字体度量
推出来的“目标 px”不可信，相关宽度工具和 CSV 已删除。

**标点后必断**：`，。！？；：、…—` 与收尾引号括号之后一律一个半角空格，不再
「只在超预算时才落刀」。行数因此变多，但行只会更短，不会更长；唯一让步是下一件
以不能起头的收尾标点（`」` `』`）开头时不断，免得标点被顶到行首。

**音译分隔符已废止（2026-11-23）**：`·` / `‧` 不再参与排版，`zh_space.strip_separators()`
在 `compact()` 之前把它们换成空格，`compact()` 用哨兵 `\x02` 占位、排完再还原，避免
`_TIGHT_SPACE` 把语义空格抹掉（只收敛 2 个以上连续空格）。`_cut_ok()` 的禁则集合不再
含 `·`，`_break_after_dot()`、`NAME` 保护正则、`zh_pipeline.find_names()` 的「名·姓」
分支都已删除；静态译名里的分隔符也已全部改成空格。

**数量短语粘右**：`bind()` 里 `QUANT_HEAD`（两字以内的 `好几` `这个` `几乎没有`）
与 `QUANT_TAIL`（量词收尾的 `好几件` 后接单字 `事`，或后接两字名词 `一座` + `城镇`）
都会把相邻词拼成一件，否则 spaCy 把「好几件事」切成两三个词，DP 就在中间落刀，
实机出「好几 件事」「一座 城镇」。`QUANT_TAIL` 的两字分支要排除 `prev` 本身是
后置词的场合，否则「之间」的「间」会被当成量词，拼出「之间运输」。

**后置方位词粘左**：`POSTPOS`（`之间` `之后` `之前` `以上` `以下` `以内` `以外` `之中`
`中间` `附近` `周围` `旁边` `里面` `外面` `当中`）遇到前面以汉字收尾的那一件就并进去。
实机出过「在这些城镇 之间运输和贸易货物」，名词与它的后置词被拆到两行。
`prev` 是变量（`%1`）时不并，变量后本来就允许断开。

**方位短语合成**：`bind()` 里 `_edge_pair()` 把「方位字 + 方位后缀」两块拼回一件，
覆盖 spaCy 切出的 `右` + `下角` 与 `右下` + `角` 两种切法，合成 `右下角`。
可拼的方位字是 `上下左右前后内外`（`FANGWEI`），后缀是 `角边侧方端面`（`EDGE`）。
实机出过「点击贸易窗口右 / 下角那个带房屋图标的按钮」，断在方位短语中间。
不加这条就不能靠数据层绕——同一条词里「右下角」出现在三处（`0xf70fedde`、
`0xf70fede1`、`0x0cf7abef`），一条条改句式只会把断点挪到别处。

分词器只有一条路：

- spaCy + `zh_core_web_sm`；用 `PR2_SPACY_PYTHON` 指向装了它的解释器
  （或仓库里的 `.venv-spacy`，会自动发现）；
- **没有 spaCy** 才用 `zh_space.fallback_wrap()`：按字数机械切，会切在词中间
  （「因 而」「进口货 物」），属于降级路径，终端会打印提示。

**不要用 jieba**（2020-02-15 之后无提交、649 个 issue 无人处理），
理由见 `docs/构建与安装.md` 的「不要用 jieba」一节。

超过 13 字、会被切成两组的片段必须进分词器，否则只能按单字成组。
`zh_space.segment()` 返回的 lookup 上挂着 `missing` 列表，有内容就说明发生了
这种情况，生成脚本会打印条数。

**验收**：补空格必须不改字。把新旧语言包都去掉空格后逐字节比较，应当 0 条内容
差异，只允许空格不同。2026-11 实测：3,548 条中内容差异 0 条、仅空格不同 967 条。

单测见 `tests/test_rules.py`（`pack / bind / spaced / fallback_wrap / collect_runs`）。

## 7. 明确不做

- **不做从右往左书写的语言**（阿拉伯语、希伯来语等）：没有游戏源代码，
  引擎的绘制方向改不了，补空格也解决不了。`Spacing` 只有三种模式，没有方向字段。
- **不按像素/字体宽度做判断**：控件宽度没有实测，见 [翻译局限](翻译局限.md)。
