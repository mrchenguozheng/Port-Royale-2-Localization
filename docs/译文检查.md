# 译文检查与清洗

> 本页承接原《译文与语言包》的检查、清洗与审计部分：提交前统一检查、外语形态层、
> 参照层清洁、零售参照导入、断行长度复核、W 级豁免和韩语量词复核。
> 译文格式、占位符规则、排版约定与语言包编译仍在[译文与语言包](译文与语言包.md)。

## 提交前统一检查

```powershell
python check.py                # 或 python src/tools/check.py
python check.py --jobs 4        # 逐语言三项检查与规则单测都分 4 路并行（CI 用这个）
```

依次跑：跨模块引用 → 语言配置 → 译文规范（`analysis/text_lint.py`）→ **断行长度
（`analysis/line_run.py`）** → 不译清单（`analysis/keep_audit.py`）→ 英文微调层 →
文档一致性 → 脚本地图 → 规则单测（`tests/`）。

语言清单只认一处：`translate.target_langs()`（`src/translations/*.toml` 里可编辑的
那些）。**默认每门语言都要过**，新加一门语言不用再来这里登记；译文规范与断行长度、
不译清单都逐语言各跑一遍。此前只跑默认语言（zh），其余语言一条都没进过 CI
—— pl 早前那条 W1（诗谜缺谜底）就是这么漏过去的。译文规范现在带 `--strict`：
**E 级和 W 级都算失败**，要放过某条 W 必须写进 `src/data/lint_ok/<语言>.txt` 并写理由。

要跳过某门语言必须**显式**，而且最好留痕：

```text
src\data\check_skip.txt        # 一行一门：代码<TAB>理由，理由会打在报告头上
```

```powershell
python check.py --skip-lang pl       # 本地临时排障，可重复，不写进仓库
```

跳过的语言会在报告头一行列出「跳过语言：xx —— 理由」，不会被当成查过了；
清单里写了不存在的语言代码（`deu`、`DE`）直接算失败，防手滑。

`--jobs N` 只改并发度、不改判据：三项逐语言检查各开 N 路；规则单测按「测试类」
贪心装箱分成 N 片并行（同一 `setUpClass` 不拆，与串行一致），末尾仍打印合计
`Ran N tests`。默认 1 就是原来的串行行为。本机 32 核实测：串行 94s，4 路 55s。



### 外语形态层（`analysis/lang_check.py`）

分工是固定的：`text_lint` 查「照原文说对了没有」（模板、占位、标注），
`lang_check` 查「这门语言写得对不对」（拼写、语法、德语复合词）。

拼写用的是 Hunspell 词典，放在 `src/data/qa/dict/<词典名>.aff` + `.dic`，**随仓库走**：
不需要在机器上装 `hunspell` 程序，`spylls`（纯 Python）直接读 .aff/.dic。已收：

| 语言 | 词典 | 来源 |
|---|---|---|
| de | `de_DE_frami` | LibreOffice dictionaries |
| fr | `fr_FR` | 同上 |
| es | `es_ES` | 同上 |
| ru | `ru_RU` | 同上 |
| pl | `pl_PL` | 同上（2026-11-19 补入） |

```bash
python src\tools\analysis\lang_check.py --lang pl --spell-only
python src\tools\analysis\lang_check.py --lang de                # 语法 + 拼写 + 复合词
```

补一门语言的词典就是照上面的来源下载 `.aff` / `.dic` 丢进 `src/data/qa/dict/`，
再在 `lang_check.py` 的 `HUNSPELL` 表里加一行 —— 表里没有的语言会退回
`pyspellchecker` 的频率表，中日韩则直接跳过（没有词表，硬走会抛 `ValueError`）。

词典只回答「有没有错字」，答不了「搭配顺不顺」。pl 的 338 个未收词里绝大多数是
德国开发者人名与加勒比地名，要按大小写分栏看小写那一栏。这轮靠它抓到并修掉的：
`wchód` → `wschód`（谜面与 clue 同一行）、`ocalalonych` → `ocalałych`、
`jakiś rozbitków` → `jakichś rozbitków`、`Henrego` → `Henry'ego`。
`slup` / `bieży` / `okręciska` 属于词典不收但不算错的（船级名、古诗体、增义名词），不报不改。

LanguageTool 还没接 pl：它的波兰语规则覆盖没实测过，不像 de/fr/es/ru 那样有命中记录，
先不拿未验证的结果当判据（ja/zh 当初也是同样理由被排除的）。

**变格语言的城镇替身（2026-11-21）**

`render()` 过去把城镇一律填主格。对 ru、pl 这是替身自造的错：译文里本来正确的
`для Тортуги`、`до Номбре`、`в Одессе` 被抹成 `для Одесса`、`до Одесса`、`в Одесса`，
再判「前置词 + 主格」；位置占位 `@l$Pos$` 的替身写成 `около Одесса`，可 `около` 支配属格，
于是每条含位置的译文都必然命中。ru 报的 55 处 `PREP_U_and_Noun`/`PREP_V_and_Noun`
全部属于这一类，逐条看原文，没有一条是真的「介词后接主格」。

修法：`TOWN_CASE` 给 ru、pl 各一张三格的城镇池（主格／属格／前置格），`GOVERN`
收支配关系单一的前置词（俄语 `до от для около возле из без после кроме против ради
вокруг мимо вдоль у` → 属格，`в во на о об при по` → 前置格；波兰语 `do od dla koło
obok bez przed oprócz wzdłuż u` → 属格，`w we na o przy` → 前置格）。替换城镇名与
`@T$`／`@l$…$` 占位时读前一词选池，判不出格就退回主格——`с`／`у`（俄语）、`po`（波兰语）
能带多个格，宁可不判。非变格语言没有这张表，走原逻辑。

读数：ru 226 → 170 处、规则 20 → 17 条，`PREP_U_and_Noun` 31 → 0、`PREP_V_and_Noun`
24 → 0；pl 拼写仍 315、缺变音符仍 7 条，两个读数不变说明 `jedn.` 没被拼写层拱起来。

人名占位不做变格替身：人名变格没有「加个词尾」的规律（`Пётр Петров` → `Петра Петрова`
两段都变），而同一个 `@N$` 也大量用在主格位置（主语、呼语），替身无论填哪一格都会在
别处造错。译文层能避就避：`для @N$ContactName$` 这类把占位放在属格支配位置上的写法
改句式（零售版的 `верните его человеку по имени @N$ContactName$` 就是现成写法）。
本轮 ru 只核出 1 条真错，即 `0xd034f206`，已按零售写法改回。


**es 这一轮（2026-11-20）**：语法命中 455 → 226（`<n>` 还原成空行后 228，清单项移出语法层后
221，首字母大写复核后 218、标签紧跟标点抹空后 210、拼写层与模板复数复核后 207、长尾小规则复核后 203，送检 2549 条），规则 47 → 25，拼写未收录

旧版「只对首字母试 `E`／`A`」的判据对它完全失效；`ACCENT_OF` 按语言分表之后
才认得出 `oído`／`traído`／`azúcar`／`Cristóbal` 这类。

真改的都按「能证伪」入库：缺变音符与重音（`continua`→`continúa`、`Tu`→`Tú`、
`para mi`→`para mí`、`mas`→`más`、`a cual`→`a cuál`、`para tí`→`para ti`、
`ya estas`→`ya estás`）、性数一致（`los último días`、`Mi nación está dispuesta`、
`Esta ancla`、`uno de sus barcos`、`barcos pirata`）、专名大写（`américa`／`europa`）、
重复词（`la la`）、连接词逗号（`pero`／`pues`／`sin embargo`／`por tanto`）、
句号前不留空格（`@D$EndDate$ .` → `.`）。

不动并记口径的五类：

1. `SOLO`（57 条，`sólo`）与 `ESTE_ESE_AQUEL_NOTILDE`（11 条，`éste`／`ésta`）：
   RAE 2010 起不强制加重音，两写都合法。全库既有 `sólo` 也有 `solo`，统一与否属口味，
   暂按原样。
2. `COMMA_ADVERB`（17 条）：句首短副词后的逗号可选，加与不加都算对。
3. `UPPERCASE_SENTENCE_START`（38 条）：几乎全是 `<n>` 切开后的界面标签
   （`consumo diario`、`la presencia militar`），标签本来就小写，渲染后被当成句首。
   只有 1 条是真错，已改（`¿deseas` → `¿Deseas`），判据见下文「句首大写复核」。
4. 配船型占位的冠词（`un %1`、`el %1`、`del %2`）：同一个模板会填进 `Fragata`（阴）、
   `Bergantín`（阳）、`Carraca`（阴）等不同性别的船型，冠词定不下来。原版当年就没
   把冠词性别算进设计里，各语言照样出 `le Frégate` 这种句子，玩家不会读成错，所以
   **这算送检噪声，不算缺陷**，不进缺陷清单、不改译文去绕。**渲染层已按词给性别**：
   `render()` 读占位前后的冠词，阳性冠词只取阳性船型、阴性冠词只取阴性船型，
   `les`／`de las`／无冠词时不筛（`SHIP_GENDER`／`ART_GENDER` 两张表，缺表语言退回
   随机）。es 的 `AGREEMENT_DET_NOUN` 11 条、fr 的 `D_N` 4 条假命中就此清零，
   `tests/test_lang_check.py` 两条单测守住。它只让报告干净，不承诺游戏内自洽。
5. `MORFOLOGIK_RULE_ES`（49 → 47）与 `PRONOMBRE_SIN_VERBO`（2 条）：逐条看过，
   只剩两类可留。一类是城镇名被换成 `Sevilla` 后，船长名列表里的 `van`／`le`／`de`
   残留成碎片，词本身没错；另一类是词源段里的 `vido`／`ganguru`／`batate`／`peirato`／
   `kangooroo`／`xocoatl`，是论证用的原文引语，动了就没有论点了。另有界面缩写
   （`BIR`／`BDR` 左右键、`Conv.` 会议、`kt` 节、`UK`）与 `lacitos`（`lacito` 词典不收
   但构词合法）同属误报。逐条核出的真错只有两条，已改：`A continúación` →
   `A continuación`（重音打错位置）、`de américa` → `de América`（漏大写）。

小写 ≥5 字母的 79 个拼写候选逐个核过：真错 21 个已改，其余是技术借词（`dummy`、`zoom`、
`scenario`、`playback`、`márqueting`、`inlay`）与词典不收但构词
合法的派生（`ventanita`、`ruedecilla`、`cazapiratas`、`cazarrecompensas`）。

第 6 类在 2026-11-21 复核后收掉：`COMMA_PARENTHESIS_WHITESPACE` 9 条**没有一条是译文错**。
`Recibirás @g$GoldPerBarrel$ por cada <g:INTEXT_GOLD_800x600.screen>.` 这类句子里的金币、
士兵图是尖括号图片标签，原先一律抹成一个空格，渲染后成了 `por cada .`——标点前那个空格是
替身自己加的。`render()` 改成「紧跟句点、逗号、右括号的标签串抹成空，并把标点前多余空格
吃掉」之后，这条规则 es 9→1（剩的 1 条是键盘字符清单）。同一改动顺带清掉 de 10 处、
fr 8 处同类假命中（见下文「读数」）。

两条真拼写错：

- `sauvegade` → `sauvage`。LanguageTool 建议的是 `sauvegarde`（词形最近），但这条的
  「原文」在 `en.gog_1.1.2.3.toml` 里本身就是德语（`Es sei aber noch kein wilder Pirat
  bei ihr vorgefahren`）——「野海盗」，对译是 `sauvage`。**照建议改会错**，这也是
  「不盲信拼写建议」的一个实例。
- `saoûl` → `saoul`。`aoû` 这个组合不合法，1990 改革后的标准写法是 `saoul`。

`oe`／`œ` 统一走合字：`oeil` → `œil`、`soeur` → `sœur`、`coeur` → `cœur`、
`oeuvre` → `œuvre`、`noeuds` → `nœuds`、`oeuvrer` → `œuvrer`，共 14 处。之前一直悬着
「要不要统一」，定下来统一——Tiepolo 字体含 `U+0153`／`U+0152`，合字能显示；同一语言里
一半 `oeil` 一半 `œil` 比两种写法各自成套更难看。`moelleux` 不动（1990 改革对 `moelle`
这一族保留 `oe`）。`Joe`／`Malboeuf`／`Schoemaker`／`Boer`／`Coen` 是专名，不动。

**fr 拼写与 `ou`／`où` 复核。** `FR_SPELLING_RULE` 22 条与 `OU_LEQUEL` 14 条全量取出来后，
真错只有 3 条，已整条替换落盘（`FR_SPELLING_RULE` 25→22）：

- `0xfca882e8`：`ne peuventpas` → `ne peuvent pas`。空格整个丢了，en 基准是 `cannot` 一个词，
  法语必须分开写。
- `0xdaeb048b`：`en bas à droit de l'icone` → `en bas à droite de l'icône`。`à droit` 是「按权利」，
  「在右下角」只能是 `à droite`；`icone` 补重音。en 基准 `bottom right of the ship display`。
- `0x0744a69a`：`aller à@T$DestTown$` → `aller à @T$DestTown$`。en 基准
  `set off for @T$DestTown$`，令牌前有空格；贴死会在游戏里拼成 `àMarseille`。

`OU_LEQUEL` 的 14 条全是不该改的：`les villes où vous trouverez…`、`la zone où a eu lieu
l'attaque` 里的 `où` 就是关系副词，LT 一律建议换成 `avec laquelle/lesquelles`，换了反而错。
`FR_SPELLING_RULE` 剩下的也以引用原文与缩写为主——`peirato`／`kangooroo`／`ganguru`／`batate`／
`Monte vido eu`（史料引语）、`Coûts const.`／`Conv. militaires`／`Nb de canons max`（界面缩写）、
`dummy`／`%s%s`／`%i`（测试串与格式串）。这些一律不改：改了就没有论点或标签会抽长。

**fr 标点前空格。** `FRENCH_WHITESPACE` 30 条里 28 条是同一件事：法语要在 `?`／`!`／`:` 前
留一个普通空格，译文却把它们贴在前一个词上。改法按条扫描、只在尖括号标签之外动手：

- 事件标题 `%1: Route commerciale interrompue` 一类 25 条（`%1` 会被填成数字，游戏里显示
  `64: …`）→ `%1 : …`。同型的有 `%1: %2`、`%1: %2 terminé`。
- 真标点 4 条：`n'est-ce pas?` → `pas ?`、`contrebande?` → `contrebande ?`、
  `(1682? – 1722)` → `1682 ?`、`@g$Reward$!` → `@g$Reward$ !`（游戏里显示 `811 !`）。
- 不动的：`%1:%2`、`%1:%2:%3` 是时间与序号格式串，冒号是分隔符不是标点；键盘符号表
  ``°§$%&()=?\\^';,:`` 是整串字符清单；`Between Us!` 是未译的英文标题。

改完 `FRENCH_WHITESPACE` 30 → 2（剩的就是上面两条不改的），fr 语法命中 475 → 447。

**fr 国名占位前的介词（`PREP_PAYS` 28 条，判不改）。** 命中全是 `qui appartient à @n$X$`、
`appartenant à @n$X$`、`la guerre qui nous oppose à @n$X$` 这几句，渲染把占位填成
`Pays-Bas`／`France` 之后就变成 `à Pays-Bas`、`à France`，LanguageTool 要求 `aux Pays-Bas`、
`en France`。逐条比对官方零售包 `fr.gog_1.1.2.42.toml`：**我方译文与零售原文一字不差**，
模板里本来就是 `à @n$…$`。法语国名前该用 `à la`／`au`／`en`／`aux` 由填充值的性别和单复数
决定，模板拿不到这个信息，任何固定写法都会在另一半国名上错。所以这是**原版模板的结构缺陷**，
不是这一轮能改的译文；判噪声、不进缺陷清单。真要治得改引擎的填充格式（让占位自带冠词），
那是另一道工序。

**de 这一轮（2026-11-20）**：逐条定性 378 条命中（30 条规则），改掉 12 条译文里的 15 处；
之后加了「跨条复检」、让 `<n>` 在送检副本里按句末条件断行、把地名与专名清单整类移出语法层，

154 是清单项移出后、`<n>` 还没条件化时的中间读数：那一步把行内折行也断了段，UPPERCASE
压下去 4 条，但同一批折行进了 `DE_CASE`（14→25），净算下来是 161——`<n:25>` 这类带参换行

规则**（`UPPERCASE` 33、`DE_CASE` 23、`GERMAN_SPELLER_RULE` 23）。降下来的是
送检方式造成的假命中：

- `GERMAN_WORD_REPEAT_BEGINNING_RULE`（116）、`DE_REPEATEDWORDS_NUN`（87）、
  `GERMAN_WORD_REPEAT_RULE`（11）：每条渲染后按空行拼成一批，同一个词在 A 条出现一次、
  在 B 条出现一次，LanguageTool 就判「同一段里重复」——加几个换行都拦不住，它把整个

- `DE_CASE`（25）、`UPPERCASE_SENTENCE_START`（28）：上一条尾部与本条首词粘连，本条首词
  被当成句首或被判「句中大写」。这两类单条复检时**照样报**（15 条里 15 条、13 条仍报），
  说明不是跨条问题，是标签与句子在同一行里混排。把 `<n>` 还原成空行之后，`DE_CASE`

2. 同一批里真正的城镇条目会被 `render()` 整条换成占位城镇。种子只按语言定死、城名池
   只有 `Berlin`／`Hamburg`／`München`／`Köln` 四个，于是每个条目都换到同一个 `Hamburg`，
   二十条拼一批就是连排——送检判成重复词和拼写错。这不是译文里有同名，是清单项被当成
   句子送检的结果。

修法是加 `list_item()`：整条是一个词（`WORD_RX`，≥3 字符大写开头）、两词以上全是首字母
大写（`NAME_RX`）、或整条在 `townset` 里，三条占一即算清单项，语法层直接跳过。这些条目
本来就没有句子可查——没有主谓、没有冠词与名词的搭配；拼错仍由拼写层的词表与 allow 表
抓，两处口径并列。跳过的量：de 1219、es 879、fr 865 条；读数 de 164→154（`GERMAN_
SPELLER_RULE` 39→23）、es 228→221、fr 478→481。这里的 154 只是这一小步的读数，
`<n>` 条件化与带参换行归一之后 de 是 159（见上）。

两词大写标题（`Feindliche Stadt`、`Militärische Stärke`）与两词地名（`New Orleans`）在
文本上不可分，一并归入清单项。这类短语没有 LT 能判的语法，单词拼错照旧由拼写层抓；
性数若真写错（`Feindlicher Stadt`）这一层看不到，记作已知盲区。

试过把本条原文喂进 `render()` 的种子，让同一条可复现、相邻条目取到不同城名，读数反而
172→184：城名池只有四个，`die München` 这类冠词与替身城名性别冲突的 `DE_AGREEMENT`
从 7 涨到 33，净亏。消连排要治的是「清单项不该送检」，不是「换个随机种子」。

**句首大写复核。** 三门 `UPPERCASE_SENTENCE_START` 共 106 条（de 33、es 39、fr 34），
只读探针把每条渲染后的上下文连同原文一起打出来，再按 id 取整条原文与
`en.gog_1.1.2.3.toml` 对照首字母。判据收紧成「原文首字符不是空格、整条 ≥25 字符、
含句末标点」，得 81 条候选，逐条读下来**只有 4 条是真错**，已整条替换落盘：

- es `0xd14f264d`：`¿deseas que organice` → `¿Deseas que organice`
- fr `0x0694a544`：`votre réputation en` → `Votre réputation en`
- fr `0x072a9579`：`je vous suis très` → `Je vous suis très`
- fr `0xd034f206`：`trouvez le coffre` → `Trouvez le coffre`

落盘用 `translate.py apply --ids`，map 的值是**整条新文本**，不是 old/new 对；按
`{id: [[old, new]]}` 写会直接报「映射的值不是字符串」。

判「不改」的三类，各有硬证据：一是 en 基准同样小写、条目在前一句后面续接——
`0xcca05df4~7`（en 为 `' and may now control...'`）、`and the harbor is...` 四连
（`0x133e8429`／`0x17abb14d`／`0x1d6d7bd9`／`0x36d535b4`，en 全是 `and the harbor...`）、
`the military presence in this town...`（`0x0cee08cc`／`0xde5bdde0`）；二是缩写点后
被当成段首（`Ciud. saqueadas/capturadas`、`Dir. administrativo Ascaron UK`、
`Stat. marchandises`）；三是纯标签与标记串（`normal`／`alto`／`max`／`tripulación máx.`／
`en 1 ciudad`、`<ts:0><ts:160>town view/sea battle<t>zoom level<n>in lists<t>scroll`）。

读数：es 221→218、fr 481→478，de 154→159（33 条 UPPERCASE 全是标签与续接，一条真错
都没有；159 比 154 多的是 `<n>` 条件化把折行从 UPPERCASE 挪进了 `DE_CASE`）。
两门的减量里有 1–2 条不来自这次改译，是探针新认出的专名写进替换表后下一轮不再命中。

**跨条复检怎么做的**：`REPEAT_RX`（`REPEATEDWORDS|WORD_REPEAT|PHRASE_REPETITION`）命中的
行，拿该条渲染文本单独 `tool.check()` 一次，单条也报同一条规则才算真命中，否则丢弃。
只复检这一类，de 命中约 200 条、去重后 150 条上下，多花几秒；es 这轮 0 丢弃、fr 0 丢弃
（两门的重复词命中单条都成立）。

真改的三类：

- `weiterhandeln` → `weiter handeln`（`0xc9500bee`）。主句里可分动词必须分开写；
  同在 `damit` 从句里的 `teilhatte` 反而是正确的，LT 建议分写是误报，不改。
- `erobern!!` → `erobern!`（`0xdfb549a5`），双感叹号。
- 数字与百分号／单位之间补空格 13 处（DIN 5008 要求 `5 %`、`30 m`）：
  `<o:…>5%<o>` 三处、`%N%` 模板六处（`%1 %` 占位不动、只把后面的字面 `%` 隔开）、
  `%1h %2m` → `%1 h %2 m`、`Kapazität<n>%1%` 等。

记口径不动的：`aneinandergekettet`（合法复合分词）、`mit Hilfe`／`in Frage`
（DIV 两写并存）、`dich`／`du` 小写（现代正字法）、`auf Arbeit`（北德口语）、
`warm zu halten`、`hierher führt`、`Ich erzähl`（口语省略 -e）、`kn`（节）、`max`、
`lacitos`、人名列表、词源引语（`vido`／`kangooroo`／`ganguru`／`batate`／`hamaka`／
`peirato`／`cabildos`／`xocoatl`）、Miles Sound System 版权段、`Tiepolo_*.res` 文件名。


### 参照层清洁（`analysis/ref_clean.py` → `en-clean` / `fr-clean` / `<语言>-clean`）

一切对照都从 en 与 fr 开始：en 是结构基准，fr 是同源的官方本地化。可这两份本身也有
缺陷，缺陷会被下游当规格抄走。四家零售（de/es/pl/ru）同理——它们既是参照，也能被
抄，先各出一份清洁版。

| 产物 | 是什么 | 拿它当什么 |
|---|---|---|
| `src\orig\en.gog_1.1.2.3.toml` | 原版基准 | 唯一权威，永不改动 |
| `src\orig\fr.gog_1.1.2.42.toml` | 官方法语 | 同上 |
| `src\orig\{de,es,pl,ru}.retail-1.0.0.toml` | 四家零售 | 同上 |
| `build\ref\clean\en-clean.toml` | en 的清洁版（派生） | 结构基准（`<n>`／`<t>`／令牌齐全版） |
| `build\ref\clean\fr-clean.toml` | fr 的清洁版（派生） | 与 en-clean 结构一致的官方译文 |
| `build\ref\clean\{de,es,pl,ru}-clean.toml` | 四家零售的清洁版（派生） | 落译文时的参照 |

```bash
python src\tools\analysis\ref_clean.py --ref en.gog_1.1.2.3 ^
    --patch src\data\qa\ref_patch\en.json --write
python src\tools\analysis\ref_clean.py --ref fr.gog_1.1.2.42 --base en-clean ^
    --patch src\data\qa\ref_patch\fr.json --write
python src\tools\analysis\ref_clean.py --ref de.retail-1.0.0 --base en-clean --add-only --align-idm --align-empty --align-foreign --write
```

三条命令的顺序不能倒：其余五份的结构基准都是 `en-clean`（不是 en），en-clean 先定
下来，后面才知道对齐到哪。es／pl／ru 与 de 同形状，各自带 `--patch
src\data\qa\ref_patch\<语言>.json`。

**`--align-foreign` 按语种退占位。** 零售包里混进来的整条外文（上面说的
`0xd34819b0` 那种德语正文）不该留在参照层：下游照抄会把外语搬进译文。判据在
`src/tools/text/lang_id.py` 的 `is_foreign()`——停用词评分、**对方至少要领先本语言
2 个命中**、`min_hits=3`；版权／许可声明白名单（`Copyright`／`RAD Game Tools`／
`Miles Sound System`／`©`／`All rights reserved`）直接放行，那条
`0xfc512ea5` 属于「各语言一律保留英文」的正当保留。只对 es／pl／ru 跑：fr-clean 的
`0xd3481945` 是零售旧译 `Remarque`，本来就是法语，不能退。

德语和西语／法语的虚词表有重叠（德语句首 `Es` 会撞西语 `es`），所以判据不能只看
绝对得分：`0xd3481944` 有 30 个词、判 de 命中 9 个，但 `es` 也白捡 1 分（`Es`），
早先「本语言 0 分才放宽」的写法把它漏掉了。反过来只看领先分差又会把
`Pedro de la Plesa`（4 词里 `de`／`la` 都得西语分）当西语，所以再加 `min_hits=3`。
两个条件同时卡住，实测三份各退 5 条、不多退一条。

**en 没有更高一层的基准**，所以它的结构缺口只能靠其他 retail 的多数票定：某条 5 个
语种里有 4 个都多一处 `<n>`，就认定 en 漏了。票数不足 3 的不动，只报。票数够了但
**切点**（那处 `<n>` 落在哪句末）机器猜不准，所以按票补数量这一步留给人工，写进
`src\data\qa\ref_patch\<语言>.json`（`{id: [[old, new], ...]}`，每对必须**唯一命中**，
否则整对不生效并报出来）。

**零售这一档要 `--add-only`**，比官方译文严三层：

1. **只补不删。** 德文文本更长、段落本来就比 en 多，ru 把某条压成一整段——按基准删
   `<n>` 会把整段挤成一行，比不修更糟。实测按默认口径跑 de 会删 13 行共 27 处换行，
   其中 `0xf562862e` 是「en 为空、只有 de 有正文」的长篇报名启事，删成一段直接毁掉。
2. **只补在句末。** 零售的句子与基准不是逐句对应，退到「分句处／词边界」的切点多半是
   错的：ru `0x1a444b3e` 会被插在 `"Страны"` 与 `хроники` 之间，把章节标题和正文劈开。
   严档句末不算冒号、引号、书名号（`STRICT_END_RX`），只认 `.!?…`。
3. **缺口超过 2 处就不补，只报。** 差一处两处还可能是段落边界丢了；差三处以上说明这
   条的段落划分本来就和基准不同，自动补是瞎猜。带参换行（`<n:25>`）一律不自动补——
   参数值是排版宽度，位置必须人给。
4. **别家只有 IDM 键名的行，正文退回键名（`--align-idm`）。** `IDM_CONTEST_01_2004_LOG_01_HDR`
   这类值是 mod 作者给「上市版没有这句」留的占位，不是给人看的文本。德语零售把这批
   2004 竞赛日志（15 条：`LOG_00`–`06` 的 HDR/TEXT 加 `POPUP_HDR`）自己译成了德语，
   en/fr/es/pl/ru 全是键名。参照里留正文，下游抄就会把德语搬进别的语言，所以先退回
   键名——15 条逐一（`0xc7537475`、`0xccd432a5`、`0xd10b5c36`、`0xdac343f7`、
   `0xdb66b4df`、`0xe47b2bb8`、`0xee331379`、`0xf7eafb3a`、`0xf93656ab`、`0xfcded04c`、
   `0x0204aa22`、`0x0b715286`、`0x0f3a5490`、`0x25940110`、`0x3426834a`）。
   `+++EMPTY+++` 不算这一类，走下面第 5 条的多数表决。
5. **`+++EMPTY+++` 按多数表决（`--align-empty`）。** 占位的意思是「上市版这句没有」，
   属版本事实、不属翻译，所以不该由单家零售独自判断。票只算「这条存在」的语言——
   缺键不是反对票（fr 比 en 多 42 条、en 也有 fr 没有的）：
   - `0xf562862e`：en/es/pl/ru 四个是占位、de 是 906 字报名启事（fr 无此键）→ 4 空
     : 0 文，de-clean 退成 `+++EMPTY+++`。
   - `0xd49a1310`：en/fr/de/es/ru 五个是占位，pl 是一个空格 → 5 空 : 0 文，pl-clean
     把空格规整成 `+++EMPTY+++`。
   - 反过来的情况（本参照是占位、过半语言有正文）**不动**，只报「要重译，别退」——
     占位换不成正文，那是重译工序。
   清完之后六份 clean 里「哪条是占位」完全一致：同一 id 只要有该条，要么全是占位、
   要么全有正文，0 处冲突。

**占位机制的跨语言共性（2026-11-21）。** 两件，一件是机制读错了，一件是原版没管语序。

先说 `@a$Amount$ @G$Goods$`：**不是**一个整体被替换，是两个独立命名占位，中间的连接字由译文自己写

命名占位不走那张表，所以也没有「让引擎按格生成」的余地。

后果是俄语：数词要支配生格，`@G$Goods$` 只给主格，`@a$Amount$ @G$Goods$` 渲染成 `102 сахар`。

python src\tools\analysis\retail_import.py --lang es --ref es.retail-1.0.0 --repair  # 先修结构再校验

报告按原因分流（不译名单／参照没翻／诗谜与引用要先走另一道工序／标注对不上／参照不是本语言），
结构缺陷（令牌个数、标签个数）仍由 `apply` 拦下，不在这里重写一份判定。

**只差首尾空白不算改动**：零售版的行首偶尔带一个缩进空格、行尾带一个空格，现译没有（或反过来）。这种差异
没有语义，整行覆盖只是把已落盘的值改一遍空白，所以 `build` 判「与参照只差首尾空白（保留现值）」直接跳过。
es 实测这一条让候选从 166 条降到 105 条，剩下的差异都是真改动（带标注 6、只差 `¿¡` 2、其他 6）。

**换语言之前先看报告开头的「## 基准覆盖」**：基准多少条、零售对上多少条（其中多少条是空）、
缺多少、多多少。**缺口**是「基准有、零售没有」的行——零售文件里根本没有这一条，导入对它
们无能为力；但缺口不等于欠译，报告再把缺口按现值分三类：**不译名单**（按键名、表头、脚本
id、存档名，正确做法就是英文原样）、**已有译文**（现值不是英文了，缺的只是零售这个来源）、
**真待译**（现值仍等于英文，也不在不译名单——只有这类才真要动，补法就是按基准英文自己译，
同 id 在别的零售语言里有平行文本可校，但不能照抄语体）。**多出的行**是版本差异
（`fr.gog_1.1.2.42` 比基准多 42 条），参照时直接忽略。实测（基准 3548 条）：es／de／ru
全覆盖 3548/3548，pl 3548/3548 但有 1 条零售为空，fr 对上 3529（缺 19 条＝不译名单 17＋
已有译文 2、真待译 0，多 42 条）。

**承标注是这道工序真正的难点**：现译里有 `[town:Cartagena]`、`[term:en_tools]`
这类标注，零售文本是纯文本，一条都没有；整行覆盖会把标注层抹掉，而标注层是给
`text/marks.py` 消费的（地名按译名表展开、术语按术语表展开）。

标注的参数不是显示文本，是译名表的键（`[town:St. Augustine]` 在 es 里展开成
`San Agustín`），所以搬运规则是「按展开结果定位」：算出标注会显示的字符串，在零售
文本里找它。三种情况分开处理：

- **同一显示文本出现 n 次、标注也有 n 处**（零售也把「Port Royal」写了两遍）：按标注
  先后依次替换第 1、2…n 个出现。标注与显示文本是同一个词，换哪一处显示效果一样，
  只有「第几处」是确定的，所以这是安全的。
- **零售写法不同**：整段找不到时依次退一步——去掉西语冠词再认（零售写 `Habana`、
  译名表是 `La Habana`），再不成就用标注参数原文再认（零售整行留英文 `Turk Islands`）。
  两者都要求出现次数与标注处数相等。
- **零售承载不了**：出现次数少于标注处数（零售少写一处地名）、或整段不是同一段文字，
  整行放弃并报原因。位置猜错会把地名套到别的词上，比不导更糟。
`[riddle:…]` 与 `[ref:…]` 整行跳过：前者要重算 clue 并逐字核对（走 `riddle_marks`），
后者会牵出另一条文本。

  零售给的是不同版本的教程/摘要，现值忠实基准，不导。
- **零售地名写法不同**（`0xc77f4d5e` 的 `Charles Town` 少一个 e、`0xd607db6d` 同型、
  `0xe6490f96` 的 `Turk Islands` 留英文原名）：现值用译名表展开（`Islas Turcas` 等），不导。
- **零售少写地名，承载不了现值的多处标注**（`0x00bff5f3` 三处只写一处、`0x353cae5f` 三处只写两处）：
  标注层不能删，不导。
- **零售标点/引号不合规范，或漏了整句**（`0xd07dbe34`、`0xd4cd0f44`、`0xd4cd0fb6`、
  `0x08e78a8c`、`0xeb1ce06f`、`0xd9720472`、`0xddbd4de4`、`0x03d3dcd8`）：现值已按 en/fr
  精修过。这一类的用处是**防覆盖**——`--write` 是「替换已译」，不设保护的话下一次落盘
  会把这几行按零售原文盖回去（es 上实测盖掉过一轮 5 行，只能从 HEAD 取回；`0x03d3dcd8`
  甚至被盖掉了一句零售本来就没有的 `Estaba en la cocina en ese momento.`）。
  所以凡是手工改过、且零售版更差的行，落盘后都记进 hold，别指望记住。
- **零售与现值同时短一截**（`0x084340c7`、`0x2efebfe6`、`0xe1cdc367`）：en 基准里的整段
  两边都没有，工具判不了这种「都没写」，只能照 en 补。补完同样进 hold，理由同上一条。

判断这三种「短」的时候别只看字符数：`ref_check` 的「长度骤降」比的是 en 基准与**参照**
（零售），不是与译文，所以它报出来的缺口要回 `es.toml` 自己看现值到底有没有那句话。

`0xd3481944` 这类「基准与零售都不是本语言」的行不进 hold：拿同源的法语版当参照重译一遍
（句法照 fr、意思照德文，`!` 句补 `¡`），死了就改译文本身，而不是放着不动。这条的 clean
现已由 `--align-foreign` 退成占位，`retail_import` 拿它当参照时本来就导不进去，已有 es
译文不受影响。

验过的两个坑（都已内置，别改回去）：`[riddle:…]` 的 arg 里带 `source=…@sha256=…`，**上千字
都有**，判「要不要延后」只能看前缀 `\[(riddle|ref):`——用带上限的 `MARK_RX` 去找会漏，整行就
当成没标注被覆盖，标注层直接没了（es 上真丢过 4 行）。判断「这一段是不是目标语言」不能用
字种正则，拉丁系五语只能走词典命中率（见上）。

#### 工具链的顺序：原始零售 → 清洁版 → 以清洁版为基准（`--clean-ref`）

一条语言要同时对着三份文本，分工别混：

| 文本 | 是什么 | 拿来干什么 |
|---|---|---|
| `src\orig\en.gog_1.1.2.3.toml` | 原版基准 | 结构（`<n>`／`<t>`／百分列／项目符号）与令牌条数的唯一依据 |
| `src\orig\<lang>.retail-1.0.0.toml` | 原始零售 | 措辞来源；也是「零售到底怎么写的」的唯一证据，永不改动 |
| `build\ref\retail_clean\<lang>.retail-1.0.0.toml` | 清洁版零售（派生） | **落盘与后续所有校验的输入**：结构已对齐、标点已按本语言定则、空白已规整 |

顺序是固定的三步，别跳第一步：

```bash
# 1) 原始零售 → 清洁版（只生成派生文件，不动译文）
python src\tools\analysis\retail_import.py --lang es --ref es.retail-1.0.0 --clean-ref
# 2) 以清洁版为参照落盘
python src\tools\analysis\retail_import.py --lang es ^
    --ref build\ref\retail_clean\es.retail-1.0.0.toml --repair --write
# 3) 后续校验也用清洁版当参照
python src\tools\analysis\ref_check.py --ref build\ref\retail_clean\es.retail-1.0.0.toml
```

拿原始零售直接 `--write` 会把它未经规整的标点、空白一并落进译文（es 上真这么错过一次：
31 条落进来，回退的路径是「按清洁版重跑一遍」，标点才被规整过来）。工具现在对这件事有
提示：`--write` 的 `--ref` 不在 `build/ref/retail_clean/` 下就会打一句「参照未经清洁」。

`--clean-ref` 也有「先清洁再导入」的一步到位写法（清洁版走内存，不落临时文件）：

```bash
python src\tools\analysis\retail_import.py --lang es --ref es.retail-1.0.0 --clean-ref --write
```

但拆成两步更好审计：清洁版的 diff 值得单独看一眼再落盘。

`--clean-ref` 的报告另写 `build\qa\retail_clean_<lang>.txt`（「## 改动明细」＋「## 留着没修的」
两节）。清洁版是派生文件（`build\` 一起 gitignore），随时可重建，**不进库**；原始零售文件
一字不动，仍是对照基准。

清洁只做能事后核对的写法修正，口径与边界：

- **换行标签个数必须与基准一致**：`<n>` 与带参数的 `<n:25>` 各自按类算，少就补、多就删，
  没有「差额太大就不动」的赦免。切点按顺序挑：最长的段里两侧都还剩 6 个字以上的句末 →
  任一段两侧都还有字的句末 → 任一段的逗号／分号分句处 → 行末（多一个空段）。越往后越像
  推定，位置不满意就人工改原始零售或进 hold 名单，别让个数对不上。
- **其余结构同样以基准对齐**：百分列还原、`-<t>` 项目符号补回。
- **标点按本语言定则**：西语问句／感叹句缺 `¿`／`¡` 就在句首补（插在第一个字母前，`"¿…?"` 也
  在引号内侧）。判句尾判得紧：`?` 后面跟破折号、括号注不算句尾（年份缩写 `(1682? – 1722)` 是
  常客）；紧跟引号括号的 `!` 是引文内部的，不补；起头符号跨 `<n>` 认（`¡%1,<n>me alegro…`
  已经有了）；没有词的字形测试串（`°§$%&()=?…`）不补。`!.`／`?.` 这种多跟一个句号的去掉。
- **空白**：去首尾空白、压行内连续空格；含 `<t>` 的行不压（那里的空白是列排版）。裸 `\t` 只报
  不转。
- **token 缺成分只报**：`%1`／`@A$X$` 少一处、引号不成对、整行不是目标语言（词典命中率判），
  都进「留着没修的」清单，等人工改原始零售或写进 `src/data/qa/retail_hold/<lang>.txt`。
  不译名单与 hold 名单里的行整个跳过（版权声明本来就该与英文一字不差，别拿词典去判它）。

es 实测（hold 名单涨到 21 条之后重跑）：改动 246 条，`<n>`／`<n:25>` 与基准逐行比对
**0 条不一致**；剩 25 处进清单（hold 名单行每条报一次、令牌 5 条）。用清洁版复跑导入：
候选 137 条、`apply` 可落 30 条、拦 5 条（全是令牌），结构类拦截一条不剩。

引用清洁版时记住它是派生件：措辞异同仍要回原始零售核对，别把清洁版的 diff 当成「零售原文」。

### 断行长度复核

`line_run.py` 回答一个机械问题：断完之后，最长的一段有没有超过上限。

口径只有一条：引擎只在 `U+0020` 与 `<n>` 处断行，一段里没有这两样就永远排在同一行。
所以量的是**最长段的可见字数**——标签不计、标注不计，变量 `%1` / `@a$Name$` 记 1 字。
不是像素宽度（控件宽度没在游戏里实测过）。

| 语言 | 上限（含） | 级别 | 说明 |
|---|---|---|---|
| zh | 14 | E | DP 预算 13，不可拆单位允许溢出到 14；>14 即回归，卡流水线 |
| ja | 13 | W | 同一全角预算（方块字，同一控件装得下同样的字数）；2026-11-21 机械断行 + 手工断点后新增 0 条，见下 |
| ko | 13 | W | 同一全角预算；当前 9 条正文超限 |
| ru / de / es / fr | — | 跳过 | 拉丁文字按空格断行，最长段就是一个单词，长度由构词决定，补空格解决不了 |

CJK 语言只判「正文段」：`Tiepolo_black14x14aaFHk.res`、`IDM_CONTEST_01_2004_LOG_04_TEXT`
这类路径与键名不算排版缺口。上限与级别都写在 `LIMITS` 里，改一个数字、一个字母即可；
把 ja 的 `W` 改成 `E` 就是「日语清零后开始卡流水线」。

```powershell
python src\tools\analysis\line_run.py            # 摘要
python src\tools\analysis\line_run.py --all      # 列出全部命中
python src\tools\analysis\line_run.py --lang ja  # 只跑一门
python src\tools\analysis\line_run.py --lang ko --update-baseline   # 显式收进基线
```

报告落 `build\qa\line_run_<lang>.txt`，E 级**新增**命中时退出码为 1。
摘要行印两个数：`命中最长` 是超限条目里最长的那个（要处理的到底多长），
`全文最长` 是全表最长段（往往是路径、键名这类技术串）。只印一个数时，
ko 会显示「最长 31」，看着像有一批 31 字的超限文本，实际命中最大只有 18。

不打算再动的命中记进 `src\data\baselines\line_run_<lang>.txt`（一行一条
`id<TAB>实测字数`），报告分「新增」与「基线内」两段，退出码只数新增。
否则 ko 那 9 条人名带括号的旧账会天天报「超限」，看的人很快就会当它不存在。
基线只能 `--update-baseline` 显式改写，不跟着扫描自动更新 ——
否则新增命中会被顺手收编，这道检查也就名存实亡。

同一个度量也做成了给人看的页面 `build\preview\断行观察窗.html`（上限可调、柱状图、命中列表），
它 `import` 的就是 `line_run.py` 的切段函数，所以页面数字与流水线判定不会各算各的：

```powershell
python build\notes\experiments\break\brk_dump.py   # 重算数据（build 目录不进仓库）
python build\notes\experiments\break\brk_html.py   # 生成 build\preview\断行观察窗.html
```

页面落在 `build\preview\` 而不是 `dist\`：`dist\` 只允许 `*.zip`、`SHA256SUMS.txt`
与 `release.json`，不放过程产物。（见[发行规范](发行规范.md)），可查阅的 HTML 属于预览产物。

**ja 断行定性（2026-11-21）。** 日语这条 453 条不是「翻译没排好」，是**机制上没有断点可用**。

引擎只在空格与 `<n>` 处断行，日语没有空格分词，长句只能自带 `<n>`。全表复算（`build/qa/ja_line_all.py`、
`ja_line_cls.py`，按同一口径切段）：475 条超限、752 个超限段，条目长度分布
14–17 字 297、18–21 字 112、22–25 字 37、26–31 字 29，最长 31。扣掉键名／资源名／数值这类非正文后
就是流水线报的 453 条。

关键是这 752 个段里**没有一个能靠标点切开**：

- 段内可切标点（`、。！？`）且切完两侧都 ≤13 字的：**0 个**。
- 有内部标点但切了仍有一侧超限：2 个（`0xd4cd0faf`、`0xd9fb62e9`，标点要么在末尾、要么切完一侧仍长）。
- 其余 **750 个段连内部标点都没有**：`副王の所在地であってはなりません！`、`フリープレイでも起こります。`、
  `イングランドのミントクッキーなどが入っていたようです` 这类，整句只有结尾一个标点。

也就是说「译者在标点处补 `<n>`」这条路对日语不成立——超限段本身就是无空格、无内部标点的连续假名汉字串。

**决定（2026-11-21）：机械断行先切，切不动的进手工断点层。两条批量路线仍否决。**

- **译文层批量加 `<n>`：否决。** 标签门要为 ja 开「不与 en 对位」的例外，`text_lint` 的结构校验
  要按语言分口径，多出来的 `<n>` 每轮还得重判位置；换来的只是把连续假名硬拆两行，位置好不好
  自动选点判不了。
- **引擎层按字数硬切：否决。** 不看词边界，`インターナショナルプロダクトマネージャー`、
  `IDM_CONTEST_01_2004_LOG_01_HDR`、`9.9990000000000006` 都会被切开。
- **引擎层按词边界切：采用。** 实现在 `src/tools/text/lang_rules/ja.py` 的 `JaLineBreak`，
  janome 分词后只认两类切点：强切点（助词后、接续词后、标点后）优先，强切点不够时才退到
  弱切点（普通词边界），但拉丁/数字串内部与专名内部不给弱切点。段边界是 `<n>` 与空格——
  空格本来就被引擎断，所以「已经用空格排好的句子」不会被重复插 `<n>`。
- **机械层切不动：交手工断点表。** `src/data/line_breaks/ja.toml`，一行 `"0x…" = [12]`。
  顺序是**先机械切、再补空格**，手工层只补 `U+0020`、不写 `<n>`——人工挑的断点用最普通的字符
  表达，标签门与 `text_lint` 都不必为它开口子。位置口径是从整条开头数**非空白**可见字，数到第 N 个
  就在它前面补一个空格；标签 `<…>` 与已有 `<n>` 不数，空格／制表不数（引擎本来就在空格处断），
  占位 `@a$Name$` / `%1` 各数 1 个字。位置越界、不严格递增、或补完仍有段超过上限，当场抛
  `ManualBreakError`，不会静默落盘。
- **手工接管的是「块」，不是整条。** 块 = 译文里空格分隔的一段。位置落在哪一块，就由人工决定
  这一块的断法：块里机械插的 `<n>` 全部作废、改用空格，其它块保留机械切。这样 838 字的
  `0xd4cd0fb4`、522 字的 `0xd4cd1020` 不会因为一处人工位点把其余段的机械断行全废掉；
  反过来，`0xc73939cf` 这种机械能切却把「かもしれません」从「かも」处割开的，人工点位同样
  落在机械结果上，把那一块重排。
- **不处理的条目：`src/data/line_breaks/ja_skip.txt`。** 一行 `id<TAB>理由`，`#` 开头是注释。
  命中这里的条目机械层完全不碰：不切、不计「切不动」、不进手工清单。键名（`IDM_CONTEST_*`）、
  字体资源名（`Tiepolo_*`）、开发占位数字（`9.9990000000000006`）、字体覆盖测试串都属这一类，
  它们不是正文，切了反而制造问题；超长拉丁人名（`Niestadtkötter`）按「放行」登记，理由写清楚。

读数（2026-11-21，`python src\tools\text\engine_text.py --lang ja --stats`）：3548 条里机械断行
改动 438 条、新插 `<n>` 726 处；切点 640 处在助词后、60 处在名词/用言/标点后、**0 处在词内部**。
37 条切不动逐条定性后归零：21 条技术串进 skip 名单、16 条专名/职位名靠手工位点补空格。
现在读数「机械改动 454 条｜手工断点 17 条｜切不动 0 条」，`line_run.py --lang ja --all` 新增 0 条
（`全文最长 31` 是键名这类技术串，不进命中）。2026-11-22 去掉片假名中点后为

口径与反例打在 `tests/test_line_breaks.py`（34 条），含「位置只接管所在块」「块内机械 `<n>` 作废」

### W 级豁免（`src\data\lint_ok\`）

`text_lint` 的 W 级里有一类永远不会靠改译文消失：判据本身不该管的那种（西语生卒年
不确定的 `?`、纯标点的图标条目、日语引文里的常体、字形覆盖测试串）。判断结果以前只
留在口头和提交信息里，下次重跑还得重新判断一遍。现在落到文件：

```
src\data\lint_ok\_common.txt     # 各语言共用
src\data\lint_ok\<语言>.txt      # 本语言专用
```

一行 `id<TAB>理由`，`#` 开头是注释。报告头先打「E 级 N 条，W 级 M 条」，再打
「已豁免 W 级 K 条」并逐条列 id、原告警与理由 —— 豁免是**点名**，不是静默消失。

- **只豁免 W 级**。E 级（模板不一致、空值、标注错误…）一律不许免：那些改得动，
  也不该留着。
- 能改判据的就改判据，不要往豁免里塞。现存只有 fr 那一条字形测试串：
  字符串本身就带 `²³€`，改了就没法再测字体覆盖，属于「值不该动、判据也不该改」。

同一层次的「不打算再动的命中」记在 `src\data\baselines\line_run_<lang>.txt`（见上），
两者取向一致：**报出来但不卡流水线**，且必须写清理由。

## 韩语量词复核（`ko_unit_checks`）

判据只有两条，都由 Kiwi 的词元决定，子串不算（正则找量词时 616 处命中里
520 处是 `대출`/`대륙`/`대신` 这类词内误命中）：

1. **缺量词**：数词位后面直接跟白名单可数名词、中间没量词 —— `%1 배`
   会渲成「10 배」。白名单是 `배/선박/함→척`、`선원/병사/정착민/주민/사람→명`、
   `물자/화물/곡물/목재/의류/상품→통`、`상자→개`、`포/대포→대`。
   不收 `선장`：英文 `Captain %1` 里的 %1 是名字，韩语写「이름 + 직함」
   `%1 선장이` 本来就对。
2. **搭配错**：数词 + 量词 + 名词，但名词要的不是这个量词 —— `5척의 병사`、
   `3개의 배`。

边界：数词位只认占位符与阿拉伯数字，固有数词（`두 배로 늘었` 的翻倍、
`한 사람` 的一个人）不参与；标签按段切开再分词，否则
`물자:<t>%2<n>대포:<t>%3` 会把 %2 拼成「%2 대포」。缺 `kiwipiepy` 时整条跳过。
存量 3090 条实测 0 命中，是给后续批次设的栅栏；`--lang ko` 时挂在 E 级。

这道门同时挂在 `apply` 上（`unit_violations` 借同一份规则）：批次十四的
`@a$Amount$통`、`@I$NumShips$척`、`1,500명` 那几处以前全靠手写对，
写成 `@a$Amount$ 물자` 会一路写盘，要到 `check.py` 里的 `text_lint` 才报。
