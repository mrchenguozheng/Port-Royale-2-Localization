# 界面映射（总览）

记录“哪句话出现在哪个界面”。这一主题按界面分卷存放，**不要再写回单个大文件**。

**键与界面位置和语言无关**：游戏按 key 取串，同一 key 在每个语言包里是不同的文本，
但“这一屏画的是哪几个 key”对所有语言都一样。所以各卷按“界面 → 键”记，
语言列只作对照；采集时用的是德语排查包，中文列直接取 `zh.toml`，
没有逐条实机核实过（中文界面要用 `zh-debug` 再走一遍）。

采集方法见 `docs/德语校对流程.md` 第 8 节。反查（看到 `[XXXX]` 想知道是哪条）用
`build/qa/de_index.csv` 按标记尾数 grep，或查 `build/debug/<lang>-debug/<lang>.txt`（带全标记的中间产物）。

## 本目录同时是排查包的“已查清清单”

重编 `<lang>-debug` 时，`debug_pack.py` 会扫描**本目录下全部 `.md`**（含本文件）：
凡是一行里既有 `[XXXX]`、又有 `0x…` 键，对应条目就不再带标记；整段声明按下面三种写法处理。

- 逐条：同一行既有 `[XXXX]` 又有 `0x` 键 —— 这一条已实机确认。
- 按类别整体清除：`` `0xfc51xxxx` ``（名表 131 条）、`` `0xcf57xxxx` ``（姓表 103 条），写在“姓名”那节。
- 整体保留：`` `0xfc512ea5` `` —— 名表段开头那条不是人名，是 Miles Sound System 的版权声明。

顺手记一条，下次重编那几行就恢复成正常文本；没记的继续带标记，不会误清。产物目录里的 `cleared.txt` 是每次实际清掉的键清单。
**推断行必须把标记列写成 `—`**（见 `09-推断-连续键区.md`），否则会被误当成已确认。

现状：3548 条里已清 2748 条（按类别整体清除的名表／姓表 + 逐条确认 + 10 卷那批「无字可译」＋片尾滚动屏一批 + 推断批次），带标记 800 条（以 `debug_pack.py` 的产物计数为准，改完卷要重编一次核对）。

写新内容时按界面归卷：菜单/剧本 → 01，自由模式与姓名 → 02，设置页 → 03，顶栏与开场 → 04，
城镇与地图 → 05，船只 → 06，各种窗口面板 → 07，编年史/国家/统计 → 08，推断 → 09，
没有文字可译的那类（图形键、专名、格式串除外）→ 10；
跨卷的界面在总览这里列一行指向两卷即可，不要为了“完整”把几卷合并。

### 历史随笔这一族到底在用没用（2026-11-15 核查）

想直接查「游戏有没有引用这些键」走不通：把游戏目录所有 `.exe`/`.dll` 按 4 字节小端扫了一遍，连实机上看过、确定在用的标题条（`0x1ab9b63f`、`0xd47ceb94`）都 0 命中——键不是编译进二进制的常量，串全部由数据文件驱动，所以「有没有被引用」读不出来。

结构证据偏向「在用」：18 条话题问句与 30 段随笔正文主题逐条对得上——Avery → `0xd4cd0f3d`、Teach → `0xd4cd0f3e`、契约劳工 → `0xd4cd0f41`、航海法案 → `0xd4cd0f42`、神话起源 → `0xd4cd0f44`、Raleigh → `0xd4cd0faf`、德国探险 → `0xd4cd0fb1`、托尔德西利亚斯 → `0xd4cd0fb3`、七海 → `0xd4cd0fb5`、百慕大 → `0xd4cd0fb6`、Polybius 论 pirate → `0xd4cd0fb4`、哥伦布 → `0xd4cd1020`。这种「问一句、给一篇」成对出现，只可能是设计出来的功能，不像废弃文案。

反面证据也要记：这一族只有问句和正文，**没有任何一条窗名、按钮、翻页或关闭的串**；真在跑的窗口一般至少有个标题或「继续」。加上全库无 library／Almanac／Handbuch 类界面名、手册 0 命中，所以「内容做进去了、入口被裁掉或没接」这种残留可能性也没法排除。

定论只能实机：找那位说「我正在起草一篇新的历史随笔」的人（`0xd4b8ac64`–`0xd4b8ac66` 是他三句招呼），看他会不会真的翻开这些随笔、窗顶写什么。

三处仍卡在「同文键用哪条」的：`%1 defeated` 三条、`Scenario completed` 五条、`Hot on the Trail of Blackbeard!` 两条 —— 屏上分不出，只能在本机 debug 包里看标题条上的标记。

## 自查坑：键比较的写法（2026-11-16）

判断某条键是否已在册，必须用 `("0x" + k[2:].upper())`——前缀小写、尾数大写，
与 `load_cleared()` 入库的格式一致。写成 `k.upper()`（前缀也被抬成 `0X`）会与入库键永不相等，
结果是**已清的键一律显示为「带标记」**。本日一次探查就因此把六条早已在册的键当成待清，
直到对照计数没变化才发现。凡要确认「还剩哪些」，跑一遍 `debug_pack.py --lang zh` 看总数，
不要只看逐键查询。
