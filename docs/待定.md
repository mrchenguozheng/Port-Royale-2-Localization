## 1. Steam 加载链：已解决（宿主 DLL 代理）

**结论**：Steam 原生 `PR2.exe` 不会从游戏目录自然加载 `VERSION.dll`；改为替换它静态导入的
`Ascaron.Logging-2.6.dll`，由代理转发 `Log` 并加载 `PR2LocalizationCore.dll`。该路线已在
Steam 实测出现中文界面，挂载/还原见 `PR2HostMount.ps1` 和 `pr2ctl/steam_host.py`。
玩家侧不再需要手工挂载：启动器判出 Steam 版后在启动前调这个脚本，还原由 GUI 的
「还原 Steam 原版」或 `PR2Localization.exe --restore` 完成。

**旧现象**：在 Steam 英文版上，`PR2Localization.exe` 能启动游戏，但界面仍是英文，
语言包没有被替换进去。GOG 英文版同样的步骤一切正常。

**已查明的**：

- Steam 目录里的旧 `PR2Localization\logs\runtime.log` 证明本项目旧 DLL 曾在 Steam 进程里
  成功命中 `ResolveByHash`、`Add` 和 vtable；
- 同一份 Steam 目录也有第三方 addon 的失败日志
  （`CStringManager import contract mismatch`），说明“引入别的本地化 DLL”不是答案；
- 旧启动器的远程注入时机早于 `A2dLib-2.20A.dll` 加载，DLL 里的固定偏移
  hook 在 `A2dLib` 未到位时直接放弃，之后不再重试。

**历史实施**（保留作诊断记录；当前已改用宿主 DLL）：

- 新增代理 `VERSION.dll`：`PR2.exe` 导入表里有它，代理转发系统 version API，
  工作线程 `Sleep(50)` 后加载同目录 `PR2LocalizationCore.dll`；
- `PR2LocalizationCore` 新增 250ms 重试线程，最多 120 次，等 `A2dLib` 到位再装
  `Add` IAT hook / `ResolveByHash` thunk hook；
- `g_pStringMgr` 优先用 `A2dLib` 导出符号定位，固定 `+0x142084` 只作 fallback；
- `ResolveByHash` 先校验 thunk 的 `E9 rel32` 目标，未知构建只记日志不盲写。

**已确认**：Steam 实测 `PR2Localization\logs\proxy.log` 出现
`[host] loaded PR2LocalizationCore.dll`，`runtime.log` 加载了 `zh` 语言包；界面为中文。
CEG 只校验 exe，宿主 DLL 路线不改 exe，理论上不触发完整性错误；实际启动正常。

**旧的最小实验**仍然有效：只注入一个会写日志的极简 DLL，能区分“注入失败”
和“注入成功但 hook 没命中”。现在代理日志已经承担这个作用。

## 3. hook 与游戏版本绑定

代码按固定偏移取 `A2dLib-2.20A.dll` 里的 `ResolveByHash` thunk。换任何游戏版本
（包括同是 GOG 的法语版、或未来的补丁版）都可能需要重新定位偏移，否则整体不生效。

现在已做两层收敛：

- `ResolveByHash` 先校验 `+0x1DC5` 的 `E9 rel32` 是否确实跳到 `+0x25C70`，
  不匹配只记日志、不写入；
- `g_pStringMgr` 优先取导出符号，固定 `+0x142084` 只作 fallback。

长期做法：把 `ResolveByHash` 也改成按导出名/特征码定位，而不是写死 thunk；
至少要把「偏移表」与「版本号」的对应关系记下来，换版本时一眼能看出要改哪。

## 4. 中文长句整条不显示

引擎按空格切词。整串汉字没有空格时会被当成一个超宽单词，**超宽的行是整条丢弃**，
不是截断。所以偶尔会出现「这一条在游戏里完全看不到」的情况，而构建产物里一切正常。

目前只能逐条实测。已经做的缓解是在**构建期**按词补空格
（`zh_space.py`，连续 13 字之内必有一刀），让长句有机会在空格处换行；
句中停顿标点（`，。！？；：、…—`）后一律断一刀，标点处一定可断。
控件宽度没有实测过，所以不做「按像素估算宽度」的离线检查——
那种数字只是推测，早先的宽度粗查工具已删除。

## 5. 字形覆盖

游戏自带字体没有中文字形，必须替换 `fonts\*.TTF`。现在只做映射：把完整 Noto 静态
字重（俄语四个自建文件）平铺到 `PR2Localization\fonts\`，由
`font-map.ini` 把四个逻辑名映射过去；同一次安装只放一个语言。

早期“以原版拉丁字体为 base、按用字从 donor 缝合”的路径已从仓库移除，
`--fonts stitch` 与 fonts presets 都不再存在。

**实机验证（2026-10-22）**：主菜单中文正常，标题字体有中文字形，无异常。

可选替代：不分发字体，改用 `PR2Localization\fonts\font-map.ini` 映射系统字体
（配置优先，内置字体兜底）。非拉丁系默认映射 Noto 对应字体，不使用 `.ttc`
集合；系统字体不保证存在，发行时可用 `release.ps1 -Fonts config`。

**波兰语（已实测，2026-11-19）**：pl 用九个拉丁扩展 A 字母（ą ć ę ł ń ó ś ź ż，另有大写）。
用 fontTools 直接读 `assets\fonts\original\` 四个字体的 cmap，逐字比对，结论：

| 原版字体 | 码位 | 缺字 |
|---|---|---|
| `ARIAL.TTF`（正文） | 1186 | 0（18 个字母全覆盖） |
| `ELGRECO_.TTF` | 223 | 16（ą ć ę ł ń ś ź ż + 大写；`ó` 在 Latin-1 里反而有） |
| `Tiepolo_black.ttf` | 223 | 同上 16 |
| `Tiepolo_bold.ttf` | 223 | 同上 16 |

所以正文不换，三个标题槽位换成 `src\tools\font\build_lat_fonts.py` 生成的
`PR2PlDisplay-Head/Black/Bold.ttf`（Noto Serif 按原版对应字体的 cap height 与
平均 advance 缩放，缩放比见脚本日志：Head 0.566/1.014、Black 0.853/0.860、
Bold 0.852/0.860；三个文件对 134 个用字缺字 0）。`font-map.ini` 的 `[pl]`
`ARIAL.TTF=none`，其余三项指向替换字体。原先挂着「实机截图核对标题与英文同高同宽」，
2026-11-21 用户定为**基本免检**，不再单独核对；同批实机只发现标题与两条标签被控件宽度裁掉，
已按长度缩（`Twoja firma` / `Bud. mieszk.` / `Pojemność:`，提交 `d0f8ad6`）。
不要用「把 ą 写成 a」这种改译文迁就字体的办法。

pl 的单行控件长度风险与估算口径（2,304 条可比条目、91 条强候选、推测 60–170 处被裁）
记在[翻译局限](翻译局限.md#2026-11-21波兰语控件裁切与超长估算)。

## 6. 旧存档名乱码（只能手工改名）

PR2.exe 只导入 ANSI 版文件 API（`FindFirstFileA` 等），文件名里的中文会被
按 Latin-1 逐字节映射，显示成 `×Ô¶´…`。

- 新的自动存档已经改成 ASCII（`Autosave %02u`），不会再乱码；
- **2026-11-15 实证**：白天把 `0x33c2c533` 译成「自动存档 %02u」后，存档目录里立刻多出两个
  `脙聴脙聰脗露脗炉脗麓脙娄脗碌脗碌 02.pr2`／`… 03.pr2` 这种双重乱码文件名，列表里显示成 `-ÂÃ" Â,Â¶…`，
  点进去弹「存档无效！」。同一目录里德语包跑过的是 `Autospeichern 02.pr2`（ASCII，正常）——
  说明**文件名就是这条模板串本身**，中文一定坏。现已回退成 `Autosave %02u`；快速存档的两条
  （`0x391f78da`／`0xd0d692a5`）同理一并回退成 `Quick Save`，代价是 ESC 菜单第一块显示英文；
- **已经存在的**中文名存档文件仍然会乱码，手动改成 ASCII 名字即可；
- 彻底修复需要 hook 引擎“文件名字节 → 文本”那一小段，代价较大，暂不做；
- **2026-11-19 复查**：`ee97ac4`（全表一致性复查）又把 `0xd0d692a5` 改回「快速存档」，
  理由是「同原文另一条已译、德法均已本地化」—— 但德法那两条是 `Autospeichern` /
  `Sauvegarde rapide`，纯 ASCII，和中文不是一回事。已回退成 `Quick Save`；同理清掉了
  ja `オートセーブ`／`クイックセーブ`、ru `Автосохр.`／`Быстрое сохранение`、
  ko `빠른 저장`、es `Guardado rápido`（`í` 也是非 ASCII，改 `rapido`）。
  现在这条规则进了流水线：`src/data/keep_as_is/<lang>.txt` 里理由写成 `save-name` 的条目，
  `text_lint` 只认「纯 ASCII」，不再认「等于英文」；同一句英文对应菜单木牌与文件名两条时
  （`0x391f78da` 与 `0xd0d692a5`），在 `src/data/allow_same_src_<lang>.txt` 里登记例外，
  「同原文异译」不再误报。
- **2026-11-19 同类普查**：`scenario00X - @I$Idx$` 六条也是存档名模板（场景存档写盘成
  `.pr2` 文件名）。es 曾把它译成 `Nacimiento` / `Aprendizaje 1` 等西语场景名 —— 纯 ASCII，
  不会乱码，但那是我们自己给的名字，与场景的内部分支可能对不上，已回退成英文原样并登记
  `save-name`。要判断「译名会不会让引擎找不到文件」，需要实机截一张场景存档列表来对照。

## 相邻占位符：哪些是「名 姓」，哪些是格式串

游戏里不少字符串把两个占位符并排写（`%1 %2`、`%2 %3`）。**2026-11-21 起中文与日文
的姓名拼接一律用空格，不再插 `·`／`・`**（见下一节「同文族」），所以这里要判断的不再是
「要不要加中点」，而是**这两个位置到底是不是名和姓**——是姓名才按空格排版，
是「等级 + 姓名」「数量 + 单位」就按原样的间隔处理。

| hash | 判定 | 说明 |
|---|---|---|
| `0xE23F403A–D` | 名 姓（`%2 %3`） | `%1`=等级、`%2`=名、`%3`=姓；姓后接「到」留一个空格 |
| `0x200D4E11` | 名 姓（`%2 %3`） | 同上，用于拼显示名 |
| `0x28B1F98D` | 名 姓（`%1 %2`） | 开局欢迎语，后文另提等级，说明前两段是人名 |
| `0xCA6F7276` | 名 姓（`%2 %3`） | 任务里「某人的名字 正在招募英雄」 |
| `0xDBCAC2B1` | 名 姓（`%2` ＋ `%3`） | 信头，2026-11-21 改作 `%1，<n>%2，%3`（夹在句中的姓名后面要接从句，用逗号比中点顺） |

**仍判断不了的（保持原样，不加符号）：**

| hash | 内容 | 判断不了的原因 |
|---|---|---|
| `0xE7270933` | `<gs:TEXTFLUSS_KEINEHOEHE>%1  %2` | 只看见两个数字位，没有上下文 |
| `0xFFDC2433` | `<c>%1  %2` | 同上 |
| `0x08B186EF` | `<r>%1<n>%2   %3` | 同上，`<r>` 是颜色标签 |
| `0x16656B80` | `%1 %2<g:scripts/intext_herz_800x600.screen>` | 末尾是「心」的图标，两位可能是数值 |

### 标签含义

- `gs:` = 图形脚本（graphic script）指令，由界面渲染器消费，**不是可译文本**；
  必须原样保留，否则该行会失去排版或图标。
- `gs:TEXTFLUSS_KEINEHOEHE` 是德语：`Textfluss` = 文本流、`Keine Höhe` = 无固定高度，
  即「文本按内容自动排布、不预留高度」。它只影响排版，没有字面含义可翻。
- `<c>`、`<r>`、`<n>` 分别是颜色 / 红色 / 换行；`<g:scripts/…>` 是引用一个界面图形
  （`intext_herz` 即「心」的图标）。

要把这四个也定下来，只能实机看它们出现在哪个界面、旁边是什么数。

### 同文族 `%1 %2`（八条，2026-11-21 定稿）

`0xd390afe5`、`0xe2cb2041`、`0xe78a6f65`、`0xfc7ddb7d`、`0xfe6eb6fe`、`0x08d29537`、
`0x11874def`、`0x13009885` 八条原文同为 `%1 %2`，界面各存一份。归属已知的：

- `0xe2cb2041`：工具行数值对（实机 `5` 桶 ＋ `0,0`），空格分隔。
- `0x11874def`：编年史的名＋姓（08 卷）。
- `0x13009885`：船／船队名条（06 卷）。
- `0xfe6eb6fe`：列表里的船队名条（06 卷）。
- 其余四条只有标记（`[AFE5]`／`[6F65]`／`[DB7D]`／`[9537]`），没有界面归属记录。

处置：用户 2026-11-21 拍板「姓名之间不插符号，就用空格，省事，问就是口味」（日语同）——
八条全部写 `%1 %2`，与英／法／德一致。实机触发点是标题条「总督 易卜拉欣 加西亚」：
`0x183f926a` 的 `%1` 走的就是这一族，屏上名与姓之间只剩空白，用户确认这样就行。
四条归属未定的（`[AFE5]`／`[6F65]`／`[DB7D]`／`[9537]`）也因此不再需要辨认——
即使拼的不是姓名，空格版也不会错（数值对 `5 0,0` 同样成立）。

## 记错一个标记：`6EE3` 其实是 `6EF3`（2026-11-15）

船长窗那屏，船名牌「圣玛丽亚」后面那个标记，我先前读成 `[6EE3]`：按 3548 条重算
`mark_map` 找不到任何一条标 6EE3，在 zh-debug 包里逐行搜也是零命中。

用户对屏确认：那其实是 **`[6EF3]`**，也就是 `0xd68b6ef3`
（`<gs:TEXTFLUSS_KEINEHOEHE><g:INTEXT_KAPITAEN_RANG_0_800x600.screen>`，纯图形键，见 06 卷）。

- 结论：这条图形键在同一屏出现两次——一次在船长名「弗兰科・桑切斯」后面，一次在船名牌船名后面；
  不是两条键，也没有「对不上键的标记」这回事。
- 教训：屏上 4 位小字标记里 `E`／`F` 最容易互读。凡重算找不到的标记，先把**相邻十六进制字符**
  逐个替换再查一遍（`E`↔`F`、`8`↔`B`、`0`↔`D`、`1`↔`7`、`5`↔`6`），命中就收；仍无命中才当疑案。
- 现状：3548 条的标记与实机屏上标记已一一对上，没有遗留的对不上键的标记。
