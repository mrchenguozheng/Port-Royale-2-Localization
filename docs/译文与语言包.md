# 译文与语言包

只有**一份**手改文本：`src\translations\<语言>.toml`。
引擎要的排版（标点全角化、按词补空格）是**构建期**从这份译文现算出来的，
产物落在 `build\preview\engine_text\<语言>.toml`：

```
src/translations/zh.toml
        │  src/tools/text/engine_text.py（排版规则）
        ▼
build/preview/engine_text/zh.toml
        │  src/tools/pack/compile_pack.py（占位符校验）
        ▼
build/runtime/PR2Localization/packs/zh.txt
```

改译文请改 `src\translations\`；`build\` 下的东西每次编译都会重新生成，
删掉也不影响构建。直接编辑 `build\runtime\PR2Localization\packs\*.txt` 下次编译会被覆盖。

---

> **补空格为什么放在构建期**：按词插空格只是为了让引擎能在词边界换行，
> 是「同一份译文、不同投放形态」的差别。把它留在仓库里就等于同一段文字
> maintain 两份，手改一轮之后两边必然漂移。
> 早期版本曾分「初版（干净文本）」和「工作文本（补完空格的文本）」两层，
> 现在合并成 **一层译文 + 构建产物**：初版对应今天的 `translations/`，
> 工作文本对应今天的 `build/preview/engine_text/`。
>
> `translations/zh.toml` 里的中文是**不带补空格**的干净文本
> （汉字之间、标点两侧、占位符两侧都不留空格），破折号与 `<o:…>` 这类
> 原文自带的间距保留。它最早是 2026-10-21 从当时的成品文本里去掉补空格
> 还原出来的，还原后重新跑规则得到的成品与部署版本逐字节一致，
> 所以可以当文本源使用。
> 它不是「当年逐条手写的第一版」——那一版没有单独留档；
> 发现某处空格是原文本来就该有的，直接改 `src/translations/zh.toml`。

## 编辑 → 构建

- `src/translations/<语言>.toml`：唯一手改层，改这里才入库；
- 构建（`apply_patch`）先在内存里套一遍排版规则，再编译语言包，
  同时把引擎文本写到 `build/preview/engine_text/<语言>.toml`（给人看，可以删）；
- 想单独看某语言的排版结果：`python src\tools\text\engine_text.py --lang zh`；
- 旧的人工审核流程（`zh_review.py`、审核标记、页面横幅、已审勾选）已全部移除。

## 规则按语言分开：三段式接口

标点/空格规则不再堆在 `normalize_text.py` 里，也不再用「一个 `normalize()` 兼职所有事」。
每种语言声明一份 `LangSpec`，由三个部件组成（实现见 `lang_rules/spec.py`）：

| 部件 | 职责 | 中文 | 日文 | 法文 |
|---|---|---|---|---|
| `Punctuation` | 纯函数，只改标点：全角化、标点后空格、占位符两侧、`<n>` 去空格 | `zh.normalize` | `ja.normalize_punct` | 无（法语不加工，也不引入 U+00A0） |
| `Segmenter` | 分词器。`prepare(texts)` 批量准备（中文一次把片段交出去），`tag(text)` 给词性（日语判助词） | spaCy → 机械兜底 | janome → fugashi → 无 | 无（`NullSegmenter`） |
| `Spacing` | 补空格策略，声明式：`mode=none / group / particle` | `group`，每组 ≤ 10 字 | `particle`，助词后一格 | `none`（词间本来有空格） |

```
src/tools/text/
├─ lang_rules/
│  ├─ __init__.py  REGISTRY + get() + get_spec()（没登记的语言返回「原样透传」）
│  ├─ spec.py      Punctuation / Segmenter / Spacing / LangSpec + 执行器 build_texts()
│  ├─ base.py      共用机制：标点后空格、占位符两侧、<n> 去空格
│  ├─ zh.py        中文：标点表 + ZhSegmenter + ZhGroupSpacing（spec()）
│  ├─ ja.py        日文：标点表 + JaSegmenter + JaParticleSpacing（spec()）
│  ├─ fr.py        法文：显式透传（不补空格、不引入 NBSP，由 text_lint 守住）
│  └─ de/es/ru/ko.py  显式不处理：spec() 透传 + SKIP 常量写明理由
├─ zh_space.py     中文分词器封装 + 按词成组（被 Spacing mode=group 调用）
└─ zh_pipeline.py  中文「分词前」：连词、人名、数字/破折号/<n><n> 空格
```

- `engine_text.build()` 只认 spec：`lang_rules.get_spec(lang)` → 三段依次执行，
  **没有** `if lang == "zh" / elif "ja" / else` 的分派；
- `normalize_text.py` 只剩 CLI，只改标点（`Punctuation.normalize` 那一段）；
- 加一种语言：在 `lang_rules/` 放 `<代码>.py`，提供 `LANG / PUNCT / ASCII / CJK_RX / normalize()`，
  再加一个 `spec()` 声明三件套，登记到 `REGISTRY` 即可；`engine_text.py`、`apply_*_rules.py` 不用改。
  词间本来就有空格的语言写 `spacing=spec.NoSpacing()`，就是原来的「原样返回」；
- **不需要加工的语言也要建模块并登记**（`de`/`es`/`ru`/`ko`），文件头与 `SKIP` 常量
  写明「为什么不处理」，`test_skip_languages_are_declared` 守住这条；
- 没有专用规则的语言仍可用 `--force` 套中文规则；
- `・`(U+30FB) 和 `ー`(U+30FC) 虽然落在假名区，但**不当作正文**，不会被拆开
  （否则 `%2・%3`、`迭戈・莫扎雷拉` 会出空格）；
- **不做从右往左书写的语言**：没有游戏源代码，绘制方向改不了，
  `Spacing` 只有 `none / group / particle` 三种模式，没有方向字段。

## 目录结构

```
src/translations/
├─ zh.toml                中文译文（唯一手改层，不带补空格）
└─ ja.toml                日语译文（唯一手改层，不带补空格）
src/data/
└─ placeholder_roles/     占位符语义规则（人工维护，不是生成物）
src/orig/
├─ en.gog_1.1.2.3.toml    英文原文，基准（id 顺序以它为准）
├─ fr.gog_1.1.2.42.toml   法文原文
└─ zh.gog_1.1.2.3.toml    中文文本的历史留档（最早那版成品表）
```

`src/orig/` 里的 `en` / `fr` 是**只读参考原文**，本身不生成语言包，
`compile_pack --lang en` 返回退出码 2。它们留在语言列表里供对照。

法语的语言包来自 `src/translations/fr.toml`：键位对齐英文本（`en.gog_1.1.2.3`），
值优先取 `src/orig/fr.gog_1.1.2.42.toml` 的法语原文（3548 条里 3279 条逐字相同），
其余按英文补齐或修订。所以 `fr` 既是被对照的原文，也是可出包的语言。

每条一行，键就是 hash：

```toml
"0xd2d0a572" = "萧条"
```

键必须加双引号（裸键不能数字开头）。**不能用 `[["0x…"]]` 数组表** ——
它拦不住重复键。

## 编译语言包

```powershell
.\build.ps1 -Target Packs -Lang zh
```

低层脚本等价于直接跑 `compile_pack.py`：

```powershell
.\src\build_translation.ps1 -Lang zh
```

它把 `src\locale.ini` 复制进 `build\runtime\PR2Localization\packs\`，但只在文件缺失时写：
活动 `locale.ini` 不存在才建，`locale.default.ini` 不存在才作为发行默认建；已有活动文件不覆盖。
DLL 优先读活动文件，缺失时才读默认文件，两者都没有才用内置 `zh`。

编出 0 条时会**报错退出码 1 并且不写文件** —— 一个 0 条的语言包装进游戏
等于没汉化，而调用方只看「文件在不在」，空文件比报错更难查。

## 两版键集与出包取值

一次编译出两份包，行数与**本版原文**逐条对得上：主包 `en.gog_1.1.2.3`（3548 条），
变体 `fr.gog_1.1.2.42`（3571 条，写到 `build\variants\<版本>\`）。两版键集不同：
共有 3529，只英文版有 19，只法文版有 42，并集 3590。译文只有一套
（`src\translations\<语言>.toml`，3548 条），法文版独有的 42 条不为它们建行 ——
那 42 条在法文原文里全是 `+++EMPTY+++`，编译时从原文表复制该值，不是漏译。

取哪条值，**按本版原文判**，不看别版：

| 本版原文 | 出包写的值 |
|---|---|
| 正文（有占位符/标签的句子） | 译文；缺译报错 |
| `IDM_CONTEST_01_2004_*` 这类开发残留标识 | **原文标识原样**，译文不覆盖 |
| `+++EMPTY+++` | 原样写 `+++EMPTY+++`，哪怕译文层写了正文 |

第三条的来历：那 15 个竞赛任务键在英文版是标识串、在法文版根本不存在，正文只在
`de.retail-1.0.0`（零售版，不是出包版本）。英文/法文两版里它们是占位，所以包里也
保持占位 —— 这一版本来就不该多出一段界面文本。**也不照零售版补写正文**：零售版的
任务书不属这两个版本，译文层把 15 条一律回退成标识串，七种语言一致。要出零售版的
正文，得另加一份 `de.retail-1.0.0` 的基线，并让那一版的原文自己带着正文。

判据是 `compile_pack._is_resource_id()`：全大写带下划线才算资源标识。只按
`validate.is_identifier` 会把法文版 `0x274e9455` 的 `ATTENTION`（9 个字母的界面词）
也当标识，那一版包里就会把它原样写出、不走译文。

编译后每份会报「条目 N 条，其中占位未翻译 p、原文空占位 e、原文即标识原样 i」，
`zh` 主包是 3548（p=0，e=2，i=15），法文变体 3571（p=0，e=43，i=0）。

**发行包出的是并集**：`compile_pack.py --union` 把两份基线合成一份（`zh` 3590 条，
空占位 44、标识原样 15），写在 `packs\<语言>.txt`。GOG 由启动器
`PR2LocalizationGUI.exe` / `PR2Localization.exe` 远程注入 `PR2LocalizationCore.dll`，
Steam 由 `PR2HostMount.ps1` 替换宿主 `Ascaron.Logging-2.6.dll`（代理再加载同一个
主逻辑 DLL），两条注入路径读的是同一份 `packs\<语言>.txt`，所以两个 zip 里放同一份
`zh.txt`，装哪种版本都能用。多出来的键对另一版只是
查不到，不产生界面差异。默认模式（逐版两份）仍保留，供版本差对照与诊断，
产物在 `build\runtime\...\packs\` 与 `build\variants\<版本>\`。

## 语言包格式

编译产物**没有任何说明头**，第一个字节就是第一条数据：

```
0x1007ADD4 = 剧本顺利完成
0x100AFA32 = %1，<n>我们的教堂需要持续修缮，……
```

| 记号 | 含义 |
|---|---|
| `0xHASH = 文本` | 一条一个 hash 一行，hash 大写 |
| `<n>` | 引擎的换行标签 |
| `<o:0x…>…</o>` | 着色标记，冒号后是 ARGB 颜色 |
| `<f:fonts\…>` | 内联指定字体 |
| `%1`、`@D$EndDate$` | 占位符，个数与种类必须和原文一致 |
| `\|` | **旧写法，已废弃**：不再自动转成 `<n>`；译文里出现裸 `\|` 会报错。换行只写 `<n>` |

解析器会跳过 `#` 和 `;` 开头的行，所以手写注释不会被当成数据 ——
但**别依赖这个**：语言包是编译产物，下次编译就没了。要写说明写在这里。

## 排版规则（实测）

- **引擎按空格分词。** 中文天然不用空格分界，整串汉字连同标点会被当成
  一个超宽单词，超宽的整行**直接丢弃 = 完全不显示**，不是截断。
  每个界面控件能放多宽都不一样，工具**不估算宽度**，只能逐个界面实测。
- 标签（`<n>`、`<o:0x…>`、`<f:fonts\…>`）**原样保留**，不要删。
- 占位符一个都不能少，也**不要新增** `<n>` —— 换行只放在原文已有
  `<n>` 的位置（与英文/法文原文的分段一一对应）。

## 空格约定（中文 / 日文这类不用空格分词的语言）

这一节是**游戏引擎渲染文字的要求**，不是排版偏好：引擎按空格切词，
词太长就整行丢弃；占位符要能被单独识别，也必须在两侧隔开。
所以凡是「词与词之间本来不写空格」的语言，译文都要按下面的规则补半角空格。

**触发条件是两个**：标点是**全角**的，而且词与词之间**本来不写空格**。
中文、日文两条都满足，所以要按下面的规则补空格。

**韩文默认不触发**：韩语有 띄어쓰기（分写法），词间本来就写空格，
分词方式和英文一样；标点也用**半角 ASCII**（`.` `,` `?` `!` `:`），不是全角。
所以韩文不需要给标点补空格，保留原有词间空格即可。参考：
[Spaces and full width punctuation in Korean（W3C 讨论）](https://lists.w3.org/Archives/Public/www-archive/2020Sep/0002.html)、
[Word Segmentation in Korean (Stanford)](https://nlp.stanford.edu/fsnlp/korean.html)。

**但如果某语言用了全角标点**（包括韩文的旧式全角写法，或以后出现的新语言），
就按同一套规则处理 —— 规则看的是「全角标点」而不是国籍。

**标点**

- 单个标点（`，。、；：！？…・` 等）后面补 **一个**半角空格；
- 成对标点（`「」『』“”《》【】（）` 等）在**外侧**各补一个：开口标点前、
  收口标点后（`日志的 「成就」 里`，不是 `日志的「 成就 」里`）；
- 相邻标点之间只留 **一个**空格，标点串要贴合（`《航海条例》。` 不会变成
  `《航海条例》 。`）；
- **整段末尾不加空格**，段首也不留；
- 间隔号 `·`（人名 Janet · Smith 那种）**不参与**规则，保持贴合。

日文用自己的一套标点：单标点 `、。！？…・：；～—`，成对 `「」『』（）［］【】〈〉〔〕`。

**占位符**

- `%1`、`%10`、`%02u`、`%s` 与 `@X$变量$`（如 `@T$Town$`、`@D$EndDate$`）
  只要一侧紧挨着中文/日文字符或标点，那一侧就补一个半角空格：
  `可在 %3 建造`、`赶往 @T$TOWN$ ，`；
- 多个空格会合并成一个，不会出现连续空格。

**日语助词（可选）**

日语句子中间的助词后面也可以补一个半角空格（`市场に 来てくれれば`），
同样是给引擎切词用。规则是保守的，只处理「汉字/片假名 + 助词 + 汉字/片假名」：

- 助词表：`から まで より など ほど ばかり だけ しか こそ さえ でも って ので のに けど`，
  以及单字 `は が を に で と も へ や か ね よ`（**不含「の」**：`木材の需要` 这种
  领格切开会显得太碎）；
- 助词后面必须紧跟汉字/片假名/开括号才补空格，**后面是平假名一律跳过**
  （避免把「について」「として」「ません」这类词尾切开）；
- 后面紧跟标点或句尾时不动，免得出现「船か 。」这种标点前空格。

判定方式（自动选择）：

1. 装了 **Janome** 或 **fugashi** 就用形态素分析，只给「名词/代词/数词 + 助词」补空格，
   并跳过 `について` `として` `によって` `という` 这类固定搭配；
2. 两个都没有时退回正则（汉字/片假名 + 助词 + 汉字/片假名）。

开关：助词空格属于构建期的补空格策略（`Spacing(mode="particle")`），
用 `python src\tools\text\engine_text.py --lang ja` 生成即可；
`normalize_text.py --particles` 已移除（它只改标点，不往译文层写排版空格）。

**其它**

- `<n>` 换行标签两侧**不留空格**（`…。 <n>下一段` 会整理成 `…。<n>下一段`）；
- 这些规则由译文处理脚本批量执行（`<n>` 规范化、标点空格、占位符空格），
  新增语言时按同一套约定处理即可。旧 `|` 换行不再兜底，出现会被校验拦下。

## 敬语体系与「过度礼貌」

有敬语体系的语言，翻译时最容易犯的错不是译错，而是**把语气抬高**。
这一节记录问题、判定标准和目前的处理约定。

**哪些语言有敬语体系**

| 语言 | 体系 | 表现 |
|---|---|---|
| 日语 | 尊敬語・謙譲語・丁寧語・美化語 | `いらっしゃる` / `差し上げる` / `です・ます` / `お〜` |
| 韩语 | 높임법（敬语法） | `하십시오체` / `해요체` / `반말`，以及 `드리다`、`모시다` 等谦让动词 |
| 汉语 | 没有语法敬语，但有敬辞 | `您`、`请`、`贵`、`光临`、`惠顾`、`敬告` |
| 英语 / 法语 / 德语 | **没有**敬语体系 | 只有人称礼貌：法 `vous`/`tu`、德 `Sie`/`du` |

**原文到底多礼貌**

本作原文是德语（`Sie`），英译用中性 `you` + 祈使句，法译一律 `vous`。
`vous` / `Sie` 是**人称上的礼貌**，不是敬语层次——它没有「谦让」这一维。
所以 `you` / `vous` 的等价物就是日语的**です・ます**，这一点不需要改动。

**过度礼貌是怎么产生的**

- 把「我给你」译成 `差し上げます`（谦让语把玩家抬高了一档，原文只是 `I will give you` / `je vous offre`）；
- 把「你会收到」译成 `お受け取りになります`（原文 `you will receive` 是平陈述）；
- 叙述句、系统通报也写成敬体，或对玩家使用 `お持ちです`、`お越しください`；
- 自行添加原文没有的收尾修饰，例如「わが国も深く感謝しています」；
- 反向错误同样存在：海盗、醉汉的台词本来粗，若照 `vous` 抬成敬体就失真。

**约定**

1. **NPC 对玩家说话**（总督、商人、财政官、信件）→ です・ます，
   **不加谦让语**，除非原文本身有明确自谦（本作没有这种情况）；
2. **海盗、醉汉、粗人** → 常体（`だ`・`ぞ`・`な`），不要因为法文用 `vous` 就跟着抬；
3. **事件通报、界面提示、系统祝贺** → 中性语气或です・ます，但**不对玩家使用敬称**；
   通报用第三人称过去时；
4. **不新增**原文没有的敬语修饰、感谢语、客套句；

## 波兰语：润色口径

波兰语是屈折语，零售版本身是波兰人写的，不是机翻：2904 条里直译腔标记很少
（被动 `zostać` 121 行 3%、`który` 系 290 行 8%、`w celu` 3 行、`posiada` 17 行），
所以这一层做的是**一致性 + 局部自然度**，不是重写。

**语体**

玩家一律 `ty`：全库 `ty` 系 1143 处、`Pan` 系 1 处（那一处是 NPC 之间互称，保留）。
不要因为德语原文是 `Sie`、法语是 `vous` 就把波兰语抬成 `Pan`。

**术语锁定**

| 英文 | 波兰语 | 说明 |
|---|---|---|
| buccaneer | `pirat` | 58 条实体行里 55 条本来就是 `pirat`；`korsarz` / `bukanier` 只在**源文自己并列列举**处保留（`0xd4cd0fb4` 的词源列举、`0xf52fee2f` 的宣传语） |

`src/data/terms/pl.toml` 的 `en_buccaneer = pirat` 是**人工定值**：统计只到 56/64（91%），
按 0.95 门槛进不了表，但实体行的一致性是人工数过一遍的。

**排版**

- 引号一律 `„…”`。混进来的 `(„Imię Boże“)`、`„…"` 这类半角收尾已改；
  键盘字符测试行 `0x11f0398f` 原样不动。
- 句点、逗号前不留空格 —— 英文原串带尾随空格时最容易漏（`@S$ShipType$ .` → `@S$ShipType$.`）。
- `<n><n>` 断段后的第一句大写；`%1`、`@T$Town$`、`<ts:20>` 打头的段不算。
- 鼠标一律 `myszy`，不写口语小称 `myszki`（19 行统一）。

**标签压平**

英文名词堆叠直译成波兰语会变长，短标签压成词组：

| 原 | 改 |
|---|---|
| `Handel przy udziale kapitana`（Captain trading） | `Handel kapitana` |
| `Wskazówki dotyczące handlu`（Trading tips） | `Wskazówki handlowe` |
| `Szybkie przewinięcie do przodu`（Fast Forward） | `Przewijanie do przodu` |

**刻意保留的写法**

`w mieście @T$Town$`、`między miastami @T$TOWN$ a @T$Town$` 这类同位语是零售版为了
**不处理城市名变格**做的选择：变量里是主格地名，套进 `w` / `między` 需要工具格或属格，
硬改变格反而会错。这类不动。

**这一层没做的**

- 长文（可见 >255 字的 266 条）只修了错字与标点（`rzymiański` → `rzymski`、`p.n.e..` → `p.n.e.`），
  逐段按「不改事实、只改语序与连接」重写还没做；

## 校验与进度

```
python src\tools\translate.py status                 # 全语言进度
python src\tools\translate.py status --lang ko       # 单语言
python src\tools\translate.py dump --lang ko --band long --limit 40 --out build\ko_b9_in.txt
python src\tools\translate.py dump --lang ko --band 24 --by-group       # 每组一条代表句
python src\tools\translate.py dump --lang ko --band all --limit 40      # 默认按结构风险分层
python src\tools\translate.py dump --lang ko --ref zh,ja --limit 40     # 附参考译文列
python src\tools\translate.py dump --lang ko --order table --band long  # 回表序（查旧账用）
python src\tools\translate.py dump --lang ko --ids 0x070c60f9,0x250c7a12  # 手选一族单独成批
python src\tools\translate.py near --lang ko --min 0.93                 # 近重复成对条目
python src\tools\translate.py apply --lang ko --map build\ko_b6_map.json
python src\tools\translate.py apply --lang ko --map build\x.json --ids 0x070c60f9  # 只落一批
python src\tools\translate.py gaps --lang ko         # 源缺失自查
python src\tools\translate.py terms --lang ko        # 术语落词全量自查（长文也算）
python src\tools\translate.py overrides              # 英文微调层自查
```

`dump` 导出下一批待译清单：`id / 可见字数 / 英文原文`（换行写作 `\n`），
`--band` 取 `short`(≤12) / `24` / `40` / `80` / `long`(81+) / `all`，
`--limit 0` 表示不限。行末出现 `dup:N` 的，说明这几条共用同一句英文 ——
按源串作键只能写进一条，需要不同译法时改用以 id 作键 `{"0x...": "译文"}`。
以前这段是每批手写的 here-string，条件还漂过（`>80` 与 `≥81`）。
`--order` 默认 `risk`：先按**结构风险**分层 —— 既无占位符也无标签的最先
（抄不错）、其次只有占位符、带 `<…>` 标签的最后（最容易抄错），同层内按字数。
`--order short` 按可见字数从短到长（配 `--band all` 用，短档就不会被 `>80`
那一档一批批压到后面），`long` 从长到短，`table` 回表序（查旧账）。
韩语剩下 291 条全落在 `>80`，纯字数排序已经没有区分度：实测 47 条既无占位符
也无标签、146 条带标签，按风险分层才知道先动哪一批。
`--ref zh,ja` 在英文原文后面追加参考列（`zh=…`、`ja=…`）：待译的 291 条在其余
六语里 **291/291 都已译**，术语与句式照现成译文最省事，也最不容易漂。
`--ids` 给一串 id 就只导这几条，**无视 `--band` 与 `--limit`**：同模板换词的
一族（桶模板五条、四国公告六条）按字数散在整个长文队列里，一轮只碰上一两条，
靠这个单独成批才收拾得干净；表头会写「# 手选批次：N 条」。
清单第二行是「# 全队列 ≤12:1  13–24:1 …」，
各档还剩多少一眼可见 —— 只报当前档时，剩下的档排在哪里是看不见的。

「已译 / 待译」的判据按语言写在 `lang_rules\<代码>.py` 的 `SCRIPT` 里：
出现**目标文字**才算译（zh 汉字、ja 假名、ko 谚文、ru 西里尔字母）。
fr / de / es 用拉丁字母，没有目标文字可认，按「与英文原文不同」判。
日文另有一条：界面标签常只写汉字不带假名（`資産`、`倉庫`、`不明`、`容量別`），
只认假名会把它们全判成未译 —— 换算时 ja 待译 560 条里有 530 条就是这么来的。
所以 ja 的汉字也算日文，但要求既不等于英文原串、也不等于同一条的中文译文；
整句（超过 12 字）与中文一模一样仍判待译，短标签（`人口`、`武器`）中日同形是正常的。
判之前先抹掉 `<n>` 一类引擎标签、`[town:Havana]` 一类键、`%1` 一类占位符 ——
它们本来就不该译，留着会把「保持原样是对的」误报成待译。
只有纯数字、纯符号条目算天然已译。所以「待译 N 条」是可以复算的数，
不是某个一次性脚本的临时口径。曾经还额外报一个「与英文逐字相同 N 条」，
后来删了 —— 没译的条目值本来就是英文原串，这个数恒等于待译条数；
按全表算又会大于待译数，两种口径写在同一行只会让人怀疑哪个错了。

判据假阴性是这套统计最容易出的一类错：值明显有文字、只是不是目标文字，
就会被算成没译，几百条看着像没干活（ja 那次 560 条里 530 条是汉字标签）。
所以 `status` 在待译数之后再报一行「其中 N 条『有文字但不是目标文字』」
并给前三个 id：先怀疑判据，再谈补译。值等于英文原串的不进这个数 —— 那是真没译。
fr / de / es 没有目标文字可认，不出这一行。

`apply` 落盘前的「必须是目标文字」用的就是 `is_translated` 同一份判据：
早先这两处各写一份（`apply` 里内联 `script.search(vis) or (lang=="ja" and CJK_RX…)`），
改一处忘了另一处，就会出现「`status` 说 0 条待译、`apply` 却说值不是目标文字」
这种自相矛盾的报错。

`apply` 把 `{英文原串: 译文}` 的 JSON 映射落进译文文件：按 strip 后的值查表、
首尾空白原样贴回。写盘前查七件事 —— 占位符与**英文基准**的个数一致
（原文两处 `@G$Goods$`、译文只留一处也要拦；比集合会放过它，界面上就少印
一个货物名）、**标签字面**与英文一致（`<n>` 少一个就是丢分段）、占位符后
不许接裸助词（`%1를` 要写成 `%1(을)를`）、
图形标签后同样不许接裸助词（`<g:…screen>를` 要写成 `<g:…screen>을(를)`）、
并列助词必须是规范次序（`%1과(와)` 写成 `%1와(과)`）、
韩语量词（缺量词或搭配错，规则与 `text_lint` 同一份）、
映射值必须是目标文字。不合格的条目**逐条列出**后跳过，合格的照常落盘
（以前是「任一条不合格整批不写」：530 条映射里夹着 2 条坏值，好条目也要陪着
重来一轮）；收尾行报「另有 N 条因不合格被跳过」，退出码非 0，改好重跑同一份映射即可
（已落盘的不会重写）。违规条目**全部列出**（以前只印前 5 条，一批七条同类问题
要跑三轮才改完）。

标签门是补上的：原先 `token_counts` 只数 `@x$…$` 与 `%N`，`<…>` 一律被抹掉再比，
所以 `<n>Hello <g:X.screen>` 与 `안녕 <g:X.screen>` 计数相同 —— 删掉 `<n>`、
把字体名写错一个字母，都可能静默落盘。现在整段 `<…>` 按**字面**比，打印缺了
哪些、多了哪些。唯一的折算：字体标签的 `…aaFH.res` 与 `…aaFHk.res` 视为同一枚
（`_FONT_K_RX`）—— 七种语言的译文统一换成窄体 `k` 版（各 65 条），不折掉这个
字母，65×7 条「正规替换」会全部报错，真正换错字体族（`ELGRECO_26x26` 写成
`Tiepolo_bold14`）反而淹在里面。折算后存量只剩中文 `0x39e9081a` 一条真错，
已修。`text_lint` 侧同一份判据报为 W（「标签与原文不一致」），七语现存 0 条。

`--ids` 给 `apply` 也开了：一个映射里混了两批（比如手抄时把下一批也写了进去）
可以按 id 只落第一批。否则两份改动落在同一次写盘里，git 那边就是一个 hunk，
提交信息也只能并成一条。

裸助词是**逐处**判的：一条译文里既有一处并列形 `@T$TOWN$이(가)`、又有一处
`@T$Town$으로`，后者照样拦 —— 以前「整条里出现过并列形就跳过整条」，
半对半错的条目两头都查不到（实机复现过，批次十四里两条就是这样漏的）。
打印的片段只给命中那一段（`@T$Town$으로`），不再甩整条译文。
量词检查借的是 `text_lint.ko_unit_checks`（规则只留一份），命中示例：

```
拒绝落盘：0 条 token 与原文不齐、0 条占位符／标签后接助词、1 条量词不对、
0 条标签与原文不一致、0 条并列助词次序反了、0 条映射值不是目标文字。
  量词   0xf64f1e5a  缺量词 ○선박（应带 척）
```

并列形的次序只有一套（`을(를)`、`은(는)`、`이(가)`、`와(과)`、`으로(로)`），
反写语义等价但全库不一致，属落盘前可机械纠正项：`PH_PAIR_BAD` 命中即拦，
`text_lint` 同一条判据报 W「并列助词次序」。`text_lint` 另有一条 W
「标签后接助词」，判据只扩到 `<g:…>` —— 渲染插图后的助词取前一占位符的收音，
与 `@x$…$` 同类；`<n>이 마을은…` 里的「이」是正文指示词，扩到 `<n>`/`<t>`
会刷 34 条误报（存量实测）。

助词被拦时，拒绝文案末尾附三条候选改法（量词后置 `…만큼을`、换句式、
写并列形），不再只报片段让人从头想 —— 批次十九至二十三累计 20 次拦截，
每次都是同三种改法。

自 `apply` 加上这道门起，存量译文里又翻出三条被并列形挡住的旧账（
`0xd7d22331` 的 `%2로`、`0xd9720473` 的 `@T$TargetTown$으로`、
`0xe3fa97ec` 的 `@T$DestTown$으로`），已统一改 `으로(로)`。
写完再对账一次：待译条数应当正好减少「本次写进去的、原本待译的」那么多，
不吻合就报出来（多半是同源串撞车，两条 id 只写进一条）。
再跑一次命中 0 条、`same` 条数等于映射条数，是幂等性的自证；
按 id 重放时值没变的也计 `same`，不算 `rewrite` —— 否则重放 40 条会报
「修正 40 条、已是当前值 0 条」，看着像整批都改过。
映射里既没按源串命中、值也不在文件里的键单独列进 `unused`，那才是真缺口。
已经译过的条目要改，用 id 作键（`{"0xe84c0655": "译文"}`），源串那时已经不在文件里了。

`gaps` 抓「源缺失」：英文原值本身就是令牌（`IDM_CONTEST_01_2004_LOG_01_HDR`），
译文里却是实文 —— 这类条目在英文表里没有可译内容，靠长度分档抽查碰不到。
只报告、不改写，也不进 `check.py` 的判定。

编辑器（`src\editor\`）走自己的 `/api/check` 与 `/api/save`，比这条命令更严：
标签轮廓（译文不得新增 `<n>` / `<o>` / `<f>` / `<c>` / `<t>`）、占位文本
（`0x<id> | <英文原文>` 形态）都在那里拦。

换行只能在原文已有 `<n>` 的位置换。自然要另起行时，
交给渲染器按宽度自动折行，不靠手工插 `<n>`。

## 有意不译清单

`src\data\keep_as_is\` 下两份文件：`_common.txt` 是七种语言共用的基线，`<语言>.txt`
只写本语言独有的条目（按键名、表头）。读的时候先读基线再读语言文件，同一个 id
两边都写了以语言文件为准。

七语共用的是**与语言无关、译了必错**的几类：职员表（36 个人名 + 公司名）、
`scenario00X - @I$Idx$` 场景存档名模板、`Autosave %02u` / `Quick Save` 两个存档名、
Miles Sound System 版权、`PR2-Contest-01-2004` 版本标识。这些原来七份文件各抄一遍
（44 条 × 7 = 308 行），现在只有一份 55 行。

清单内的条目不计入待译，`status` 会写
「共 3548 条：已译 3008 / 可译 3481（86.4%），待译 473 条（另 67 条有意不译，不计）」
—— 口径是 **已译 /（总数 − 有意不译）**，不是已译 / 总数。否则
`F1`–`F12`、`ESC`、`Page Up`、`Looted<t>%1<t>%2<t>%3<n>`、职员表这类东西永久占着
分母，比例永远到不了 100%，也分不清剩下的是「没干」还是「不该干」。

`apply` 对名单内条目放行「映射值写成英文」：平时写回英文会被判成抄错行，但名单内
条目的正确值本来就是英文 —— ja 把 36 个人名音译成片假名后就是靠这条改回去的。

把一条改成「不译」时**不要删 `src\translations\<语言>.toml` 里的行**：删一行会让
后面的条目全部错位，`translate.py` 读基准表时就报「条目数不一致，无法合并」。
正确做法是值退回英文原串、再去 keep 清单登记 id 与理由，于是 `status` 只是把它
从分母里拿掉。对齐检查现在会把缺的、多的各前 4 个 id 印出来并附这句改法 ——
报错只说「条数不对」等于让人自己去数 3500 行。

清单漏登记不会自己暴露：值等于英文原文却不在名单里的条目，会一直算「待译」。
`analysis\keep_audit.py`（`check.py` 里独立一步）逐语言对账三件事：

- 登记的 id 必须在基准表里存在（版本差删掉的键会在这里露出来）；
- 登记项不许出现目标文字 —— 出现了就是「该翻的却登记成不译」；
- 待译里**不含任何字母**的条目（纯符号/数字/空占位/资源标识）必须登记，
  这类按规则永远译不了，留着只会占分母。

含字母但值等于英文原文的（`Dummy`、人名、`F1` 这类按键名）只列进
`build\qa\keep_audit_<语言>.txt`，是漏译还是该登记由人定。zh 那 55 条
（`F1`–`F12`、`Dummy`×11、职员表、`Port Royale 2`、`scenario004 - @I$Idx$`、
两条 `+++EMPTY+++`）就是被它点出来后一次补登的；两条 `+++EMPTY+++` 同时挪进
`_common.txt`（七语共用），ko 原本把空占位译成 `+++비어 있음+++` 也改回字面量。

反向也查，三种理由判据不同：

- `key` / `label` / `id` / `credit` / `name`：正确译法就是英文原样，值一旦不等英文，`text_lint`
  报「名单内但已改动」W 级 —— `ESC` 变成「이스케이프」不是改进。
  `name` 是「原文就是本语言写法」的专名（城镇名、海盗与姓氏池）：西语版
  `Tampa` / `Nombre de Dios` / `Edward Teach` 照抄就对，改成别的写法反而是错。
- **基准侧没有正文**：英文基准这一条是 `IDM_CONTEST_01_2004_LOG_00_TEXT` 这样的
  开发残留标识，或是构建基准里的空占位 `+++EMPTY+++`。这类键的正文只存在于别的
  版本（`IDM_CONTEST_01_2004` 那 15 个竞赛任务键，德语零售版有整段任务书，GOG 英文
  版是标识串），「等于英文」这条判据没有基准可比，直接跳过。判据落在
  `text_lint.base_without_text()`（复用 `validate.is_identifier`），`apply` 侧同一条
  判断也跳过 token 与标签两道门，否则给这种键补正文必被「多了 `<n>`／多了占位符」拦。
  跳过的条目在报告里单列一行（「以基准版为占位／标识的名单条目 N 条」），
  不静默 —— 15 条全部进名单，七种语言的值都是标识串（原来照德语零售版补的
  正文已回退），出包主包里同样原样是标识，见上一节「两版键集与出包取值」。
- `save-name`：这条模板会变成 `.pr2` 存档文件名。PR2.exe 只导入 ANSI 版文件 API，
  非 ASCII 字节按 Latin-1 映射，写出去就是 `脙聴… 02.pr2` 这种乱码文件，点进去弹
  「存档无效」。所以它**不必等于英文，但必须是纯 ASCII** —— de `Autospeichern %02u`、
  es `Autoguardado %02u`、fr `Sauvegarde automatique %02u` 合法；ja/ru/zh/ko 必须回退成
  `Autosave %02u` / `Quick Save`。实机记录见 `docs/待定.md` §6。

同一句英文同时用于「菜单木牌」与「存档文件名」时（`0x391f78da` 与 `0xd0d692a5` 都是
`Quick Save`），两条可以合法地不同译，登记在 `src/data/allow_same_src_<语言>.txt`，
否则「同原文异译」检查会把它当成不一致。

加进去的门槛是**译了反而错**。`Capacity<n>%1%` 是界面标签，照常译，不进名单。

### 各语言名单规模为什么不一致（参照物不对称）

七种语言的「有意不译」不是同一个判法的结果，因为手上能拿来核对的参照物不一样。
这一栏不对称必须写清楚，否则看名单条数会以为某门语言偷懒：

| 语言 | 参照物 | 判法 | 本语言名单 |
|---|---|---|---|
| zh | 无（母语，直接译） | 按键名、职员表、存档名这类规则登记 | 53 |
| ja | 无日文零售版 | 同上；汉字标签另走判据 | 30 |
| ko | 无韩文零售版 | 同上 | 27 |
| ru | 俄文零售版 `ru.retail-1.0.0`（仅抽查） | 同上 | 42 |
| es | 官方西语零售版 `es.retail-1.0.0` | 逐条比：与英文逐字相同的登记 `same`/`name`，其余照零售版改 | 382 |
| de | 官方德语零售版 `de.retail-1.0.0` | 同上 | 466 |
| pl | 官方波兰语零售版 `pl.retail-1.0.0` | 同上（id 与英文基准 0 缺 0 多） | 577 |
| fr | 无（`fr.gog_1.1.2.42` 本身就是官方法语，是译文而非对照版） | 按「同形」判：照英文写法即正确的词才登记 `same` | 493 |

`_common.txt` 另 67 条七语共用，不在上表行内。

## 骨架分组与近重复

`dump --by-group` 把占位符/标签抹成 `§` 后当「骨架」，同骨架只出一条代表句，
行末 `grp:N` 列出同组 id。模板族（四国公告、七档城镇状态）照一版改词填空即可，
不用逐条各写一版。

`python src\tools\translate.py near --lang ko --min 0.93`
列出待译里相似度 ≥ 阈值的成对条目，并排打印 `difflib` 的差异片段。
两个用途：一是「只差一个词」的句子照着同一模板翻；二是原文自相矛盾时会自己
浮出来 —— 批次十一撞到的「替你夺城的国家也必须军力**虚弱**」对「必须军力**强大**」
（`0xf4b68a6b` vs `0xf651cc3f`）就属于这一类，现在靠 `near` 主动报，不靠译者碰巧读到。

## 术语落词

术语表 `src\data\terms\<语言>.toml` 里的英文词，在**短标签**（可见 ≤24 字）里出现时，
译文必须用指定译法，否则 `text_lint` 报 W 级「术语未用」。长句不查：叙述句里的
同一个词是行文的一部分，全族强求会报上百条噪音。

只在**对齐过**的语言上开：`src\data\terms\enforce_<语言>.txt` 一行一个键，
没这个文件就完全不查。例外（专名、问候语）登记在 `allow_<语言>.txt`。
ko 已开；es / ja 的术语表与实际用词还没统一（`Pirata` vs `pirata`、`バッカニア`
vs `海賊`），先不开，免得报出来没人处理。

屈折语不能按整串比：`Konwój` 在正文里是 `Konwoje` / `Konwoju`、`Pirat` 是
`Piraci` / `Piratów`，只认原形会把**译对了**的条目全报成漂移（pl 实测 633 条）。
`text_lint.term_hit` 对 `pl` / `ru` 改成按词干比对：取值里每个词的前 4 个折叠
字母各自作为词的开头出现即算落词（`Kryjówka` 认 `kryjówce`、`jakość życia`
认 `jakości życia`）。其余语言仍按整串。

`translate.py terms` 是这道检查的**全量版**：同一份规则，但不设 24 字上限、
只报告不判定（不进 `check.ps1`）。长文里术语漂掉是真事 —— ko 实测 25 条
（`en_business` 10、`en_quality_of_life` 3、`en_convoy` 3、`en_plague_of_rats` 2、
`en_warehouse` 2 …）。放进 lint 意味着立刻多出 25 条 W 而没人清，所以留在
自查命令里，按词排序、一次挑要改的。注意它只算**已译**条目：待译条目的值
还是英文，把英文词算成「未落词」会凭空多出 200 多条假命中。

pl 这轮是反过来的用法：术语表刚由 `terms_seed.py` 起草、按词干比对后一次报出
8 条（`hideout` 5 条写成 `schronienie`／`ustroniu`／`skrytkę`、`governor` 1 条
把「from the Governor of a nation」整句省掉、`warehouse` 1 条写成
「w swoim mieście」、`trade route` 1 条写 `Szlak handlowy` vs 锁定的
`Szlak kupiecki`），逐条改完再跑到 0 条 —— 这道检查从「空表空转」变成真能挑出活。


## 英文微调层

原版提取 `src\orig\en.gog_1.1.2.3.toml` **永不改动**，它是审计与 token 比对的基准。
确认原版写错的条目，写进 `src\overrides\en.toml`（`id = 修正后的整句`），
依据与复核清单记在 `src\overrides\en.md`。

- `translate.load_toml()` 读完原版后套这一层，得到**语义基准**：出 english 包、
  各语言参照都走这一版，游戏里显示的就是微调后的句子。
- **占位符与标签仍以原版为准**：`text_lint` 直接读原版文件比 token，微调层改坏
  `%1` / `@n$…$` 不会被它掩盖。
- `python src\tools\translate.py overrides` 守两道：id 必须存在于原版、token 集合
  与原版完全一致，白改（与原版无差别）也报。有问题退出码 1。
- 改过英文的 id，七种语言都要按新句复核。当前一条：`0xf4b68a6b`（`weak`→`strong`），
  ko / ja / es 已改，zh 本来就写「强大」，ru / de / fr 本来就写「stark / forte / сильным」。

门槛：只收**原版自相矛盾或与玩法不符**，且能拿同族文本互证。不做文风润色 ——
否则半年后没人说得清为什么和原版不一样。

## 加一种语言

完整流程（分工、字体、元数据、部署、验收、出包）见[新语言](新语言.md)。这里只列数据层：

1. `src/translations/<代码>.toml`：用 `python src\tools\pack\new_lang.py --new-lang <代码> --from en` 创建；
   条目数与顺序必须和基准表一致，`<代码>` 就是语言包文件名和 `locale.ini` 的 `language=`。
2. `src/packs/<代码>.toml`：`alias`、`min_runtime`。
3. 启动器界面不需要新增 `ui/<代码>.ini`：固定默认 `ui.default.ini`，用户可放 `ui.ini` 覆盖。

语言代码没有形式要求，`zh` / `zh-CN` / `de` / `pt-BR` 都行，只要和 toml 文件名一致。
构建与部署见[构建与安装](构建与安装.md)。

非拉丁文字的语言（谚文、西里尔、假名……）另外要在 `src\tools\text\lang_rules\<代码>.py`
里写一份 `SCRIPT` 正则：`translate.py status` 靠它判「这条到底译没译」。
拉丁语言的 `<代码>.py`（如 `nl.py`）只声明透传 spec，不写 `SCRIPT`。

上面三条只是数据层最少的一步。真加一门语言时，`check.py` 会逼你补齐下面这些
——每一项都是它自己报出来才知道的，所以记在这里（pl 就是这么踩过来的）：

| 位置 | 谁逼你改 | 不改会怎样 |
|---|---|---|
| `src\tools\text\lang_rules\__init__.py` 的 `REGISTRY` | 不登记就取不到本语言模块 | `script_re` 返回 None —— 拉丁语言刚好等价，非拉丁语言整门判据失效 |
| `src\font-map.ini` 的 `[<代码>]` 四个逻辑名 | `config_check._check_font_maps` | 直接报「缺少 [xx] 字体映射」，配置检查失败 |
| `src\tools\README.md` 语言规则表加一行 | `tools_check`（脚本地图） | 报「没有出现在 README」，整条 check 失败 |
| `src\data\keep_as_is\<代码>.txt` | `keep_audit` 的「结构性不可译未登记」 | 纯符号/按键/存档名永远留在待译里，比例到不了 100% |
| `src\tools\analysis\line_run.py` 的 `SKIP` | 不写就只是「没有上限配置，跳过」 | 读的人分不清「拉丁语言不适用」还是「忘了配」 |
| `src\data\placeholder_roles\<代码>.toml` | `config_check` 只报警告 | 占位符之间要不要补连接符这件事没有落卷（拉丁语系写一句「普通空格、无连接符」即可） |

`check.py` 的语言清单取自 `src/translations/*.toml`，**新加的语言自动进检查**，
不用来这张表里登记；语言还没完工、暂时不想让 CI 红，就写进
`src/data/check_skip.txt`（`代码<TAB>理由`），理由会打在报告头上。

有参照版的语言（现在只有 es / de / pl 有完整零售版）把参照里的
「与英文逐字相同」那批直接登记进 `keep_as_is`，剩下的照零售版落盘即可。

上面这张表以外的部分都交给一条命令：

    python src\tools\pack\lang_add.py --lang pl --alias Polski ^
        --alphabet "ąćęłńóśźżĄĆĘŁŃÓŚŹŻ" --ref pl.retail-1.0.0

它做的是：复制英文基准 → 建 `packs` / `placeholder_roles` → 有参照版就按
「与英文逐字相同」生成 `keep_as_is`（分类判据与当年 pl 那批同一套）→ 建
`lang_rules/<代码>.py` 并登记 `REGISTRY` → 建 `font-map.ini` 的 `[<代码>]` →
补 `line_run` 的 `SKIP` → 补两处 README（脚本地图与语言完成度表）→
最后用 fontTools 实测原版四个字体缺不缺本语言字母，并给结论。
已存在的文件不覆盖；`--dry-run` 只看不改。

脚本不做的是**译文本身**：句子只有人能写，判错了没人能替你发现。

术语表 `src\data\terms\<代码>.toml` 也不用逐条手填，按键取证即可：

    python src\tools\analysis\terms_seed.py --lang pl            # 只看
    python src\tools\analysis\terms_seed.py --lang pl --write    # 落到 src/data/terms/pl.toml

两档取证：**整行标签**（英文整条就是该词，`Pirate` / `Trade route`）直接取值，
单数行优先于复数行；没有整行标签的按**全库共现**，要求词干簇覆盖 ≥0.95、
锚词与候选的相对位置吻合 ≥0.95、锚定条目里的密度至少是全库的 2.5 倍，
三个都达标才成值，否则只把候选和证据写进注释等人定。`--write` 默认不改已有值
（`--force` 才覆盖），`de_…` / `fr_…` 键英文侧没有可锚的词，一律留手工。

pl 实测 22 个键：整行标签档成值 11 个（`Narzędzia`、`Plaga szczurów`、`Celność`、
`Pirat`、`Gubernator`、`Magazyn`、`Konwój`、`Kapitan`、`Żeglarz`、`Kryjówka`、
`Szlak kupiecki`），共现档 2 个（`jakość życia` 11/11、`kolonia` 9/9）；
`business` / `buccaneer` / `market` 三项证据不足留空（`market` 的词频榜首是
`towaru`「货物」，位置吻合只有 84%，真正的译法 `rynek` 排第三）。

诗谜的**骨架**不用手抄：`answer`／`group`／`level`／`certainty`／`source`
都是谜题元数据，跟用哪种字无关，从已核过的语言（ko）搬过来即可，
只有 `clue=` 要按本语言谜面重写（`marks.py` 要求每项逐字出现在谜面里，
大小写也算，抄韩文 clue 必然对不上）。这条命令搬骨架、核对 clue、出映射表：

    python src\tools\analysis\riddle_marks.py --lang pl --from ko --dump
    python src\tools\analysis\riddle_marks.py --lang pl --from ko ^
        --clues build\pl_riddle_clues.json --out build\pl_riddle_map.json

`--dump` 先把 32 条代表谜面的正文列出来，照着它挑 clue；`--clues` 是
`{id: "词, 词"}` 的 JSON。有 clue 缺、词不在谜面、副本指向另一条副本时
拒绝出表并逐条点名。pl 这轮用它复现了同一份 48 条映射（0 条差异）。

副本还有一处必须点名的坑：零售版每条副本都自带完整谜面，写 `[riddle:copy=键]`
会让本条正文取代表那条的。所以搬运时如果**本条正文与代表不同**，脚本会逐条
列出「哪条会被谁覆盖」，默认继续出表、`--strict` 则拒绝。pl 这轮 16 条副本
全属此类（同一谜语的另一种写法），已确认统一，输出与手工版 0 差异。

照抄参照版之前先跑一遍健康检查，别等 `apply` 逐条拦下来才知道哪几条不能抄：

    python src\tools\analysis\ref_check.py --ref src\orig\pl.retail-1.0.0.toml

E 级（令牌不齐、标签个数不齐）就是 `apply` 会拦的那批，先修再抄；W 级是
疑似截断（正好停在 255 字符且收尾不完整、或比英文短到 0.75 以下），逐条看。
pl 这轮 3548 条里 E 7 条、W 2 条；参照版与英文逐字相同的那批只计数，不当坏数据。

## 占位符连接规则（按 hash，不做批量替换）

`%1 %2` 可能是「等级 + 全名」也可能是「名 + 姓」，批量替换必然有一边出错。
现在改成按 hash 记录规则：

```toml
# src/data/placeholder_roles/zh.toml
["0x338a357f"]
rules = [
  { pair = ["1", "2"], sep = " ", note = "等级 + 全名" },
]
```

**人名占位符的间隔号**：编年史里 `%1 %2 %3` 通常是「等级 / 名 / 姓」，
所以只写 `%1 %2・%3`（等级后空格，名与姓之间用 `・`）；
`%1 %2` 这种两段式若表示「等级 + 全名」，用空格，不能写成 `%1・%2`，
否则会出现「见习水手·巴尔塔萨·马尔伯夫」。

工具：`python src/tools/placeholder_roles.py`

- `--report --lang zh|ja`：扫描所有相邻 `%N %N`，导出 `docs/csv/analysis/占位符语义.<lang>.csv`
  （hash、当前连接符、推断建议、英文上下文），供人工判断；
- `--check`：按该语言已记录的规则校验，列出不符的连接符；
- `--fix`：**只**改有明确规则的条目，其余不动；
- 规则按语言分开：`placeholder_roles/zh.toml`、`placeholder_roles/ja.toml`，默认 `--lang zh`。

新增一条规则：在 CSV 里找到那对参数 → 在 toml 里加一行 → `--check` →（需要时）`--fix`
→ `python src/tools/text/engine_text.py --lang zh` 重新生成。

## 排版优先用空格，不改词句

游戏按空格断行，详情框高度固定。遇到「顶部被裁、只剩最后一行」这类显示问题，
处理方式是**在合适位置补少量空格**，让断行提前，而不是删字或缩短译文。

- 空格是排版手段，不改变语义；译文内容以文本源为准；
- 需要压缩行数时，优先在句读处、长词前补空格；
- 不要为了塞进框里而改写或删减译文。

## 译文层就是干净文本

`src/translations/<语言>.toml` 本身就是**不带排版空格**的干净译文，
补空格在构建期由 `engine_text.py` 现算，不进仓库。

`src/orig/` 里的 `zh.gog_1.1.2.3.toml` 是最早那版成品表的历史留档，
不再参与日常流程；`en` / `fr` 的原文仍是只读参考（`fr` 的译文在 `src/translations/fr.toml`）。

## 日语：译文 → 构建产物

```powershell
python src/tools/text/engine_text.py --lang ja          # 生成 build/preview/engine_text/ja.toml
python src/tools/text/engine_text.py --lang ja --check  # 只对比，不写文件
```

规则来自 `lang_rules/ja.py` 声明的 spec：标点（`Punctuation`）、形态素分词器
（`Segmenter`）、助词空格（`Spacing mode=particle`，装了 janome/fugashi 用形态素，
没装用正则兜底）。
产物写进 `build/preview/engine_text/ja.toml`，**不会**回写译文层。

## 占位符数量必须逐个一致

原文与译文数量不同的占位符由编译期校验拦下：`compile_pack --strict`
（含 `--lang` 全量编译）发现任何占位符多用或少用会拒绝出包，
并列出具体条目与数量（原文 N 个 / 译文 M 个）。

改完一条可以用 `quick.py` 先自检：

```powershell
python src\tools\pack\quick.py --lang zh --id 0x… --text "修正后的译文"
```

## 直接改文件

- 译文就是 `src/translations/<语言>.toml`，改完跑 `.\apply_patch.ps1` 或 `compile_pack.py`；
- `orig/` 只放只读参考原文；引擎文本与语言包一律由构建产生。

文本上不可分，一并归入清单项。这类短语没有 LT 能判的语法，单词拼错照旧由拼写层抓；
性数若真写错（`Feindlicher Stadt`）这一层看不到，记作已知盲区。

试过把本条原文喂进 `render()` 的种子，让同一条可复现、相邻条目取到不同城名，读数反而
172→184：城名池只有四个，`die München` 这类冠词与替身城名性别冲突的 `DE_AGREEMENT`
从 7 涨到 33，净亏。消连排要治的是「清单项不该送检」，不是「换个随机种子」。

**句首大写复核。** 三门 `UPPERCASE_SENTENCE_START` 共 106 条（de 33、es 39、fr 34），
只读探针把每条渲染后的上下文连同原文一起打出来，再按 id 取整条原文与
`en.gog_1.1.2.3.toml` 对照首字母。判据收紧成「原文首字符不是空格、整条 ≥25 字符、
含句末标点」，得 81 条候选，逐条读下来**只有 4 条是真错**，已整条替换落盘：

- es `0xd14f264d`：`¿deseas que organice` → `¿Deseas que organice`
- fr `0x0694a544`：`votre réputation en` → `Votre réputation en`
- fr `0x072a9579`：`je vous suis très` → `Je vous suis très`
- fr `0xd034f206`：`trouvez le coffre` → `Trouvez le coffre`

落盘用 `translate.py apply --ids`，map 的值是**整条新文本**，不是 old/new 对；按
`{id: [[old, new]]}` 写会直接报「映射的值不是字符串」。

判「不改」的三类，各有硬证据：一是 en 基准同样小写、条目在前一句后面续接——
`0xcca05df4~7`（en 为 `' and may now control...'`）、`and the harbor is...` 四连
（`0x133e8429`／`0x17abb14d`／`0x1d6d7bd9`／`0x36d535b4`，en 全是 `and the harbor...`）、
`the military presence in this town...`（`0x0cee08cc`／`0xde5bdde0`）；二是缩写点后
被当成段首（`Ciud. saqueadas/capturadas`、`Dir. administrativo Ascaron UK`、
`Stat. marchandises`）；三是纯标签与标记串（`normal`／`alto`／`max`／`tripulación máx.`／
`en 1 ciudad`、`<ts:0><ts:160>town view/sea battle<t>zoom level<n>in lists<t>scroll`）。

读数：es 221→218、fr 481→478，de 154→159（33 条 UPPERCASE 全是标签与续接，一条真错
都没有；159 比 154 多的是 `<n>` 条件化把折行从 UPPERCASE 挪进了 `DE_CASE`）。
两门的减量里有 1–2 条不来自这次改译，是探针新认出的专名写进替换表后下一轮不再命中。

**跨条复检怎么做的**：`REPEAT_RX`（`REPEATEDWORDS|WORD_REPEAT|PHRASE_REPETITION`）命中的
行，拿该条渲染文本单独 `tool.check()` 一次，单条也报同一条规则才算真命中，否则丢弃。
只复检这一类，de 命中约 200 条、去重后 150 条上下，多花几秒；es 这轮 0 丢弃、fr 0 丢弃
（两门的重复词命中单条都成立）。

真改的三类：

- `weiterhandeln` → `weiter handeln`（`0xc9500bee`）。主句里可分动词必须分开写；
  同在 `damit` 从句里的 `teilhatte` 反而是正确的，LT 建议分写是误报，不改。
- `erobern!!` → `erobern!`（`0xdfb549a5`），双感叹号。
- 数字与百分号／单位之间补空格 13 处（DIN 5008 要求 `5 %`、`30 m`）：

  `%1h %2m` → `%1 h %2 m`、`Kapazität<n>%1%` 等。

记口径不动的：`aneinandergekettet`（合法复合分词）、`mit Hilfe`／`in Frage`
（DIV 两写并存）、`dich`／`du` 小写（现代正字法）、`auf Arbeit`（北德口语）、
`warm zu halten`、`hierher führt`、`Ich erzähl`（口语省略 -e）、`kn`（节）、`max`、
`lacitos`、人名列表、词源引语（`vido`／`kangooroo`／`ganguru`／`batate`／`hamaka`／
`peirato`／`cabildos`／`xocoatl`）、Miles Sound System 版权段、`Tiepolo_*.res` 文件名。


### 参照层清洁（`analysis/ref_clean.py` → `en-clean` / `fr-clean` / `<语言>-clean`）

一切对照都从 en 与 fr 开始：en 是结构基准，fr 是同源的官方本地化。可这两份本身也有
缺陷，缺陷会被下游当规格抄走。四家零售（de/es/pl/ru）同理——它们既是参照，也能被
抄，先各出一份清洁版。

| 产物 | 是什么 | 拿它当什么 |
|---|---|---|
| `src\orig\en.gog_1.1.2.3.toml` | 原版基准 | 唯一权威，永不改动 |
| `src\orig\fr.gog_1.1.2.42.toml` | 官方法语 | 同上 |
| `src\orig\{de,es,pl,ru}.retail-1.0.0.toml` | 四家零售 | 同上 |
| `build\ref\clean\en-clean.toml` | en 的清洁版（派生） | 结构基准（`<n>`／`<t>`／令牌齐全版） |
| `build\ref\clean\fr-clean.toml` | fr 的清洁版（派生） | 与 en-clean 结构一致的官方译文 |
| `build\ref\clean\{de,es,pl,ru}-clean.toml` | 四家零售的清洁版（派生） | 落译文时的参照 |

```bash
python src\tools\analysis\ref_clean.py --ref en.gog_1.1.2.3 ^
    --patch src\data\qa\ref_patch\en.json --write
python src\tools\analysis\ref_clean.py --ref fr.gog_1.1.2.42 --base en-clean ^
    --patch src\data\qa\ref_patch\fr.json --write
python src\tools\analysis\ref_clean.py --ref de.retail-1.0.0 --base en-clean --add-only --align-idm --align-empty --align-foreign --write
```

三条命令的顺序不能倒：其余五份的结构基准都是 `en-clean`（不是 en），en-clean 先定
下来，后面才知道对齐到哪。es／pl／ru 与 de 同形状，各自带 `--patch
src\data\qa\ref_patch\<语言>.json`。

**`--align-foreign` 按语种退占位。** 零售包里混进来的整条外文（上面说的
`0xd34819b0` 那种德语正文）不该留在参照层：下游照抄会把外语搬进译文。判据在
`src/tools/text/lang_id.py` 的 `is_foreign()`——停用词评分、**对方至少要领先本语言
2 个命中**、`min_hits=3`；版权／许可声明白名单（`Copyright`／`RAD Game Tools`／
`Miles Sound System`／`©`／`All rights reserved`）直接放行，那条
`0xfc512ea5` 属于「各语言一律保留英文」的正当保留。只对 es／pl／ru 跑：fr-clean 的
`0xd3481945` 是零售旧译 `Remarque`，本来就是法语，不能退。

德语和西语／法语的虚词表有重叠（德语句首 `Es` 会撞西语 `es`），所以判据不能只看
绝对得分：`0xd3481944` 有 30 个词、判 de 命中 9 个，但 `es` 也白捡 1 分（`Es`），
早先「本语言 0 分才放宽」的写法把它漏掉了。反过来只看领先分差又会把
`Pedro de la Plesa`（4 词里 `de`／`la` 都得西语分）当西语，所以再加 `min_hits=3`。
两个条件同时卡住，实测三份各退 5 条、不多退一条。

**en 没有更高一层的基准**，所以它的结构缺口只能靠其他 retail 的多数票定：某条 5 个
语种里有 4 个都多一处 `<n>`，就认定 en 漏了。票数不足 3 的不动，只报。票数够了但
**切点**（那处 `<n>` 落在哪句末）机器猜不准，所以按票补数量这一步留给人工，写进
`src\data\qa\ref_patch\<语言>.json`（`{id: [[old, new], ...]}`，每对必须**唯一命中**，
否则整对不生效并报出来）。

**零售这一档要 `--add-only`**，比官方译文严三层：

1. **只补不删。** 德文文本更长、段落本来就比 en 多，ru 把某条压成一整段——按基准删
   `<n>` 会把整段挤成一行，比不修更糟。实测按默认口径跑 de 会删 13 行共 27 处换行，
   其中 `0xf562862e` 是「en 为空、只有 de 有正文」的长篇报名启事，删成一段直接毁掉。
2. **只补在句末。** 零售的句子与基准不是逐句对应，退到「分句处／词边界」的切点多半是
   错的：ru `0x1a444b3e` 会被插在 `"Страны"` 与 `хроники` 之间，把章节标题和正文劈开。
   严档句末不算冒号、引号、书名号（`STRICT_END_RX`），只认 `.!?…`。
3. **缺口超过 2 处就不补，只报。** 差一处两处还可能是段落边界丢了；差三处以上说明这
   条的段落划分本来就和基准不同，自动补是瞎猜。带参换行（`<n:25>`）一律不自动补——
   参数值是排版宽度，位置必须人给。
4. **别家只有 IDM 键名的行，正文退回键名（`--align-idm`）。** `IDM_CONTEST_01_2004_LOG_01_HDR`
   这类值是 mod 作者给「上市版没有这句」留的占位，不是给人看的文本。德语零售把这批
   2004 竞赛日志（15 条：`LOG_00`–`06` 的 HDR/TEXT 加 `POPUP_HDR`）自己译成了德语，
   en/fr/es/pl/ru 全是键名。参照里留正文，下游抄就会把德语搬进别的语言，所以先退回
   键名——15 条逐一（`0xc7537475`、`0xccd432a5`、`0xd10b5c36`、`0xdac343f7`、
   `0xdb66b4df`、`0xe47b2bb8`、`0xee331379`、`0xf7eafb3a`、`0xf93656ab`、`0xfcded04c`、
   `0x0204aa22`、`0x0b715286`、`0x0f3a5490`、`0x25940110`、`0x3426834a`）。
   `+++EMPTY+++` 不算这一类，走下面第 5 条的多数表决。
5. **`+++EMPTY+++` 按多数表决（`--align-empty`）。** 占位的意思是「上市版这句没有」，
   属版本事实、不属翻译，所以不该由单家零售独自判断。票只算「这条存在」的语言——
   缺键不是反对票（fr 比 en 多 42 条、en 也有 fr 没有的）：
   - `0xf562862e`：en/es/pl/ru 四个是占位、de 是 906 字报名启事（fr 无此键）→ 4 空
     : 0 文，de-clean 退成 `+++EMPTY+++`。
   - `0xd49a1310`：en/fr/de/es/ru 五个是占位，pl 是一个空格 → 5 空 : 0 文，pl-clean
     把空格规整成 `+++EMPTY+++`。
   - 反过来的情况（本参照是占位、过半语言有正文）**不动**，只报「要重译，别退」——
     占位换不成正文，那是重译工序。
   清完之后六份 clean 里「哪条是占位」完全一致：同一 id 只要有该条，要么全是占位、
   要么全有正文，0 处冲突。

- **疑似参照少分段**（es `0x010faa75`、`0x2efebfe6`、`0x084340c7`；ru `0xe1cdc367` 只有

- **疑似缺令牌**（de `0xca4930dc` 的 `@a$Amount$`／`@A$Amount$`；es／pl／ru 的 `%3`、`%1`、

机器补不了的这批，用途只有一个：**抄之前先看报告这一栏**，别整条照搬。

**校验工具（`src/tools/qa`）。** 五个脚本进版本库，产物仍落 `build/qa`（该目录不入库）：

| 脚本 | 用途 | 产物 |
|---|---|---|
| `ab_diff.py <lang> [--rev <commit>]` | 基线提交与工作树两份 `lang_check` 各跑一遍 `grammar()`，输出规则集合的 gone／new／delta | `build/qa/ab_diff_<lang>.txt` |
| `dump_hits.py <lang>` | 全量命中导出，首行写「提交／语言／送检／命中／规则数／渲染种子」 | `build/qa/<lang>_hits_all.txt` |
| `prefix_stat.py [lang…]` | 统计位置／国家占位的前一词与 20 字符前文，全量输出 | `build/qa/prefix_<lang>.txt` |
| `lang_mix.py` | 扫六份 clean 的串语言条目，三种判据分开标 | `build/qa/lang_mix.txt` |
| `ref_gap.py [lang…] [--no-view]` | 只取 `ref_check` 的 E 段，按令牌／`<n>`／长度比／句数分「疑似」几类，并把每条疑似的四段全文并排写出 | `build/qa/ref_gap.txt`、`build/qa/ref_gap_view.txt` |

`ab_diff` 是这一轮返工最多的那一步的固化：改替身池会让全局 `rng` 的消费序列整体
漂移，总命中数天然不可比，能判「有没有引入新规则」的只有规则集合差异。以前靠手工
`git checkout`＋跑两次 dump＋`git checkout` 回来，中途覆盖文件还丢过一次读数。
现在一条命令：`python -X utf8 src/tools/qa/ab_diff.py fr --rev 87ba9a2` → 352 对 316、
规则集合零变化、只有 `PREP_PAYS` 28→2 与 `ELISION` 11→1，两分钟内出结论。

`dump_hits` 的首行元数据是必须的：同名文件在不同提交下可能是「跨条丢弃前 405／105」
也可能是「之后 352／74」，没有这行只能靠猜。`prefix_stat` 的前文按「前一词」取，
不再按 10 字符硬截——旧版输出 `'ofesseur. '` 这种断词碎片，判定「介词 + 裸国名」
全靠猜。

**占位机制的跨语言共性（2026-11-21）。** 两件，一件是机制读错了，一件是原版没管语序。

先说 `@a$Amount$ @G$Goods$`：**不是**一个整体被替换，是两个独立命名占位，中间的连接字由译文自己写

### 零售参照导入（`analysis/retail_import.py`）

把官方零售版换进已有语言时，别整行覆盖。先弄清楚这门语言处于哪种状态：

| 状态 | 例子 | 该走的路 |
|---|---|---|
| 大片没译，现值仍等于英文 | pl 接入时（2737 行仍是英文） | `--only-empty`：只填没译的行 |
| 译过，但不如零售 | es（1477 行与零售不同，其中 1400 行是整句改写） | 默认口径：替换已译 |

```bash
python src\tools\analysis\retail_import.py --lang es --ref es.retail-1.0.0          # 只出报告
python src\tools\analysis\retail_import.py --lang es --ref es.retail-1.0.0 --repair  # 先修结构再校验
python src\tools\analysis\retail_import.py --lang pl --ref pl.retail-1.0.0 --only-empty --write
```

报告按原因分流（不译名单／参照没翻／诗谜与引用要先走另一道工序／标注对不上／参照不是本语言），
结构缺陷（令牌个数、标签个数）仍由 `apply` 拦下，不在这里重写一份判定。

**只差首尾空白不算改动**：零售版的行首偶尔带一个缩进空格、行尾带一个空格，现译没有（或反过来）。这种差异
没有语义，整行覆盖只是把已落盘的值改一遍空白，所以 `build` 判「与参照只差首尾空白（保留现值）」直接跳过。
es 实测这一条让候选从 166 条降到 105 条，剩下的差异都是真改动（带标注 6、只差 `¿¡` 2、其他 6）。

**换语言之前先看报告开头的「## 基准覆盖」**：基准多少条、零售对上多少条（其中多少条是空）、
缺多少、多多少。**缺口**是「基准有、零售没有」的行——零售文件里根本没有这一条，导入对它
们无能为力；但缺口不等于欠译，报告再把缺口按现值分三类：**不译名单**（按键名、表头、脚本
id、存档名，正确做法就是英文原样）、**已有译文**（现值不是英文了，缺的只是零售这个来源）、
**真待译**（现值仍等于英文，也不在不译名单——只有这类才真要动，补法就是按基准英文自己译，
同 id 在别的零售语言里有平行文本可校，但不能照抄语体）。**多出的行**是版本差异
（`fr.gog_1.1.2.42` 比基准多 42 条），参照时直接忽略。实测（基准 3548 条）：es／de／ru
全覆盖 3548/3548，pl 3548/3548 但有 1 条零售为空，fr 对上 3529（缺 19 条＝不译名单 17＋
已有译文 2、真待译 0，多 42 条）。

**承标注是这道工序真正的难点**：现译里有 `[town:Cartagena]`、`[term:en_tools]`
这类标注，零售文本是纯文本，一条都没有；整行覆盖会把标注层抹掉，而标注层是给
`text/marks.py` 消费的（地名按译名表展开、术语按术语表展开）。

标注的参数不是显示文本，是译名表的键（`[town:St. Augustine]` 在 es 里展开成
`San Agustín`），所以搬运规则是「按展开结果定位」：算出标注会显示的字符串，在零售
文本里找它。三种情况分开处理：

- **同一显示文本出现 n 次、标注也有 n 处**（零售也把「Port Royal」写了两遍）：按标注
  先后依次替换第 1、2…n 个出现。标注与显示文本是同一个词，换哪一处显示效果一样，
  只有「第几处」是确定的，所以这是安全的。
- **零售写法不同**：整段找不到时依次退一步——去掉西语冠词再认（零售写 `Habana`、
  译名表是 `La Habana`），再不成就用标注参数原文再认（零售整行留英文 `Turk Islands`）。
  两者都要求出现次数与标注处数相等。
- **零售承载不了**：出现次数少于标注处数（零售少写一处地名）、或整段不是同一段文字，
  整行放弃并报原因。位置猜错会把地名套到别的词上，比不导更糟。
`[riddle:…]` 与 `[ref:…]` 整行跳过：前者要重算 clue 并逐字核对（走 `riddle_marks`），
后者会牵出另一条文本。

es 实测：**32 条诗谜正文 + 16 条 `copy=` 复制行**（复制行的正文与组首行完全相同，只有
`copy=<id>`；「缺 answer」是正常形态，别当缺陷修），32 条的 `<n>`、令牌与 `answer/clue/level`
字段全部对齐基准，词典命中率也都在目标语言内。剩下 9 条承载不了的进 hold 名单（见下）。

es 实测与落盘（候选 1365 条，`apply` 落 1339 条、留 4 条不导；报告里另有 48 条诗谜、
3 条引用、18 条标注对不上）。

第一轮落盘之后又修了承标注与兜底，es 的实测一路是：

| 参照 | 候选 | `apply` 可落 | 拦 |
|---|---|---|---|
| 原始零售，`--repair` | 127 | 31 | 5（令牌） |
| 原始零售落盘后重跑 | 119 | 0 | 5（令牌） |

「可落 0」说明零售能给到 es 的措辞已经全吸收了，再跑只是核对。注意原始零售与清洁版的
可落条数不一样（31 / 30）：清洁版把几条原本能落的行修成了「与现值已一致」，差的那一条
就是这个差。**落盘是替换已译**，不设保护：手工改过的行必须同时进 hold（见下），否则
下一次 `--write` 会按参照原文盖回去。

**零售参照自己的结构缺陷、以及「零售文件里混进了别的语言」，现在都由工具自己处理**，
复跑 de/ru 时不必再写一次性脚本（这两件事原先都是在 `build/es_repair.py` 里手工做的）：

- `--repair`：在 `build` 之后、`apply` 之前跑，只对结构不对的行动手，而且**只调换行标签与
  `<t>`，一个字不改**——按基准的个数补/删换行标签（`<n>` 与带参数的 `<n:25>` 各自按类算；
  `<n>` 差额成对时按一整个段落 `<n><n>` 补；切点按句末挑，挑不到退到分句处或行末；删除时
  接缝处留一个空格，后面紧跟标签或标点则不留），项目符号按基准里「标签`-<t>`」的**第几处**
  补回（连破折号一起丢的也补），百分列按基准同一处还原（见下）。令牌与字体标签不齐的一律
  不动，保留原值让 `apply` 继续拦。修过的与修不了的都写进报告「## 结构修复」一节。

**百分列**：零售 1.0.0 把「`%2` 制表 `%3%`」这一栏拍成「`%2` 空格 `(%3%)`」（制表位变成
空格、百分号被括注吃掉），es 只有 `0x08bb47a4` 一条，de/pl/ru/fr 都是基准写法。这条按
「基准同一处是 `%A<t>%B%<t>`、参照同一处是 `%A …(%B%)<t>`、A/B 对得上」成对认，还原成
`%A<t>%B%<t>`——**不按 id 认**，换成别的拉丁语言遇到同型也能改。基准那一处不是
`%A<t>%B%<t>` 的括注不动（那可能是文案自己写的百分比说明）。
- 语言闸：拉丁文字没有「字种」可判（`translate.apply_map` 的 `script_re` 对 de/fr/es/ru/pl
  返回 None，压根不看），所以 `build` 里按本语言词典的命中率判一次：抹掉令牌／标签／标注后
  词数 ≥ 8，且命中率 < 0.30，判「参照这一行不是目标语言」整行跳过。词典取
  `src/data/qa/dict/<base>.aff|.dic`（与 `lang_check` 同一份），词典缺失就不判——宁可放过
  也不错杀。

es 那 22 条拦下（令牌 5、标签 17）按现在的口径分流：

| 形态 | 处法 |
|---|---|

| 零售这一条内容本身就短了一截（少整句、少整段、换了另一段说明，es 有 4 条：`0x084340c7`、`0x2efebfe6`、`0xe1cdc367`、`0x010faa75`） | 结构现在能对齐（换行标签个数照基准补齐，参数照抄基准），但**内容对不上就不导**；译文本身按 en/fr 重译到通顺，别拿零售那段错位的文字顶上 |

`--repair` 补的换行标签是位置推定：个数与基准一致，切点优先落句末，某一段里排不下时退到

- **零售地名写法不同**（`0xc77f4d5e` 的 `Charles Town` 少一个 e、`0xd607db6d` 同型、

  标注层不能删，不导。
- **零售标点/引号不合规范，或漏了整句**（`0xd07dbe34`、`0xd4cd0f44`、`0xd4cd0fb6`、

  会把这几行按零售原文盖回去（es 上实测盖掉过一轮 5 行，只能从 HEAD 取回；`0x03d3dcd8`
  甚至被盖掉了一句零售本来就没有的 `Estaba en la cocina en ese momento.`）。
  所以凡是手工改过、且零售版更差的行，落盘后都记进 hold，别指望记住。
- **零售与现值同时短一截**（`0x084340c7`、`0x2efebfe6`、`0xe1cdc367`）：en 基准里的整段
  两边都没有，工具判不了这种「都没写」，只能照 en 补。补完同样进 hold，理由同上一条。

判断这三种「短」的时候别只看字符数：`ref_check` 的「长度骤降」比的是 en 基准与**参照**
（零售），不是与译文，所以它报出来的缺口要回 `es.toml` 自己看现值到底有没有那句话。

`0xd3481944` 这类「基准与零售都不是本语言」的行不进 hold：拿同源的法语版当参照重译一遍
（句法照 fr、意思照德文，`!` 句补 `¡`），死了就改译文本身，而不是放着不动。这条的 clean
现已由 `--align-foreign` 退成占位，`retail_import` 拿它当参照时本来就导不进去，已有 es
译文不受影响。

验过的两个坑（都已内置，别改回去）：`[riddle:…]` 的 arg 里带 `source=…@sha256=…`，**上千字
都有**，判「要不要延后」只能看前缀 `\[(riddle|ref):`——用带上限的 `MARK_RX` 去找会漏，整行就
当成没标注被覆盖，标注层直接没了（es 上真丢过 4 行）。判断「这一段是不是目标语言」不能用
字种正则，拉丁系五语只能走词典命中率（见上）。

#### 工具链的顺序：原始零售 → 清洁版 → 以清洁版为基准（`--clean-ref`）

一条语言要同时对着三份文本，分工别混：

| 文本 | 是什么 | 拿来干什么 |
|---|---|---|
| `src\orig\en.gog_1.1.2.3.toml` | 原版基准 | 结构（`<n>`／`<t>`／百分列／项目符号）与令牌条数的唯一依据 |
| `src\orig\<lang>.retail-1.0.0.toml` | 原始零售 | 措辞来源；也是「零售到底怎么写的」的唯一证据，永不改动 |
| `build\ref\retail_clean\<lang>.retail-1.0.0.toml` | 清洁版零售（派生） | **落盘与后续所有校验的输入**：结构已对齐、标点已按本语言定则、空白已规整 |

顺序是固定的三步，别跳第一步：

```bash
# 1) 原始零售 → 清洁版（只生成派生文件，不动译文）
python src\tools\analysis\retail_import.py --lang es --ref es.retail-1.0.0 --clean-ref
# 2) 以清洁版为参照落盘
python src\tools\analysis\retail_import.py --lang es ^
    --ref build\ref\retail_clean\es.retail-1.0.0.toml --repair --write
# 3) 后续校验也用清洁版当参照
python src\tools\analysis\ref_check.py --ref build\ref\retail_clean\es.retail-1.0.0.toml
```

拿原始零售直接 `--write` 会把它未经规整的标点、空白一并落进译文（es 上真这么错过一次：
31 条落进来，回退的路径是「按清洁版重跑一遍」，标点才被规整过来）。工具现在对这件事有
提示：`--write` 的 `--ref` 不在 `build/ref/retail_clean/` 下就会打一句「参照未经清洁」。

`--clean-ref` 也有「先清洁再导入」的一步到位写法（清洁版走内存，不落临时文件）：

```bash
python src\tools\analysis\retail_import.py --lang es --ref es.retail-1.0.0 --clean-ref --write
```

但拆成两步更好审计：清洁版的 diff 值得单独看一眼再落盘。

`--clean-ref` 的报告另写 `build\qa\retail_clean_<lang>.txt`（「## 改动明细」＋「## 留着没修的」
两节）。清洁版是派生文件（`build\` 一起 gitignore），随时可重建，**不进库**；原始零售文件
一字不动，仍是对照基准。

清洁只做能事后核对的写法修正，口径与边界：

- **换行标签个数必须与基准一致**：`<n>` 与带参数的 `<n:25>` 各自按类算，少就补、多就删，
  没有「差额太大就不动」的赦免。切点按顺序挑：最长的段里两侧都还剩 6 个字以上的句末 →
  任一段两侧都还有字的句末 → 任一段的逗号／分号分句处 → 行末（多一个空段）。越往后越像
  推定，位置不满意就人工改原始零售或进 hold 名单，别让个数对不上。
- **其余结构同样以基准对齐**：百分列还原、`-<t>` 项目符号补回。
- **标点按本语言定则**：西语问句／感叹句缺 `¿`／`¡` 就在句首补（插在第一个字母前，`"¿…?"` 也
  在引号内侧）。判句尾判得紧：`?` 后面跟破折号、括号注不算句尾（年份缩写 `(1682? – 1722)` 是
  常客）；紧跟引号括号的 `!` 是引文内部的，不补；起头符号跨 `<n>` 认（`¡%1,<n>me alegro…`
  已经有了）；没有词的字形测试串（`°§$%&()=?…`）不补。`!.`／`?.` 这种多跟一个句号的去掉。
- **空白**：去首尾空白、压行内连续空格；含 `<t>` 的行不压（那里的空白是列排版）。裸 `\t` 只报
  不转。
- **token 缺成分只报**：`%1`／`@A$X$` 少一处、引号不成对、整行不是目标语言（词典命中率判），
  都进「留着没修的」清单，等人工改原始零售或写进 `src/data/qa/retail_hold/<lang>.txt`。
  不译名单与 hold 名单里的行整个跳过（版权声明本来就该与英文一字不差，别拿词典去判它）。

es 实测（hold 名单涨到 21 条之后重跑）：改动 246 条，`<n>`／`<n:25>` 与基准逐行比对
**0 条不一致**；剩 25 处进清单（hold 名单行每条报一次、令牌 5 条）。用清洁版复跑导入：
候选 137 条、`apply` 可落 30 条、拦 5 条（全是令牌），结构类拦截一条不剩。

引用清洁版时记住它是派生件：措辞异同仍要回原始零售核对，别把清洁版的 diff 当成「零售原文」。

### 断行长度复核

`line_run.py` 回答一个机械问题：断完之后，最长的一段有没有超过上限。

口径只有一条：引擎只在 `U+0020` 与 `<n>` 处断行，一段里没有这两样就永远排在同一行。
所以量的是**最长段的可见字数**——标签不计、标注不计，变量 `%1` / `@a$Name$` 记 1 字。
不是像素宽度（控件宽度没在游戏里实测过）。

| 语言 | 上限（含） | 级别 | 说明 |
|---|---|---|---|
| zh | 14 | E | DP 预算 13，不可拆单位允许溢出到 14；>14 即回归，卡流水线 |
| ja | 13 | W | 同一全角预算（方块字，同一控件装得下同样的字数）；当前 460 条超限，属待办 |
| ko | 13 | W | 同一全角预算；当前 9 条正文超限 |
| ru / de / es / fr | — | 跳过 | 拉丁文字按空格断行，最长段就是一个单词，长度由构词决定，补空格解决不了 |

CJK 语言只判「正文段」：`Tiepolo_black14x14aaFHk.res`、`IDM_CONTEST_01_2004_LOG_04_TEXT`
这类路径与键名不算排版缺口。上限与级别都写在 `LIMITS` 里，改一个数字、一个字母即可；
把 ja 的 `W` 改成 `E` 就是「日语清零后开始卡流水线」。

```powershell
python src\tools\analysis\line_run.py            # 摘要
python src\tools\analysis\line_run.py --all      # 列出全部命中
python src\tools\analysis\line_run.py --lang ja  # 只跑一门
python src\tools\analysis\line_run.py --lang ko --update-baseline   # 显式收进基线
```

报告落 `build\qa\line_run_<lang>.txt`，E 级**新增**命中时退出码为 1。
摘要行印两个数：`命中最长` 是超限条目里最长的那个（要处理的到底多长），
`全文最长` 是全表最长段（往往是路径、键名这类技术串）。只印一个数时，
ko 会显示「最长 31」，看着像有一批 31 字的超限文本，实际命中最大只有 18。

不打算再动的命中记进 `src\data\baselines\line_run_<lang>.txt`（一行一条
`id<TAB>实测字数`），报告分「新增」与「基线内」两段，退出码只数新增。
否则 ko 那 9 条人名带括号的旧账会天天报「超限」，看的人很快就会当它不存在。
基线只能 `--update-baseline` 显式改写，不跟着扫描自动更新 ——
否则新增命中会被顺手收编，这道检查也就名存实亡。

同一个度量也做成了给人看的页面 `dist\断行观察窗.html`（上限可调、柱状图、命中列表），
它 `import` 的就是 `line_run.py` 的切段函数，所以页面数字与流水线判定不会各算各的：

```powershell
python build\brk_dump.py      # 重算数据（build 目录不进仓库）
python build\brk_html.py      # 生成 dist\断行观察窗.html
```

### W 级豁免（`src\data\lint_ok\`）

`text_lint` 的 W 级里有一类永远不会靠改译文消失：判据本身不该管的那种（西语生卒年
不确定的 `?`、纯标点的图标条目、日语引文里的常体、字形覆盖测试串）。判断结果以前只
留在口头和提交信息里，下次重跑还得重新判断一遍。现在落到文件：

```
src\data\lint_ok\_common.txt     # 七语共用
src\data\lint_ok\<语言>.txt      # 本语言专用
```

一行 `id<TAB>理由`，`#` 开头是注释。报告头先打「E 级 N 条，W 级 M 条」，再打
「已豁免 W 级 K 条」并逐条列 id、原告警与理由 —— 豁免是**点名**，不是静默消失。

- **只豁免 W 级**。E 级（模板不一致、空值、标注错误…）一律不许免：那些改得动，
  也不该留着。
- 能改判据的就改判据，不要往豁免里塞。现存只有 fr 那一条字形测试串：
  字符串本身就带 `²³€`，改了就没法再测字体覆盖，属于「值不该动、判据也不该改」。

同一层次的「不打算再动的命中」记在 `src\data\baselines\line_run_<lang>.txt`（见上），
两者取向一致：**报出来但不卡流水线**，且必须写清理由。

## 韩语量词复核（`ko_unit_checks`）

判据只有两条，都由 Kiwi 的词元决定，子串不算（正则找量词时 616 处命中里
520 处是 `대출`/`대륙`/`대신` 这类词内误命中）：

1. **缺量词**：数词位后面直接跟白名单可数名词、中间没量词 —— `%1 배`
   会渲成「10 배」。白名单是 `배/선박/함→척`、`선원/병사/정착민/주민/사람→명`、
   `물자/화물/곡물/목재/의류/상품→통`、`상자→개`、`포/대포→대`。
   不收 `선장`：英文 `Captain %1` 里的 %1 是名字，韩语写「이름 + 직함」
   `%1 선장이` 本来就对。
2. **搭配错**：数词 + 量词 + 名词，但名词要的不是这个量词 —— `5척의 병사`、
   `3개의 배`。

边界：数词位只认占位符与阿拉伯数字，固有数词（`두 배로 늘었` 的翻倍、
`한 사람` 的一个人）不参与；标签按段切开再分词，否则
`물자:<t>%2<n>대포:<t>%3` 会把 %2 拼成「%2 대포」。缺 `kiwipiepy` 时整条跳过。
存量 3090 条实测 0 命中，是给后续批次设的栅栏；`--lang ko` 时挂在 E 级。

这道门同时挂在 `apply` 上（`unit_violations` 借同一份规则）：批次十四的
`@a$Amount$통`、`@I$NumShips$척`、`1,500명` 那几处以前全靠手写对，
写成 `@a$Amount$ 물자` 会一路写盘，要到 `check.ps1` 里的 `text_lint` 才报。

## 三层分工

```
src/orig/            英文、法语原版参考：绝对只读，任何流程都不写
src/translations/    译文：唯一手改层，改这里才入库
build/preview/engine_text/   引擎文本：构建期从译文套排版规则生成，不进仓库
build/runtime/PR2Localization/packs/      语言包：编译产物，改了下一次编译就覆盖
```

- 只有 `src/translations/` 是可写的译文层；引擎文本与语言包都是构建产物；
- 想看某个语言补完空格的样子：`python src\tools\text\engine_text.py --lang zh`，
  结果在 `build/preview/engine_text/zh.toml`，可以删。
