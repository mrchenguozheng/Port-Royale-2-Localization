# 译文与语言包

译文的人工维护源是 `src\translations\<语言>.toml`，
`build\PR2Packs\<语言>.txt` 是它的**编译产物**：

```
src/live/zh.toml ──src/tools/pack/compile_pack.py──▶  build/PR2Packs/zh.txt
```

改译文请改 `src\translations\`，然后重新编译语言包。
直接编辑 `build\PR2Packs\*.txt` 下次编译会被覆盖。

## 生成 → 编辑 → 构建

- `src/seed/<语言>.toml`：初版译文（默认锁定，编辑器里逐条解锁才能改）；
- `src/live/<语言>.toml`：编辑器直接维护的工作文本；保存只写这里；
- 构建（`apply_patch`）直接编译 `live/`，不会重新生成或覆盖；
- 需要从初版重新生成时，手动跑 `apply_zh_rules.py` / `apply_ja_rules.py`；
- 旧的人工审核流程（`zh_review.py`、审核标记、页面横幅、已审勾选）已全部移除。

## 规则按语言分开

标点/空格规则不再堆在 `normalize_text.py` 里，而是一语言一份：

```
src/tools/text/lang_rules/
├─ base.py   共用机制：标点后空格、占位符两侧、<n> 去空格
├─ zh.py     中文：全角标点表、半角→全角映射（, → ，）、normalize()
└─ ja.py     日文：自己的标点表（, → 、）、助词空格、normalize(particles=)
```

- `normalize_text.py` 只剩 CLI：选语言 → 读 toml → 调 `lang_rules.<语言>.normalize()` → 写回；
- 加一种语言：在 `lang_rules/` 放 `<代码>.py`，提供 `LANG / PUNCT / ASCII / CJK_RX / normalize()`，
  再登记到 `lang_rules/__init__.py` 的 `REGISTRY`；
- 没有专用规则的语言仍可用 `--force` 套中文规则；
- `・`(U+30FB) 和 `ー`(U+30FC) 虽然落在假名区，但**不当作正文**，不会被拆开
  （否则 `%2・%3`、`迭戈・莫扎雷拉` 会出空格）。

## 目录结构

```
src/live/
├─ zh.toml                生成物：规则加完空格的结果，别手改
└─ ja.toml                日语译文（直接编辑）
src/orig/
├─ en.gog_1.1.2.3.toml    英文原文，基准（id 顺序以它为准）
├─ fr.gog_1.1.2.42.toml   法文原文
└─ zh.gog_1.1.2.3.toml    中文文本源：干净的译文，不带任何补空格
```

`en` / `fr` 是**只读参考原文**，不生成语言包，`compile_pack --lang en`
返回退出码 2。它们留在语言列表里供对照。

每条一行，键就是 hash：

```toml
"0xd2d0a572" = "萧条"
```

键必须加双引号（裸键不能数字开头）。**不能用 `[["0x…"]]` 数组表** ——
它拦不住重复键。

## 编译语言包

```
src\build_translation.bat
```

只编语言包，等价于 `python src\tools\pack\compile_pack.py`，只是顺带自己找 Python。

它把 `src\locale.ini` 原样复制进 `build\PR2Packs\` —— 那个文件是模板不是
生成物，DLL 靠它知道该读哪个语言包，缺了就什么都加载不出来。

编出 0 条时会**报错退出码 1 并且不写文件** —— 一个 0 条的语言包装进游戏
等于没汉化，而调用方只看「文件在不在」，空文件比报错更难查。

## 语言包格式

编译产物**没有任何说明头**，第一个字节就是第一条数据：

```
0x1007ADD4 = 剧本顺利完成
0x100AFA32 = %1，<n>我们的教堂需要持续修缮，……
```

| 记号 | 含义 |
|---|---|
| `0xHASH = 文本` | 一条一个 hash 一行，hash 大写 |
| `<n>` | 引擎的换行标签 |
| `<o:0x…>…</o>` | 着色标记，冒号后是 ARGB 颜色 |
| `<f:fonts\…>` | 内联指定字体 |
| `%1`、`@D$EndDate$` | 占位符，个数与种类必须和原文一致 |
| `\|` | **旧写法，已废弃**：编译时仍会转成 `<n>` 兜底，源文件里不要再写 |

解析器会跳过 `#` 和 `;` 开头的行，所以手写注释不会被当成数据 ——
但**别依赖这个**：语言包是编译产物，下次编译就没了。要写说明写在这里。

## 排版规则（实测）

- **引擎按空格分词。** 中文天然不用空格分界，整串汉字连同标点会被当成
  一个超宽单词，超宽的整行**直接丢弃 = 完全不显示**，不是截断。
  每个界面控件能放多宽都不一样，工具**不估算宽度**，只能逐个界面实测。
- 标签（`<n>`、`<o:0x…>`、`<f:fonts\…>`）**原样保留**，不要删。
- 占位符一个都不能少，也**不要新增** `<n>` —— 换行只放在原文已有
  `<n>` 的位置（与英文/法文原文的分段一一对应）。

## 空格约定（中文 / 日文这类不用空格分词的语言）

这一节是**游戏引擎渲染文字的要求**，不是排版偏好：引擎按空格切词，
词太长就整行丢弃；占位符要能被单独识别，也必须在两侧隔开。
所以凡是「词与词之间本来不写空格」的语言，译文都要按下面的规则补半角空格。

**触发条件是两个**：标点是**全角**的，而且词与词之间**本来不写空格**。
中文、日文两条都满足，所以要按下面的规则补空格。

**韩文默认不触发**：韩语有 띄어쓰기（分写法），词间本来就写空格，
分词方式和英文一样；标点也用**半角 ASCII**（`.` `,` `?` `!` `:`），不是全角。
所以韩文不需要给标点补空格，保留原有词间空格即可。参考：
[Spaces and full width punctuation in Korean（W3C 讨论）](https://lists.w3.org/Archives/Public/www-archive/2020Sep/0002.html)、
[Word Segmentation in Korean (Stanford)](https://nlp.stanford.edu/fsnlp/korean.html)。

**但如果某语言用了全角标点**（包括韩文的旧式全角写法，或以后出现的新语言），
就按同一套规则处理 —— 规则看的是「全角标点」而不是国籍。

**标点**

- 单个标点（`，。、；：！？…・` 等）后面补 **一个**半角空格；
- 成对标点（`「」『』“”《》【】（）` 等）在**外侧**各补一个：开口标点前、
  收口标点后（`日志的 「成就」 里`，不是 `日志的「 成就 」里`）；
- 相邻标点之间只留 **一个**空格，标点串要贴合（`《航海条例》。` 不会变成
  `《航海条例》 。`）；
- **整段末尾不加空格**，段首也不留；
- 间隔号 `·`（人名 Janet · Smith 那种）**不参与**规则，保持贴合。

日文用自己的一套标点：单标点 `、。！？…・：；～—`，成对 `「」『』（）［］【】〈〉〔〕`。

**占位符**

- `%1`、`%10`、`%02u`、`%s` 与 `@X$变量$`（如 `@T$Town$`、`@D$EndDate$`）
  只要一侧紧挨着中文/日文字符或标点，那一侧就补一个半角空格：
  `可在 %3 建造`、`赶往 @T$TOWN$ ，`；
- 多个空格会合并成一个，不会出现连续空格。

**日语助词（可选）**

日语句子中间的助词后面也可以补一个半角空格（`市场に 来てくれれば`），
同样是给引擎切词用。规则是保守的，只处理「汉字/片假名 + 助词 + 汉字/片假名」：

- 助词表：`から まで より など ほど ばかり だけ しか こそ さえ でも って ので のに けど`，
  以及单字 `は が を に で と も へ や か ね よ`（**不含「の」**：`木材の需要` 这种
  领格切开会显得太碎）；
- 助词后面必须紧跟汉字/片假名/开括号才补空格，**后面是平假名一律跳过**
  （避免把「について」「として」「ません」这类词尾切开）；
- 后面紧跟标点或句尾时不动，免得出现「船か 。」这种标点前空格。

判定方式（自动选择）：

1. 装了 **Janome** 或 **fugashi** 就用形态素分析，只给「名词/代词/数词 + 助词」补空格，
   并跳过 `について` `として` `によって` `という` 这类固定搭配；
2. 两个都没有时退回正则（汉字/片假名 + 助词 + 汉字/片假名）。

开关：`python src\tools\text\normalize_text.py --lang ja --particles`。

**其它**

- `<n>` 换行标签两侧**不留空格**（`…。 <n>下一段` 会整理成 `…。<n>下一段`）；
- 这些规则由译文处理脚本批量执行（`|`→`<n>`、标点空格、占位符空格），
  新增语言时按同一套约定处理即可。

## 敬语体系与「过度礼貌」

有敬语体系的语言，翻译时最容易犯的错不是译错，而是**把语气抬高**。
这一节记录问题、判定标准和目前的处理约定。

**哪些语言有敬语体系**

| 语言 | 体系 | 表现 |
|---|---|---|
| 日语 | 尊敬語・謙譲語・丁寧語・美化語 | `いらっしゃる` / `差し上げる` / `です・ます` / `お〜` |
| 韩语 | 높임법（敬语法） | `하십시오체` / `해요체` / `반말`，以及 `드리다`、`모시다` 等谦让动词 |
| 汉语 | 没有语法敬语，但有敬辞 | `您`、`请`、`贵`、`光临`、`惠顾`、`敬告` |
| 英语 / 法语 / 德语 | **没有**敬语体系 | 只有人称礼貌：法 `vous`/`tu`、德 `Sie`/`du` |

**原文到底多礼貌**

本作原文是德语（`Sie`），英译用中性 `you` + 祈使句，法译一律 `vous`。
`vous` / `Sie` 是**人称上的礼貌**，不是敬语层次——它没有「谦让」这一维。
所以 `you` / `vous` 的等价物就是日语的**です・ます**，这一点不需要改动。

**过度礼貌是怎么产生的**

- 把「我给你」译成 `差し上げます`（谦让语把玩家抬高了一档，原文只是 `I will give you` / `je vous offre`）；
- 把「你会收到」译成 `お受け取りになります`（原文 `you will receive` 是平陈述）；
- 叙述句、系统通报也写成敬体，或对玩家使用 `お持ちです`、`お越しください`；
- 自行添加原文没有的收尾修饰，例如「わが国も深く感謝しています」；
- 反向错误同样存在：海盗、醉汉的台词本来粗，若照 `vous` 抬成敬体就失真。

**约定**

1. **NPC 对玩家说话**（总督、商人、财政官、信件）→ です・ます，
   **不加谦让语**，除非原文本身有明确自谦（本作没有这种情况）；
2. **海盗、醉汉、粗人** → 常体（`だ`・`ぞ`・`な`），不要因为法文用 `vous` 就跟着抬；
3. **事件通报、界面提示、系统祝贺** → 中性语气或です・ます，但**不对玩家使用敬称**；
   通报用第三人称过去时；
4. **不新增**原文没有的敬语修饰、感谢语、客套句；
5. 汉语：`您` 与原文 `vous` 对齐，同一角色**不要忽「您」忽「你」**；
   敬辞（`光临`、`惠顾`）只用于商人招揽生意的文案；
6. 韩语（尚未开始）：先统一选定 `해요체` 还是 `하십시오체`，
   同一 NPC 不得混用；谦让动词 `드리다`/`모시다` 只在原文确有自谦时使用。

**怎么查**

```bash
python src\tools\analysis\speaker_audit.py
```

会重新生成 [说话人分级](说话人分级.md)（含 A/B/C/N 分级）和逐条
`speaker-audit.csv`，其中「语体待查」一栏列出日语里出现
`差し上げ` / `お受け取り` / `お持ち` / `お越し` / `申し上げ` / `いたします`、
而英文原文是平陈述的条目。

轻重不同：`差し上げます`、`お受け取りになります` 最该改；
`お持ちです`、`お越しください` 只是普通敬语，与 `vous` 相称，可以保留；
`おめでとうございます` 属系统祝贺，不算超格。

## 校验

```
python src\tools\translate.py status              # 进度
python src\tools\translate.py export --out x.jsonl # 导出待译条目
python src\tools\translate.py check x.jsonl        # 校验
```

三个子命令都接受 `--lang <代码>`，默认操作 `translations\` 下第一个
可编辑语言。

`check` 拦这几类问题：

| 检查 | 含义 |
|---|---|
| 占位符 | `@D$EndDate$`、`%1` 必须与原文**种类和数量**一致 |
| 标签轮廓 | 译文**不得**新增 `<n>` / `<o>` / `<f>` / `<c>` / `<t>` 任何标签 |
| 未译 | 占位文本形如 `0x<id> \| <英文原文>` |

换行只能在原文已有 `<n>` 的位置换。自然要另起行时，
交给渲染器按宽度自动折行，不靠手工插 `<n>`。

## 加一种语言

三步，全程不需要碰 C++ 或 DLL。

1. **建译文文件** `src\translations\<代码>.toml`。

   一条命令搞定 —— 复制一份原文当模板，逐条把右边改成译文：

   ```
   python src\tools\pack\new_lang.py --new-lang <代码>
   ```

   它复制 `references\en.gog_1.1.2.3.toml`（想从法文起步就加 `--from fr`），
   生成的文件每行右边都是原文，也就是「未译」状态。
   已存在的文件不会被覆盖。

   手抄也行，格式每条一行：

   ```toml
   "0xd2d0a572" = "Vegetating"
   ```

   只写你真要翻的条目就够 —— 剩下的自动显示英文。但**条目数与顺序必须和
   `references\en.gog_1.1.2.3.toml` 完全一致**，因为对齐靠位置。少了或多了
   `compile_pack.py` 会报错。

   `<代码>` 就是文件名，会直接变成语言包里的文件名和 `locale.ini`
   里的 `language=` 值，也用作合并时的字段名 —— 所以别用别的分隔符。

2. **跑窗口** `start.bat`，在新语言那一栏打勾 →
   「构建所选语言」→ 选游戏目录 → 「复制到游戏目录」。

   语言列表是扫 `translations\*.toml` 得到的，加了文件就自动出现。

3. **切语言** 直接用窗口的「启动语言」下拉，然后点「保存语言设置」——
   **下拉本身不动任何文件**，只有点「启动游戏（已注入）」或
   「保存语言设置」才写 `PR2Packs\locale.ini` 的 `language=`
   （`build\` 和游戏目录各一份）。语言没变化时连这个也不写。

命令行的等价做法：

```
python src\tools\pack\compile_pack.py --lang <代码>
python src\tools\translate.py status --lang <代码>
```

语言代码没有形式要求，`zh` / `zh-CN` / `de` / `pt-BR` 都行，
只要**和 toml 文件名一致**。

### 译文编辑区（contenteditable）

译文区不再用「透明 textarea + 高亮覆盖层」，而是 `contenteditable`：空格直接渲染成 `<span class="hl-sp">`，
不存在两层排版对不齐的问题。中文输入法组合输入期间（compositionstart→end）不重绘 DOM，
只在组合结束后统一重排并恢复光标，避免打断候选词。

**人名占位符的间隔号**：编年史里 `%1 %2 %3` 通常是「等级 / 名 / 姓」，
所以只写 `%1 %2・%3`（等级后空格，名与姓之间用 `・`）；
`%1 %2` 这种两段式若表示「等级 + 全名」，用空格，不能写成 `%1・%2`，
否则会出现「见习水手·巴尔塔萨·马尔伯夫」。

### 占位符连接规则（按 hash，不做批量替换）

`%1 %2` 可能是「等级 + 全名」也可能是「名 + 姓」，批量替换必然有一边出错。
现在改成按 hash 记录规则：

```toml
# src/live/placeholder_roles/zh.toml
["0x338a357f"]
rules = [
  { pair = ["1", "2"], sep = " ", note = "等级 + 全名" },
]
```

工具：`python src/tools/placeholder_roles.py`

- `--report --lang zh|ja`：扫描所有相邻 `%N %N`，导出 `docs/占位符语义.<lang>.csv`
  （hash、当前连接符、推断建议、英文上下文），供人工判断；
- `--check`：按该语言已记录的规则校验，列出不符的连接符；
- `--fix`：**只**改有明确规则的条目，其余不动；
- 规则按语言分开：`placeholder_roles/zh.toml`、`placeholder_roles/ja.toml`，默认 `--lang zh`。

新增一条规则：在 CSV 里找到那对参数 → 在 toml 里加一行 → `--check` →（需要时）`--fix`
→ `apply_zh_rules.py` 重新生成。

### 排版优先用空格，不改词句

游戏按空格断行，详情框高度固定。遇到「顶部被裁、只剩最后一行」这类显示问题，
处理方式是**在合适位置补少量空格**，让断行提前，而不是删字或缩短译文。

- 空格是排版手段，不改变语义；译文内容以文本源为准；
- 需要压缩行数时，优先在句读处、长词前补空格；
- 不要为了塞进框里而改写或删减译文。

### 编辑器里的占位符与空格提示

每条译文上方有一条信息栏：

- **占位符**：列出当前条目英文里的 `%1` / `@T$Town$` 等，并给含义
  （`%N` 按英文上下文标「等级/头衔、名、姓、姓名」，`@g$…$` 标「金额」等）；
  - 占位符在正文里渲染成可拖动的胶囊，胶囊内直接显示含义（如 `@g$TotalPrice$ 金额`）；
  含义用 CSS `::after` 渲染，不会进入正文或保存内容；
- 拖动胶囊到目标位置即完成移动；
  - 占位符不能删除：删掉后会自动补回（数量以英文原文为准）；
  - 信息栏只显示每个占位符需要的个数（`×2`）与含义，不再有插入/移除按钮；
  - 译文里有、原文没有的标红「原文没有」并可移除；
- **空格**：只显示比干净译文多几处（标点后补的排版空格），不列位置；
- **标记**：`<n>` 等排版标签的含义。

接口：`/api/entry-info?lang=zh&id=<hash>`。

### 干净文本源

`src/orig/` 下每个语言可以有一份**不带排版空格**的干净译文：

- `zh.gog_1.1.2.3.toml`：中文（生成 `live/zh.toml` 的源）；
- `ja.toml`：日语（从 `live/ja.toml` 去掉排版空格得到）。

编辑器信息栏的「空格：多 N 处」就是拿当前译文和这份干净文本对比得出的。

### 日语：干净源 → 规则生成

```powershell
python src/tools/text/apply_ja_rules.py          # 只对比，打印差异条数与样例
python src/tools/text/apply_ja_rules.py --write  # 写入 live/ja.toml
```

规则来自 `lang_rules/ja.py`：标点规范化、占位符两侧空格、助词后补空格
（装了 janome/fugashi 用形态素，没装用正则兜底）。
默认不写文件，避免覆盖手工排版；确认差异可接受后再加 `--write`。

### 占位符数量必须逐个一致

- 信息栏按数量显示（如 `×2`），原文与译文数量不同的占位符标红，并提示「占位符数量不符」；
- 保存时服务端强制校验：`/api/patch` 发现任何占位符多用或少用会整批拒绝，
  返回具体条目与数量（原文 N 个 / 译文 M 个），不会写入文件。

### 撤销与还原干净原文

信息栏右侧两个按钮：

- **撤销**：撤销当前条目上一次编辑（最多保留 20 步，内存中有效）；
- **还原干净原文**：用 `orig/` 里的干净文本替换当前译文（`/api/clean`），
  还原后仍是未保存状态，可再撤销或保存；

有未保存改动时，翻页、跳转、切换语言或切到「安装与启动」都会先弹确认，
选择保存才会离开；关闭/刷新页面也会提示。译文与刚载入时相同则视为未改动，不会拦。

注意：干净文本本身不带排版空格；还原后如果要保留排版，需要重新套用对应语言的规则。

### 按 hash 的术语例外

术语检查误报时（例如 `0x28b1f98d` 的「Ship's Boy」在译文里是运行时占位符，
不该要求出现「见习水手」），可以在编辑器里单独放行：

- 信息栏会显示「术语：Ship's Boy 应为「见习水手」」和「忽略」按钮；
- 点「忽略」写入 `glossary/hash_rules.toml`，只对这一条生效；
- 已忽略的显示「已忽略：Ship's Boy」和「恢复」按钮；
- 接口：`GET /api/hash-rules?id=`、`POST /api/hash-rule {id, term, skip}`。

`0x28b1f98d` 已按此规则忽略「Ship's Boy」。

### 保存即生效

- 编辑器里点保存直接写 `live/`，没有单独的审核步骤；
- `orig/` 只放干净文本（不含排版空格），生成物一律由规则产生。

### 提交前统一检查

```powershell
check.bat                 # 或 python src/tools/check.py
```

依次跑：跨模块引用检查 → 规则单测（`tests/`）→ 生成物一致性（`apply_zh_rules.py --check`）。

### 三个目录的分工

```
src/orig/   英文、法语原版参考：绝对只读，任何流程都不写
src/seed/   初版译文（机器/AI/人工初稿）：默认锁定，编辑器里逐条解锁后才能改
src/live/   编辑器直接维护的文本：保存就改这里，构建也只从这里读
```

- 编辑器保存只写 `live/`，不再动 `seed/`；
- 译文框下方固定显示「初版」文本，便于和当前工作文本对照；内容不同（忽略空格）时左侧出现高亮竖线；
- 初版块右上角「解锁编辑」打开初版弹窗：默认只读；点「解锁编辑」并确认后，
  只能改这一条，保存或关闭后自动重新锁定（不记住解锁状态）；
- 「还原干净原文」用的是初版文本，会覆盖当前工作文本（可撤销）；
- `apply_zh_rules.py` 仍可手动从 `seed/zh.toml` 生成 `live/zh.toml`，但不是构建步骤。

### 规则轨迹（可视化）

信息栏「规则」按钮打开弹窗，逐阶段显示这条译文：

```
初版            → 标点规范化 → 连词后空格 → 人名/城镇名空格 → 当前译文
```

- 每个阶段只把「相对上一阶段变化的部分」高亮；
- 接口：`/api/rule-trace?lang=&id=`；
- 目前中文展示 4 个阶段，其它语言展示「初版 → 规范化 → 当前译文」；
- 末尾「命中标注」按颜色标出规则改动的字符：橙色=标点/占位符空格，蓝色=连词，绿色=人名/城镇名；
  当前译文与规则生成不同时，会注明标注针对的是生成结果。

### 正文里的空格着色（L1）

编辑器默认不高亮空格；「空格着色」已移除（效果不稳定），
需要看规则处理过程时可打开信息栏的「规则」弹窗，按阶段查看。

### 手动修改占位符含义

- 信息栏占位符胶囊后的「改」按钮：弹出输入框，改这个占位符在**当前 hash** 里的含义；
- 保存到 `glossary/placeholder_meanings.toml`，按语言 + hash + 占位符各存一份；
  含义允许空字符串（表示明确留空，不再自动推断）；
  编辑器打开一条时也会把该条用到的占位符含义固定下来，互不影响；
- 改动只影响显示，不影响译文与编译；可反复修改。
