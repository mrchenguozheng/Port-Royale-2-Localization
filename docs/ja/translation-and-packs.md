# 翻訳と言語パック

翻訳のために人間が保守するソースは `src\translations\<language>.toml` であり、
`build\PR2Packs\<language>.txt` はその**コンパイル済み出力**である：

```
src/live/zh.toml ──src/tools/pack/compile_pack.py──▶  build/PR2Packs/zh.txt
```

翻訳を変更するには `src\translations\` を編集してから、言語パックを再コンパイルする。
`build\PR2Packs\*.txt` を直接編集しても、次回のコンパイルで上書きされる。

---


> **`seed/zh.toml` の由来**：2026-10-21 に、当時の `zh.toml` から
> **追加されたスペースをすべて取り除く**形で再構築した（漢字の間、約物の周囲、プレースホルダーの両側のいずれにも
> 残っていない）。一方、原文がもともと持っているスペース（em ダッシュと `<o:…>`）は
> そのまま残した。再構築後に `apply_zh_rules.py` を再度実行したところ、得られた `zh.toml` は
> 配備版と**バイト単位で完全に一致**したため、テキストソースとして使用できる。
> これは「当時、項目ごとに手書きした最初の版」ではない。その版は別途アーカイブされて
> いない。後になって、あるスペースがもともと原文にあったことが判明した場合は、
> `seed/zh.toml` を直接編集すればルールが再生成する。



## 生成 → 編集 → ビルド

- `src/seed/<language>.toml`：初期翻訳（既定ではロックされている。エディタで項目ごとにロックを解除して変更する）；
- `src/live/<language>.toml`：エディタが直接保守する作業テキスト。保存はここにのみ書き込まれる；
- ビルド（`apply_patch`）は `live/` を直接コンパイルし、再生成も上書きもしない；
- 初期版から再生成するには、`apply_zh_rules.py` / `apply_ja_rules.py` を手動で実行する；
- 旧来の手動レビュー作業（`zh_review.py`、レビューマーカー、ページバナー、レビュー済みチェックボックス）は完全に削除された。

## 言語ごとに分割されたルール

句読点とスペースのルールは、もう `normalize_text.py` に詰め込まれていない。言語ごとに 1 ファイルになっている：

```
src/tools/text/lang_rules/
├─ base.py   shared machinery: space after punctuation, spaces around placeholders, removing spaces around <n>
├─ zh.py     Chinese: full-width punctuation table, half-width→full-width map (, → ，), normalize()
└─ ja.py     Japanese: its own punctuation table (, → 、), particle spacing, normalize(particles=)
```

- `normalize_text.py` は現在 CLI のみである。言語を選ぶ → toml を読む → `lang_rules.<language>.normalize()` を呼ぶ → 書き戻す；
- 言語を追加するには、`lang_rules/` に `<code>.py` を置き、`LANG / PUNCT / ASCII / CJK_RX / normalize()` を提供し、
  次に `lang_rules/__init__.py` の `REGISTRY` に登録する；
- 専用ルールのない言語でも、`--force` で中国語ルールを適用できる；
- `・`(U+30FB) と `ー`(U+30FC) はカナのブロックに含まれるが、**本文としては扱われず**、決して
  分割されない（そうしないと `%2・%3` や `迭戈・莫扎雷拉` にスペースが入ってしまう）。

## ディレクトリ構成

```
src/live/
├─ zh.toml                generated: the result after the rules add spaces; do not edit by hand
└─ ja.toml                Japanese translation (edited directly)
src/orig/
├─ en.gog_1.1.2.3.toml    English original, the baseline (id order follows it)
├─ fr.gog_1.1.2.42.toml   French original
└─ zh.gog_1.1.2.3.toml    Chinese text source: a clean translation with no added spaces
```

`en` / `fr` は**読み取り専用の参照原文**である。これらの言語パックは生成されず、
`compile_pack --lang en` は終了コード 2 を返す。比較のために言語一覧には残している。

1 行 1 エントリで、キーはハッシュである：

```toml
"0xd2d0a572" = "萧条"
```

キーはダブルクォートで囲む必要がある（ベアキーは数字で始められない）。**`[["0x…"]]` の配列テーブルは使わない** —
重複キーを検出できないためである。

## 言語パックのコンパイル

```
src\build_translation.bat
```

言語パックのみをコンパイルする。`python src\tools\pack\compile_pack.py` と同等だが、Python の場所も自動的に見つける。

`src\locale.ini` をそのまま `build\PR2Packs\` にコピーする。このファイルはテンプレートであり、生成物ではない。DLL はこれを見てどの言語パックを読むかを決めるため、これがないと何も読み込まれない。

0 エントリをコンパイルしようとした場合は、**終了コード 1 で失敗し、ファイルを書き出さない**。0 エントリのパックをゲームに入れても何も翻訳されないし、呼び出し側は「ファイルがあるか」しか見ないため、空ファイルはエラーよりも診断が難しい。

## 言語パックの形式

コンパイル済み出力には**一切の説明ヘッダーがない**。先頭のバイトが最初のデータエントリである：

```
0x1007ADD4 = 剧本顺利完成
0x100AFA32 = %1，<n>我们的教堂需要持续修缮，……
```

| 記法 | 意味 |
|---|---|
| `0xHASH = text` | 1 行 1 ハッシュ。ハッシュは大文字 |
| `<n>` | エンジンの改行タグ |
| `<o:0x…>…</o>` | 色指定。コロンの後ろが ARGB カラー |
| `<f:fonts\…>` | インラインのフォント指定 |
| `%1`、`@D$EndDate$` | プレースホルダー。個数と種類が原文と一致していなければならない |
| `\|` | **旧形式・非推奨**：コンパイル時に `<n>` へ変換されるフォールバックは残っているが、ソースファイルにはもう書かない |

パーサーは `#` と `;` で始まる行をスキップするため、手書きのコメントはデータとして扱われない。
ただし**これに頼らないこと**：言語パックはコンパイル済み出力であり、次のコンパイルでそれらは消える。説明はこちら（この文書）に書く。

## レイアウトのルール（実測）

- **エンジンはスペースでトークン化する。** 中国語はもともとスペースを語の境界に使わないため、漢字の連なりと
  約物がまとめて 1 つの幅の広すぎる語として扱われ、幅を超えた行は
  **丸ごと破棄される＝まったく表示されない**（切り詰めではない）。
  UI コントロールごとに幅は異なり、ツールは**幅を見積もらない**。画面ごとに実測するしかない。
- タグ（`<n>`、`<o:0x…>`、`<f:fonts\…>`）は**そのまま保持する**。削除しない。
- プレースホルダーを 1 つでも欠かしてはならず、**新たに `<n>` を追加してもいけない**。改行は原文に
  すでに `<n>` がある位置にのみ入れる（英語・フランス語原文の段落分けと 1 対 1 に対応させる）。

## スペースの慣習（中国語・日本語など、単語をスペースで区切らない言語向け）

本節は**ゲームエンジンがテキストを描画する方法上の要件**であり、組版上の好みではない。エンジンは
スペースで単語を分割し、長すぎる語は行全体を破棄させる。プレースホルダーは単体で認識できる
必要があるため、両側も区切らなければならない。
したがって「単語を通常スペースで区切らない」言語では、以下のルールに従って翻訳に
半角スペースを追加する。

**トリガー条件は 2 つ**ある。約物が**全角**であること、そして単語を**通常スペースで区切らない**こと。
中国語と日本語は両方を満たすため、以下のルールに従う。

**韓国語は既定では該当しない**。韓国語には 띄어쓰기（分かち書き）があり、単語はすでにスペースで
区切られていて、トークン化も英語と同じように機能する。約物も**半角 ASCII**
（`.` `,` `?` `!` `:`）であり、全角ではない。
したがって韓国語では約物の周囲にスペースを追加する必要はなく、既存の単語間スペースを保てばよい。参考：
[韓国語の空白と全角約物（W3C の議論）](https://lists.w3.org/Archives/Public/www-archive/2020Sep/0002.html)、
[韓国語の単語分割（Stanford）](https://nlp.stanford.edu/fsnlp/korean.html)。

**ただし全角約物を使う言語**（旧式の全角韓国語や、後に現れる新しい言語を含む）では、同じルール一式で
扱う。ルールは「全角約物」を見ており、国籍を見ているわけではない。

**約物**

- 単独の約物（`，。、；：！？…・` など）の後ろに**半角スペースを 1 つ**入れる；
- 対になる約物（`「」『』“”《》【】（）` など）は、それぞれの**外側**に 1 つ入れる。開きの前、
  閉じの後ろ（`日志的 「成就」 里` と書き、`日志的「 成就 」里` とは書かない）；
- 隣接する約物の間は**スペース 1 つ**だけにする。約物の連続は詰めたまま（`《航海条例》。` を
  `《航海条例》 。` にしない）；
- **段落の末尾にはスペースを入れない**。先頭にも入れない；
- 中黒 `·`（Janet · Smith のような名前）は**ルールの対象外**で、詰めたままにする。

日本語は独自の約物セットを使う。単独形 `、。！？…・：；～—`、対 `「」『』（）［］【】〈〉〔〕`。

**プレースホルダー**

- `%1`、`%10`、`%02u`、`%s`、`@X$variable$`（`@T$Town$`、`@D$EndDate$` など）については、片側が
  中国語・日本語の文字や約物に直接隣接するとき、その側に半角スペースを 1 つ入れる：
  `可在 %3 建造`、`赶往 @T$TOWN$ ，`；
- 複数のスペースは 1 つにまとめられる。連続したスペースが現れることはない。

**日本語の助詞（任意）**

日本語文の途中で助詞の後ろに半角スペースを追加してもよい（`市场に 来てくれれば`）。これも
エンジンのトークン化のためである。ルールは保守的で、「漢字/カタカナ + 助詞 + 漢字/カタカナ」のみを扱う：

- 助詞一覧：`から まで より など ほど ばかり だけ しか こそ さえ でも って ので のに けど`、
  および 1 文字の `は が を に で と も へ や か ね よ`（**「の」は除外**：`木材の需要` のような
  所有表現を分割すると区切り過ぎて見える）；
- スペースを入れるのは、助詞の直後が漢字/カタカナ/開き括弧のときだけである。
  **ひらがなが続く場合は必ずスキップ**する（「について」「として」「ません」のような語尾を切らないため）；
- 直後に約物や文末が続く場合は何もしない（「船か 。」のような約物前のスペースを避ける）。

判定方法（自動で選択される）：

1. **Janome** か **fugashi** がインストールされていれば、形態素解析を使い、
   「名詞/代名詞/数詞 + 助詞」の場合にのみスペースを入れる。`について` `として` `によって` `という` などの固定表現はスキップする；
2. どちらも使えない場合は正規表現（漢字/カタカナ + 助詞 + 漢字/カタカナ）にフォールバックする。

切り替え：`python src\tools\text\normalize_text.py --lang ja --particles`。

**その他**

- `<n>` 改行タグの両側に**スペースを入れない**（`…。 <n>下一段` は `…。<n>下一段` に正規化される）；
- これらのルールは翻訳処理スクリプト（`|`→`<n>`、約物のスペース、プレースホルダーの
  スペース）によって一括適用される。新しい言語は同じ慣習に従えばよい。

## 敬称体系と「過剰な丁寧さ」

敬称体系を持つ言語で翻訳時にもっとも起こりやすい誤りは、誤訳ではなく
**語域（レジスター）を上げてしまうこと**である。本節では問題・判断基準・現在の慣習を記録する。

**敬称体系を持つ言語**

| 言語 | 体系 | 現れ方 |
|---|---|---|
| 日本語 | 尊敬語・謙譲語・丁寧語・美化語 | `いらっしゃる` / `差し上げる` / `です・ます` / `お〜` |
| 韓国語 | 높임법（敬語法） | `하십시오체` / `해요체` / `반말`、ほかに `드리다`、`모시다` などの謙譲動詞 |
| 中国語 | 文法上の敬称はないが、丁寧な語彙がある | `您`、`请`、`贵`、`光临`、`惠顾`、`敬告` |
| 英語 / フランス語 / ドイツ語 | 敬称体系は**ない** | 個人的な丁寧さのみ：フランス語 `vous`/`tu`、ドイツ語 `Sie`/`du` |

**原文は実際どれくらい丁寧か**

本作の原文はドイツ語（`Sie`）である。英語訳は中立的な `you` と命令形を使い、フランス語訳は
全体に `vous` を使っている。
`vous` / `Sie` は**人への呼びかけ方の丁寧さ**であり、敬称のレベルではない。「謙譲」の次元はない。
したがって `you` / `vous` に相当するのは日本語の**です・ます**であり、そこを変える必要はない。

**過剰な丁寧さはどう生まれるか**

- 「I give you」を `差し上げます` と訳す（謙譲形でプレイヤーを 1 段上げてしまうが、原文は
  `I will give you` / `je vous offre` にすぎない）；
- 「you will receive」を `お受け取りになります` と訳す（原文の `you will receive` は平叙文である）；
- 地の文やシステム通知まで丁寧体で書き、プレイヤーに `お持ちです`、
  `お越しください` と呼びかける；
- 原文にない結びの修飾を加える。たとえば「わが国も深く感謝しています」；
- 逆の誤りもある。海賊や酔漢の台詞はもともと粗い。`vous` に合わせて丁寧体に
  持ち上げると不自然になる。

**慣習**

1. **プレイヤーに話しかける NPC**（総督、商人、財務官、手紙）→ です・ます。
   **謙譲形は使わない**。ただし原文自体が明確に自己卑下的な場合を除く（本作には該当例がない）；
2. **海賊、酔漢、粗野な人物** → 常体（`だ`・`ぞ`・`な`）。フランス語が `vous` だからといって上げない；
3. **イベント通知、UI のプロンプト、システムの祝福** → 中立の語域または です・ます。ただし
   **プレイヤーへの敬称は使わない**。通知は三人称の過去形を使う；
4. 原文にない敬称の修飾、感謝、世辞を**加えない**；
5. 中国語：`您` は原文の `vous` に対応する。同一人物の範囲内で**「您」と「你」を切り替えない**。
   丁寧な語彙（`光临`、`惠顾`）は商人の売り込みでのみ使う；
6. 韓国語（未着手）：まず `해요체` か `하십시오체` のどちらかに決めて一貫して適用し、同じ NPC で
   混在させない。謙譲動詞 `드리다`/`모시다` は原文が本当に自己卑下的な場合にのみ使う。

**確認方法**

```bash
python src\tools\analysis\speaker_audit.py
```

[話者ティア](speaker-tiers.md)（A/B/C/N のティア付き）と、エントリごとの
[speaker-audit.csv](../csv/analysis/speaker-audit.csv) を再生成する。「register to review」列には、
日本語に `差し上げ` / `お受け取り` / `お持ち` / `お越し` / `申し上げ` / `いたします` が含まれる一方で、
英語原文が平叙文であるエントリが並ぶ。

重大度はさまざまである。`差し上げます` と `お受け取りになります` はもっとも修正が必要である。
`お持ちです` と `お越しください` は通常の敬語で、`vous` に見合う範囲であり、そのままでよい。
`おめでとうございます` はシステムの祝福であり、線を越えていない。

**現在の残り（2026-10-21）**

- レビュー待ちが **26 エントリ**。一覧は
  [speaker-audit.csv](../csv/analysis/speaker-audit.csv) の `register to review` 列にある；
- 典型的な例：`0x13601073`（`…a barque` → `バークを差し上げます`）、
  `0xf94c02c2`（`you will receive` → `お受け取りになります`）、
  `0x171746e9`、`0xfbb36ec1`、`0xfdaf6463`（土地給付の文面の `差し上げます`）；
- **まだ変更していない**。基調（トーン）の基準が固まってから一度にまとめて処理する。変えてから
  戻すのを避けるためである。

## 検証

```
python src\tools\translate.py status              # progress
python src\tools\translate.py export --out x.jsonl # export entries awaiting translation
python src\tools\translate.py check x.jsonl        # validate
```

3 つのサブコマンドはいずれも `--lang <code>` を受け付け、既定では `translations\`
配下の最初の編集可能な言語を対象にする。

`check` は次の種類の問題を検出する：

| 検査 | 意味 |
|---|---|
| プレースホルダー | `@D$EndDate$`、`%1` が原文と**種類・個数**で一致していなければならない |
| タグ構成 | 翻訳は `<n>` / `<o>` / `<f>` / `<c>` / `<t>` タグを**追加してはならない** |
| 未翻訳 | `0x<id> \| <English original>` 形式のプレースホルダーテキスト |

改行は原文にすでに `<n>` がある位置にのみ入れてよい。新しい行が自然に欲しい場合は、
レンダラーに幅で自動折り返しさせ、手で `<n>` を挿入しない。

## 言語の追加

3 ステップで、途中で C++ や DLL に触れる必要は一切ない。ゼロからの完全な手順は
[新しい言語](new-language.md)を参照。

1. **翻訳ファイルを作成する** `src\translations\<code>.toml`。

   コマンド 1 つでできる。原文をテンプレートとしてコピーし、各エントリの右辺を翻訳に変える：

   ```
   python src\tools\pack\new_lang.py --new-lang <code>
   ```

   `references\en.gog_1.1.2.3.toml` をコピーする（`--from fr` を付けるとフランス語から始める）。生成されたファイルでは
   各行の右辺が原文、つまり「未翻訳」の状態である。
   既存のファイルは上書きされない。

   手で書いてもよい。形式は 1 行 1 エントリである：

   ```toml
   "0xd2d0a572" = "Vegetating"
   ```

   実際に翻訳する予定のエントリだけ書けばよい。残りは自動的に英語で表示される。ただし
   **エントリの数と順序は `references\en.gog_1.1.2.3.toml` と完全に一致させなければならない**。位置で対応づけるためである。
   過不足があれば `compile_pack.py` がエラーを報告する。

   `<code>` はファイル名である。そのまま言語パックのファイル名になり、`locale.ini` の `language=` の値にもなり、
   マージ時のフィールド名にも使われる。したがって他の区切り文字を使わないこと。

2. `start.bat` で**ワークベンチを起動**し、インストールページで新しい言語を選ぶ →
   「生成」→「デプロイ」。

   言語一覧は `src/live/*.toml` から作られる。新しい言語は翻訳編集ページから ＋ を
   クリックして直接作成することもできる。

3. **言語を切り替える**：インストールページの「言語」ドロップダウンで切り替え、次に「ゲーム言語に設定」をクリックする。
   **ドロップダウン自体はファイルに一切触れない**。「ゲームを起動（インジェクション）」は選択中の
   言語で起動するだけで、`locale.ini` を書かない。ディスクへの書き込みは「ゲーム言語に設定」でのみ行われる。

コマンドラインでの同等の操作：

```
python src\tools\pack\compile_pack.py --lang <code>
python src\tools\translate.py status --lang <code>
```

言語コードに正式な要件はない。`zh` / `zh-CN` / `de` / `pt-BR` はすべて動作する。**toml のファイル名と一致している**ことだけが必要である。

---

## 原文をすべて再生成する（ほとんど使わない）

引数なしの `src\tools\pack\new_lang.py` は、英語とフランス語の原文から en / fr / zh の 3 ファイルを再生成する。初回セットアップ時か、
ゲームのバージョンを切り替えるときにのみ使う。
データソースである `editor\data\editor-data.json` はリポジトリに含まれていない。

**日常の翻訳編集では実行しないこと**。古いデータで変更が上書きされる。

### 翻訳編集エリア（contenteditable）

翻訳エリアは「透明な textarea + ハイライトのオーバーレイ」ではなく `contenteditable` を使う。スペースは
`<span class="hl-sp">` として直接描画されるため、二層の位置合わせの問題はない。中国語 IME の変換中
（compositionstart→end）は DOM を再描画しない。変換終了後に一度だけ再レイアウトし、
キャレットを復元するので、候補ウィンドウが途切れない。

**名前プレースホルダーの中黒**：年代記では `%1 %2 %3` は通常「階級 / 名 / 姓」である。
したがって `%1 %2・%3` とだけ書く（階級の後にスペース、名と姓の間に `・`）。
2 要素の `%1 %2` が「階級 + フルネーム」を意味する場合はスペースを使い、`%1・%2` とは書かない。
そうしないと「见习水手·巴尔塔萨·马尔伯夫」のようになる。

### プレースホルダー結合ルール（ハッシュ単位、一括置換なし）

`%1 %2` は「階級 + フルネーム」を意味する場合もあれば「名 + 姓」を意味する場合もある。一括置換では
どちらかを必ず誤る。そこでルールをハッシュ単位で記録する：

```toml
# src/live/placeholder_roles/zh.toml
["0x338a357f"]
rules = [
  { pair = ["1", "2"], sep = " ", note = "等级 + 全名" },
]
```

ツール：`python src/tools/placeholder_roles.py`

- `--report --lang zh|ja`：隣接する `%N %N` をすべて走査し、
  `docs/csv/analysis/占位符语义.<lang>.csv`（ハッシュ、現在の区切り、推定される提案、英語の文脈）を人のレビュー用に出力する；
- `--check`：その言語に記録済みのルールと照合し、一致しない区切りを一覧する；
- `--fix`：明示的なルールがあるエントリ**のみ**を変更する。それ以外はそのまま残す；
- ルールは言語ごとに別に保持する：`placeholder_roles/zh.toml`、`placeholder_roles/ja.toml`。既定は `--lang zh`。

ルールを追加するには：CSV でそのパラメータの組を見つける → toml に 1 行追加する → `--check` →（必要なら）`--fix`
→ `apply_zh_rules.py` で再生成する。

### レイアウトにはスペースを使い、語や文は変えない

ゲームはスペースで改行し、詳細ボックスは高さが固定されている。「上が切れて最後の行しか
残らない」といった表示の問題では、**適切な位置にスペースをいくつか追加**して早めに改行させるのが
正しい対処であり、文字を削ったり翻訳を短くしたりすることではない。

- スペースはレイアウトの道具であり意味を変えない。翻訳内容はテキストソースに従う；
- 行数を減らす必要があるときは、節の境界や長い語の前にスペースを追加するのを優先する；
- ボックスに収めるためだけに翻訳を書き換えたり削ったりしない。

### エディタでのプレースホルダーとスペースのヒント

各翻訳の上に情報バーがある：

- **プレースホルダー**：現在のエントリの英語に現れる `%1` / `@T$Town$` などを、その意味とともに
  一覧する（`%N` は英語の文脈から「階級/称号、名、姓、フルネーム」と表示され、`@g$…$` は
  「金額」などと表示される）；
  - 本文中では、プレースホルダーはドラッグ可能なピルとして描画され、意味がその中に直接表示される（例：`@g$TotalPrice$ 金额`）。
    意味は CSS の `::after` で描画され、本文テキストや保存内容には決して入らない；
- ピルを目標位置へドラッグすると移動できる；
  - プレースホルダーは削除できない。削除されると自動的に戻される（個数は英語原文に従う）；
  - 情報バーは各プレースホルダーの必要個数（`×2`）と意味のみを表示する。挿入/削除ボタンはもうない；
  - 翻訳にあって原文にないものは「原文にない」として赤く表示され、削除できる；
- **スペース**：きれいな翻訳より何個多いかだけを表示し（約物の後に追加したレイアウト用スペース）、
  位置は一覧しない；
- **マークアップ**：`<n>` などのレイアウトタグの意味。

API：`/api/entry-info?lang=zh&id=<hash>`。

### クリーンなテキストソース

`src/orig/` 配下の各言語は、**レイアウト用スペースのない**クリーンな翻訳を持てる：

- `zh.gog_1.1.2.3.toml`：中国語（`live/zh.toml` の生成元）；
- `ja.toml`：日本語（`live/ja.toml` からレイアウト用スペースを取り除いたもの）。

エディタの情報バーの「スペース：N 個多い」は、現在の翻訳をこのクリーンなテキストと比較して求められる。

### 日本語：クリーンなソース → ルールで生成

```powershell
python src/tools/text/apply_ja_rules.py          # compare only; prints the number of differing entries and samples
python src/tools/text/apply_ja_rules.py --write  # write to live/ja.toml
```

ルールは `lang_rules/ja.py` に由来する：約物の正規化、プレースホルダー両側のスペース、助詞の後の
スペース（janome/fugashi があれば形態素解析、なければ正規表現フォールバック）。
既定ではファイルを書き出さない（手動のレイアウトを上書きしないため）。差分が許容できるようになったら `--write` を付ける。

### プレースホルダーの個数は 1 つずつ一致させる

- 情報バーは個数（例：`×2`）を表示する。原文と翻訳で個数が異なるプレースホルダーは
  赤く表示され、「プレースホルダーの個数が一致しません」と通知される；
- 保存時にサーバーが検証を強制する。`/api/patch` がプレースホルダーの使用回数の過不足を
  見つけると、バッチ全体を拒否し、該当エントリと個数（原文 N / 翻訳 M）を返し、ファイルは
  書き込まない。

### 元に戻す・クリーンな原文の復元

情報バーの右側に 2 つのボタンがある：

- **元に戻す**：現在のエントリの直前の編集を取り消す（最大 20 ステップ、メモリ上に保持）；
- **クリーンな原文を復元**：現在の翻訳を `orig/` のクリーンなテキストで置き換える（`/api/clean`）。
  復元後も未保存のままで、取り消しも保存もできる；

未保存の変更がある場合、ページ送り、ジャンプ、言語の切り替え、「インストールと起動」への切り替えの前に
確認を求める。保存を選んだ場合のみ離れられる。ページを閉じたり更新したりしたときも確認が出る。読み込んだ直後と
同じ翻訳なら変更なしとみなされ、ブロックされない。

注意：クリーンなテキスト自体はレイアウト用スペースを持たない。復元後にレイアウトを保ちたい場合は、
対応する言語のルールを再適用する。

### ハッシュ単位の用語例外

用語チェックが誤検出を報告した場合（例：`0x28b1f98d` では「Ship's Boy」が翻訳では実行時
プレースホルダーなので、「见习水手」の出現を要求すべきではない）、エディタでそのエントリだけ
例外にできる：

- 情報バーに「用語：Ship's Boy は「见习水手」であるべき」と「無視」ボタンが表示される；
- 「無視」をクリックすると `glossary/hash_rules.toml` に書き込まれ、その 1 エントリにのみ適用される；
- 無視したものは「無視済み：Ship's Boy」と「復元」ボタンが表示される；
- API：`GET /api/hash-rules?id=`、`POST /api/hash-rule {id, term, skip}`。

`0x28b1f98d` はこのルールで「Ship's Boy」を無視している。

### 保存は即時反映

- エディタで保存をクリックすると `live/` に直接書き込まれる。別途のレビューステップはない；
- `orig/` はクリーンなテキスト（レイアウト用スペースなし）のみを持ち、生成物はすべてルールが作る。

### コミット前の一括チェック

```powershell
check.bat                 # or python src/tools/check.py
```

次の順に実行する：モジュール間参照チェック → ルールのユニットテスト（`tests/`）→ 生成物の整合性
（`apply_zh_rules.py --check`）。

### 3 つのディレクトリの役割分担

```
src/orig/   English and French original references: strictly read-only, never written by any process
src/seed/   initial translations (machine/AI/human first drafts): locked by default; editable only after unlocking entry by entry in the editor
src/live/   text maintained directly by the editor: saving writes here, and the build reads only from here
```

- エディタの保存は `live/` にのみ書き込み、`seed/` にはもう触れない；
- 「初期版」のテキストは翻訳ボックスの下に常に表示され、現在の作業テキストと比較できる。
  内容が異なる場合（スペースを無視）、左側に強調された縦棒が現れる；
- 初期版ブロックの右上の「編集をロック解除」で初期版ダイアログが開く。既定は読み取り専用である。
  「編集をロック解除」をクリックして確認すると、その 1 エントリだけ編集でき、保存または閉じると
  自動的に再ロックされる（ロック解除の状態は記憶されない）；
- 「クリーンな原文を復元」は初期版のテキストを使い、現在の作業テキストを上書きする（取り消し可能）；
- `apply_zh_rules.py` は今も手動で実行して `seed/zh.toml` から `live/zh.toml` を生成できるが、ビルドのステップではない。

### ルールのトレース（可視化）

情報バーの「ルール」ボタンでダイアログが開き、この翻訳が段階ごとに表示される：

```
初版            → 标点规范化 → 连词后空格 → 人名/城镇名空格 → 当前译文
```

- 各段階では、前の段階から変わった部分だけが強調される；
- API：`/api/rule-trace?lang=&id=`；
- 現在、中国語は 4 段階を表示する。他の言語は 初版 → 规范化 → 当前译文
  （initial → normalized → current）を表示する；
- 末尾の「注釈の一致」は、ルールによって変わった文字を色分けする：オレンジ = 約物/プレースホルダーの
  スペース、青 = 接続詞、緑 = 人名/町名。現在の翻訳が
  ルール生成のものと異なる場合は、注釈が生成結果に対するものである旨が記される。

### 本文中のスペースの色分け（L1）

エディタは既定ではスペースを強調しない。「スペースの色分け」は削除された（効果が不安定だった）。
ルールの適用状況を確認するには、情報バーの「ルール」ダイアログを開いて段階ごとに見る。

### プレースホルダーの意味を手動で変更する

- 情報バーのプレースホルダーピルの後ろにある「編集」ボタン：入力ボックスが開き、そのプレースホルダーの意味を
  **現在のハッシュに対して**変更できる；
- `glossary/placeholder_meanings.toml` に保存され、言語 + ハッシュ + プレースホルダーごとに 1 レコードである。
  意味は空文字でもよい（意図的に空白にし、自動推論を行わない）；
  エディタがエントリを開くとき、そのエントリで使われるプレースホルダーの意味も固定されるので、互いに
  影響しない；
- 変更は表示のみに影響し、翻訳やコンパイルには影響しない。何度でも変更できる。
