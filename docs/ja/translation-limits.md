# 翻訳の限界: 翻訳に欠陥が付きまとう理由

本書は、**既知であり、ツールでは完全には排除できない**問題と、実際にどこまで検証したのかを記録したものです。
目的は責任逃れではなく、後から関わる人が「どの部分は信用してよく、どの部分は実際のゲームで確認しなければならないか」を知るためのものです。

## 1. 排除できない3つの欠陥

### 1.1 話者と語調: 「誰が話しているか」の正解データがない

言語パックに含まれるのは `hash = text` だけです。あるセリフをどの NPC が、どの画面で話すのかは、**言語パックには書かれていません**。
確定できるのは次の2種類だけです。

- **グレード A、6件**: テキスト自体に署名・自称・肩書きが含まれているもの（例: `…, Governor of %5`）
- **副王の音声セリフ、35件**: `PR2.exe` 内のポインタテーブル上で、この一群の音声が `ID_NPC_VICEROY_*` と1対1に対応しているもの（[音声マッピング](../语音映射.md) を参照）

残りの3,500件以上は**話題キーワード**でしか分類できず、「話題 ≠ 話者」です。
`On behalf of my nation, I would like to thank you for destroying a convoy of the notorious pirate…`
には `pirate` が含まれていますが、話者は総督です。したがって:

- カテゴリ単位で一括して語調を変えることはできません（[語調の提案](tone-proposal.md) でもこの点を述べています）。
- 180 個のテンプレートファミリーについては文体の統一性を確認済みです（混在は 0 ファミリー）。これは同一ファミリー内のテンプレートが互いに矛盾していないことを示しますが、
  「カテゴリ全体としてどの語調を使うべきか」は依然として人による判断が必要です。

### 1.2 レイアウト: エンジンは空白で単語を分割し、ウィジェットの幅は不明

エンジンの単語分割ルールは、[翻訳と言語パック](translation-and-packs.md) の「空白の慣例」の節で説明しています。
中国語と日本語には単語間の空白がないため、文字列全体が幅の広すぎる1つのトークンとして扱われ、**幅を超えた行は（切り詰めではなく）丸ごと表示されなくなります**。
私たちはそのルールに従って空白を追加していますが、なお残余リスクがあります。

- ウィジェットごとに幅が異なり、ある行を表示するウィジェットの幅がどれだけになるかを、ツールが**事前に知ることはできません**。
- 短いラベル（`Corn` → `とうもろこし`、`Brig` → `ブリッグ`、人名 → カタカナ）は本質的に英語より幅が広く、
  しかもこうした要素こそ狭いボタンやリストに現れやすいものです。
- タグと `<n>` の改行位置は原文に従うしかなく、勝手に追加・削除してはいけません。

ゲームのフォントを使った幅の概算チェック（`src/tools/analysis/width_check.py`、同一フォントにおける「翻訳幅 ÷ 英語幅」を代理指標とする）:

| 言語 | 比較対象件数 | 幅比の中央値 | ≥1.5× | ≥2.0× | 200px 以上の単一トークン |
|---|---|---|---|---|---|
| 日本語 | 3,421 | 0.85 | 171 | 10 | 415 |
| 中国語 | 3,421 | 0.64 | 11 | 2 | 688 |

結論: **全体としては、中国語も日本語も英語より幅が広いわけではありません**（中央値 0.85 / 0.64）。実際のリスクは
**短いラベル・固有名詞・単位**に集中しています（例: `%1 (%2 kn)` → `%1 （ %2 ノット）`）。
項目ごとの値は [宽度粗查-ja.csv](../csv/analysis/宽度粗查-ja.csv) と [宽度粗查-zh.csv](../csv/analysis/宽度粗查-zh.csv) を参照してください。

### 1.3 意味: 英語とフランス語の突き合わせまでで、しかも誤読は起こりうる

- 原文自体に誤記があります: `D774`（英語版は日付が誤っており、フランス語版が正しい — [保留項目](pending.md) を参照）。
- プレースホルダの意味を読み違えることがあります: `0xfbb36ec1` の `%1` は、中国語訳で一時「町の数」と解釈されていましたが、
  実際には町の名前です（英語版・フランス語版の原文と突き合わせて修正済み）。
- バージョン差: フランス語版 `1.1.2.42` は英語版 `1.1.2.3` より新しく、42 件はフランス語版にのみ、19 件は英語版にのみ存在するため、
  突き合わせで比較できるのはハッシュの積集合だけです。
- 文化固有の用語（`Letter of Marque`、`buccaneer`、`viceroy`）は、訳者が語調を決める必要があります。
  私たちは歴史研究の慣例（私掠免許状 / バッカニア / 副王）に従いましたが、これも一つの選択であり、唯一の答えではありません。

## 2. 実際にどこまで検証したか

| 項目 | 網羅範囲 | 方法 |
|---|---|---|
| プレースホルダ / `<n>` / タグ列 | **100%**（3,548件） | `compile_pack`、`check_breaks`、エラー 0 |
| フォントのグリフ被覆 | 全体 | `subset_fonts` が使用文字に基づき fontstitch で自動的に再縫合（現在 2,922 文字） |
| 語調の一貫性（同一テンプレート内） | 180 ファミリー | テンプレートファミリー比較、混在 0 ファミリー |
| 幅のリスク | 全体（代理指標） | `width_check.py`、実際のウィジェット幅ではない |
| **ゲーム内描画** | **333 / 3,548 = 9.4%** | インジェクトした DLL の `ResolveByHash`/`Add` ログ（`_logs_1843/*.log`） |
| 会話の整合性 | 検証不能 | エンジンの会話順序が必要で、言語パックには含まれない |

この **9.4%** という数字は重要です。これは、私たちが試した数回のプレイで**実際に要求された**ハッシュの数です。
残り 90% のテキストは静的検証を通過しただけで、ゲーム内で一度も表示されていません。

## ゲーム内での観察

### 2026-10-21: 中国語版のレイアウト改善（プレイヤーのフィードバック）

- **観察**: 中国語ビルドは以前よりゲーム内でのレイアウトが良くなった。抜き打ちで確認した画面では、**完全に空になった行は見られなかった**
  （エンジンが幅超過のトークンを捨てたケース）。
- **関係している可能性のある変更**（時間的に一致しただけで、因果関係は未検証）:
  1. 中国語 120 件で半角の句読点（`,` `;` `:` `!` `?`）を全角に統一した。以前は英語のカンマの後に空白が入らず、
     隣の文字とくっついて1つのトークンになりやすかった。
  2. 日付書式文字列とプレースホルダの空白ルール（`DATE_FORMAT_IDS`）により、`1600 年 4月 1 日` のような文字列が空白で分断されないようにした。
  3. 純粋な書式文字列（`%1 / %2` など）は英語に戻し、漢字を含む文字列に訳さないようにした。
  4. フォントの自動再縫合（fontstitch）により、新しく追加した文字がグリフ欠落で空白にならないようにした
     （[フォントと配布](fonts-and-distribution.md) を参照）。
- **ただしこれも完全な検証とは言えません**: インジェクションのログに含まれるのは、実際に要求された 333 / 3,548 件（9.4%）のハッシュだけなので、
  「空白が見られなかった」は実際にプレイした画面の範囲に限られます。

**抜き打ち確認を推奨する短いラベル**（中国語で幅比 ≥1.5 の 11 件すべて。狭いウィジェットに入りやすいものです）:

| ハッシュ | 英語 | 中国語 | 幅比 |
|---|---|---|---|
| `0x24646e0d` | Brig | 双桅横帆船 | 2.65 |
| `0xff0dd628` | `%1 (%2 kn)` | `%1 （ %2 结点）` | 2.04 |
| `0x1ac38a65` | `%1. %2. %3` | `%3年%2%1日` | 1.99 |
| `0xfc517063` | Piet | 皮耶特 | 1.63 |
| `0xfc517067` | Dirk | 迪尔克 | 1.58 |
| `0xfc5171bf` | Luis | 路易斯 | 1.58 |
| `0xc77f4c7c` | Biloxi | 比洛克西 | 1.54 |
| `0xfc51a0f3` | Elvira | 埃尔维拉 | 1.53 |
| `0xd3e8c706` | `%1: Fire` | `%1 ： 起火` | 1.52 |
| `0xcf572275` | Ruiz | 鲁伊斯 | 1.51 |
| `0xfc51a0f6` | Olivia | 奥利维亚 | 1.50 |

大半は船種と欧米の人名で、これらのウィジェットはたいてい幅が広いため、「一見する価値はある」ものの「確実に問題」というわけではありません。
同じことは日本語にも当てはまります（幅比の中央値 0.85、≥1.5× のものは大半がカタカナの人名）。日本語については、まだ同様のゲーム内フィードバックは得ていません。

### 単語間の空白（中国語）

上記の「レイアウト改善」の後、再び文字切れが現れました（シナリオ選択パネルの右側の列）。原因は、文の中に空白のない
長い漢字の連なりが残っていることです。エンジンは空白でしか折り返せないため、ウィジェットを超えた部分は切れてしまいます。解決策は全角の句読点を増やすことではなく、
**単語ごとに空白を挿入する**ことです。

- ツール: `src/tools/text/space_words.py`。既定では **spaCy + zh_core_web_sm** のトークナイザを使います
  （活発にメンテナンスされており、未知語の扱いが jieba より良く、中黒を含む人名も1つにまとまります）。jieba はフォールバックのみです。
- spaCy には Python 3.11 が必要です（依存パッケージには 3.14 向けのホイールがまだありません）。そのインタプリタを環境変数
  `PR2_SPACY_PYTHON` で指定します。インストール方法は [ビルドとインストール](build-and-install.md) の `space_words.py` の節を参照してください。
- 処理対象は、最長の漢字連続が ≥ 12 かつ最長トークンが ≥ 180px の項目だけです。短いラベル、ボタン、人名には手を加えません。
- 単語は目標幅（既定 120px）ごとにグループ化し、空白は**グループ間だけ**に入れるため、1文あたりの空白は通常 1〜5 個で済みます。
- 中国語 842 件に適用しました（項目ごとの適用前後の幅は [space-words-zh.csv](../csv/generated/space-words-zh.csv) にあります）。

これで「長い漢字の連なりが折り返せない」問題は解決しますが、「ウィジェット自体が狭すぎる」問題は解決しません。それはテキストの長さを変える以外に対処できません。

## 3. プレイスルーの自動化やデータのフックはできるのか

- **プレイの自動化**: 現実的ではありません。ゲームはリアルタイムで進行するため、すべてのハッシュを発火させるには複数のルートを最後までクリアする必要があり、
  入力のシミュレーション（クリックやキー入力）だけでも遅くて脆く、ランダムイベントに中断されます。
- **データのフック**: 実現可能で、すでに進行中です（[インジェクション](injection.md) を参照）。既存の DLL は `CScreenStrings::ResolveByHash`
  と `CStringManager::Add` をフックしており、ログにはハッシュ、バッファ容量（`zhlen`/`cap`）、原文が記録されます。
  ある行が**レイアウトを破綻させるか**を本当に判定するには、テキストを描画する時点にもう一つフックを仕掛け、
  **ウィジェットの矩形**と**計測されたテキスト幅**を記録する必要があります。そうすれば通常のプレイ中にデータを集められます。プレイスルーは不要ですが、
  すべての画面を一度は表示させる必要があります。

  この道筋に必要な作業は、逆アセンブルしてテキスト描画関数を特定する → `rect`/`GetTextExtent` を記録する → ディスクに書き出す、です。
  文章を編集するより、こちらのほうが価値のある方向です。どの項目がどの画面ではみ出すのかという事実が手に入るからです。

## 4. 既知の個別不備（統計に含まれない例外）

| 種類 | 例 | 対応 |
|---|---|---|
| 原文の誤記 | `D774` の日付 | そのまま残し、訳文は意味で補正。[保留](pending.md) に記録 |
| プレースホルダの誤読 | `0xfbb36ec1` の `%1` | 英語版・フランス語版の原文に合わせて修正 |
| 署名の書式 | `0x03fb5c6a` の `%1 、 %2 の副王` | 括弧を付ける案を提示したが、**今回は変更しないことにした** |
| 語調が不確実 | 海賊・酒場カテゴリの 111 件はこの人物のセリフではない | 一括変更せず、一人称の 53 件のみ手作業で確認 |
| 幅のリスク | 幅比 ≥1.5× の日本語短ラベル 171 件 | 個別対応せず、概算チェックの CSV を参照 |

## 5. 結論

- **機械的に保証できるもの**: プレースホルダ、タグ、フォント、同一テンプレート内の語調の一貫性
- **機械的に保証できないもの**: 話者、ウィジェットのレイアウト、原文の意味の細部
- **受け入れの提案**: ゲーム内被覆 9.4% を出発点とし、「幅の概算チェック」で ≥1.5× の短いラベルと、
  [語調の提案](tone-proposal.md) にあるグレード A / 副王の項目（6 + 35 件）をよく確認し、残りは現状のまま受け入れる
- レイアウト検証を実質的なものにするには、文章の編集を続けるのではなく、DLL を拡張してウィジェットの矩形と計測幅を記録するのが次の一歩です。
