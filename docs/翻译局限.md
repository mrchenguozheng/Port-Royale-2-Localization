# 翻译局限：为什么译文一定有瑕疵

这份文档记录**已知的、无法靠工具彻底消除**的问题，以及我们实际验证到了什么程度。
目的不是免责，而是让后来的人知道：哪些地方可以信，哪些地方必须实机看。

## 一、三类无法根除的瑕疵

### 1. 说话人与语气：没有权威的「谁在说」数据

语言包里只有 `hash = 文本`。同一句话由哪个 NPC、在哪个界面上说出，**不在语言包里**。
能确定的只有两类：

- **A 级 6 条**：文本自己带落款/自称/头衔（如 `…, Governor of %5`）；
- **副王语音 35 条**：`PR2.exe` 的指针表里这批语音与 `ID_NPC_VICEROY_*` 逐条对应（见[语音与映射](语音与映射.md)）。

其余 3,500 多条只能按**话题关键词**归类，而「话题 ≠ 说话人」：
`On behalf of my nation, I would like to thank you for destroying a convoy of the notorious pirate…`
含 `pirate`，说话人却是总督。所以：

- 不能按类别批量改语气（[语体拟改清单](语体拟改清单.md) 已写明这一点）；
- 模板族 180 族经检查风格一致（0 族混杂），说明同类模板内部没有自相矛盾，
  但「整类该用哪种语气」仍然只能人工判断。

### 2. 排版：引擎按空格分词，控件宽度未知

引擎切词的规则见[空格约定](译文与语言包.md#空格约定中文--日文这类不用空格分词的语言)：
中文/日文没有词间空格，整串会被当作一个超宽 token，**超宽时整行丢弃（不是截断）**。
我们按规则补了空格，但仍有残余风险：

- 每个界面控件的宽度不同，工具**无法预知**某句话会落在多宽的控件里；
- 短标签（`Corn` → `とうもろこし`、`Brig` → `ブリッグ`、人名 → 片假名）天然比英文宽，
  这类恰恰最可能出现在窄按钮/列表里；
- 标签、`<n>` 换行位置只能照原文，不能自行增删。

**这里没有任何像素判据**。曾经有过一个按字体算宽度的工具
（`width_check.py`）和一份「宽度粗查」CSV，结论是「中文比英文窄、日语约等于英文」——
那是用字体度量推出来的，**控件在游戏里到底多宽没有实测过**，
数值不可信，已连同工具与 CSV 一起删除。
现在的做法是：补空格时按**字数预算**成组（默认每组最多 12 字，见下文「词间空格」），
不需要知道控件宽度；真正的宽度风险只能进游戏看。

### 3. 语义：只能靠英法互证，仍会读错

- 原文本身有笔误：`D774`（英文版把日期写错，法文版是对的，见[待定事项](待定.md)）；
- 占位符含义可能误读：`0xfbb36ec1` 的 `%1` 曾被中文当成「城镇数量」，
  实际是城镇名（已按英法原文修正）；
- 版本差异：法文 `1.1.2.42` 比英文 `1.1.2.3` 高，有 42 条英文里没有、19 条英文里有而法文没有，
  参照时只能按 hash 交集比对；
- 文化词（`Letter of Marque`、`buccaneer`、`viceroy`）需要译者定调，
  我们按史学界惯例处理（私掠免许状 / バッカニア / 副王），但仍是选择而非唯一答案。

## 二、实际验证到了什么程度

| 项目 | 覆盖 | 手段 |
|---|---|---|
| 占位符 / `<n>` / 标签序列 | **100%**（3,548 条） | `compile_pack`、`check_breaks`，0 错误 |
| 字体用字覆盖 | 以字重覆盖为准 | 映射到完整 Noto 静态字重，没有按用字裁剪/缝合 |
| 语气一致性（同模板内） | 180 族 | 模板族比对，0 族混杂 |
| 排版（补空格后行长） | 全量 | `engine_text.py` 按字数预算成组，非像素 |
| **实机渲染** | **333 / 3,548 = 9.4%** | 注入 DLL 的 `ResolveByHash`/`Add` 日志（`_logs_1843/*.log`） |
| 对话连贯 | 无法验证 | 需要引擎对话顺序，不在语言包 |

那个 **9.4%** 很关键：它是我们跑过的几次游戏会话里**真实被请求过**的 hash 数，
剩下 90% 的文本只经过静态校验，没在游戏里显示过一次。


## 实机观察记录

### 2026-10-21：中文版排版改善（玩家反馈）

- **观察**：中文版在游戏里排版比之前好，抽查过的界面**没有出现整行空白**（即超宽 token 被引擎丢弃）的情况；
- **可能相关改动**（只是时间上吻合，未做因果验证）：
  1. 把 120 条中文里的半角标点（`,` `;` `:` `!` `?`）统一成全角——之前英文逗号后不加空格，容易和相邻字符粘成一个 token；
  2. 日期格式串与占位符空格规则（`DATE_FORMAT_IDS`），避免 `1600 年 4月 1 日` 这类被空格拆碎；
  3. 纯格式串（`%1 / %2` 等）强制回英文，不再被译成带汉字的串；
  4. 字体换成完整 Noto 字重（映射），不再按用字缝合，新增用字不会缺字形。
- **仍然不能当作全量验证**：注入日志里真实被请求过的 hash 只有 333 / 3,548（9.4%），
  「没看到空白」只覆盖到实际玩过的界面。

**建议抽查的短标签**：船型、西方人名、单位这几类天然比英文长
（`Brig` → 双桅横帆船、`%1 (%2 kn)` → `%1 （ %2 结点）`），
控件通常较宽，属于「值得看一眼」而不是「一定有问题」。
具体哪些条，按游戏里遇见再看，不提供按像素筛出来的清单。
日文同理（片假名人名与船型为主），尚未收到同类实机反馈。


### 词间空格（中文）

上面那条「排版改善」之后又出现了裁切（剧本选择面板右栏）。原因是句子里还有一长串
没有空格的汉字，引擎只能在这些空格处换行，超出控件就被裁掉。修法不是继续加全角标点，
而是**按词补空格**，并且这件事放在**构建期**做：

- 能力在 `src/tools/text/zh_space.py`：分词器**只有** **spaCy + zh_core_web_sm** 一条路
  （维护活跃，含间隔号的人名整段不拆）。spaCy 需要 Python 3.9～3.13，仓库根的
  `.venv-spacy` 会被自动发现，也可以用环境变量 `PR2_SPACY_PYTHON` 指定解释器；
  装法见「构建与安装」；
- **不要用 jieba**：它 2020-02-15 之后没有提交，649 个 issue 基本无人处理。
  这条是硬性规定，理由写在「构建与安装」的「不要用 jieba」一节；
- 没有 spaCy 时，才退回 `zh_space.fallback_wrap()` 的**按字数机械切**
  （会切在词中间，属于降级路径，不是默认路径）；
- 成组标准是**连续 13 个字必须断一次**（`MAX_CHARS`，2026-11-19 由 15 收紧），
  不是像素：控件宽度没在游戏里量过，用字体算出来的 px 只是推测，早先那套「120px
  目标」的说法已经作废（工具与 CSV 都已删除）。历史上试过 12 和 9：12 是拿编年史
  提示那条在窄框里数行数量出来的（12 估算 6 行、和原文对齐），15 当年估算 7 行、
  末句被裁；9 虽然也不裁，但正文每隔八九个字断一次，读着碎（「你的目标是从
  一个默默无闻的商人」）。窄控件里必须更早断的文本只能靠改短文案，没有别的手段；
- 数的是**字符**，全角标点也算一格（早先版本把片尾标点排除在外，那样 13 字的
  token 实际会画出 14～15 个字形，窄框里照样超宽）。唯一的例外是变量
  `%1`、`@X$Name$`：替换后的长度构建期不知道，只按 3～6 格估；
- 半角标点不一律全角化，判据集中在一个函数：`lang_rules/base.py` 的
  `punct_context()`。它先切出标点所属的**半角记号**（`ascii_token()`，字符集
  `ASCII_TOKEN_CHARS`），再分类——`CTX_CJK` 才转全角，`CTX_WORD`（Port）、
  `CTX_NUM`（22.8）、`CTX_TIME`（12:30）、`CTX_IDENT`（1.0.0、`f:fonts/…aaFHk.res`）
  一律原样保留；整条不含汉字的条目根本不进这一步。断点许可
  （`zh_space._cut_ok()` / `_ascii_split()`）问的 `base.is_ascii_ch()` 是同一套口径，
  所以「这里是一个半角记号」只有一份定义，不会两处各判一遍。现状：全库 442 处半角
  标点全部落在不含汉字的条目里（414 处在字体/文件名标签内、5 处时间、23 处英文标点），
  中文句子里的半角为 0 处；
- 预算按**「离上一个空格有多远」**算，不是按「连续汉字串」算：只用标点分开的
  短句（「你可以在市场买货，也可以去酒馆打听，还可以……」）里一个空格都没有，
  整段就是一个超长 token，照样会空白。2026-11-18 的空白回归就是这个原因——
  旧实现只切连续汉字串，多短句长文一条空格都拿不到；
- 译文里已有的空格只抹一半：**两边都是汉字或全角标点的**算手打噪声，删掉；
  **汉字与拉丁词、数字之间的**留着——中文与西文混排本来就该有那点空隙
  （「欢迎来到 Port Royale 2」「在 18 世纪」），而且空格正好是引擎的折行点，
  留着还白送一个可断位置。全库共 289 处这类空隙，其中汉字→拉丁 184、拉丁→汉字 105；
- **条目先分类，再决定排不排**（`src/tools/text/entries.py` 的 `kind()`）：去掉行内
  标签与变量后按「有无句读、几个汉字、还剩什么」分成正文 / 短标签 / 名词短语 /
  无汉字 / 模板·符号 / 诗谜六类，只有**无汉字**与**模板·符号**不进排版
  （`entries.UNTOUCHED`）。现状：正文 1599、短标签 1523、名词短语 198、无汉字 117、
  模板·符号 99、诗谜 12；参与扫描 3332 条，token 10481、空格 7149、最长 13、坏断 158。
  短标签与名词短语**照旧进排版**：它们短、通常一刀不用，但带变量时
  （「你还需要%1才能升到下一级」）能在变量前留一个断点，窄框里用得上——
  实测把它们也停掉会撤掉 6 条真实断点，属于回归；
- `<n>`、`<n:25>` 这类换行标签能把预算清零；`%1`、`@P$PirateName$` 这类变量和
  `<c>`/`<f:…>` 标签都算在行内预算里（变量按 3～6 字计），否则
  「9 字 + %1 + 12 字 + %2 + …」连起来仍是一个超长 token；
- 断点由 `_dp_pack()` 的 DP 挑，不再「填满就断」。代价只有三项：每刀算 2
  （先求刀数最少）；收尾是标点 → 免掉这 2；收尾是「从/在/也/和」这类往后粘的字、
  下一段以「的/了/着」开头（往左粘）、下一段是「与/和/及/或」这类并列连词 → +8。
  半角数字与 `%` 之间根本不许断。这样不会切出「你的目标是从 一个默默无闻的商人」，
  也不会切出「「X」 / 的按钮」。破折号「——」和省略号「…」例外，允许出现在行首
  （中文禁则只管逗号句号那一类，拦掉它们会让片尾白白多占两格）。补语字、
  指示词+量词、孤字/两字组这三条罚分在
  2026-11-19 的消融里测出零收益（3548 条上坏断率 483 → 483/489/485），已删；
- DP 先按硬约束求（不超过预算、标点不能起头、开括号不能收尾、半角串不许拆）；
  求不出来时才退到软约束，把「超预算」和「标点起头/开括号收尾」降级成重罚。
  会触发这条的只有一种情形：开括号 + 正好占满预算的长串（「（」+ 13 字），
  「开括号不能收尾」与「不超过预算」在这里互相打架。软约束阶段宁可让「（」吊在
  行尾，也不让整段失去断点——没有断点的长串会被引擎当成超宽 token 整行丢掉；
- 带间隔号的人名作为一个整体，不会被切开，也不会把整句吞成「人名」
  （旧正则 `[\u4e00-\u9fff]+(?:·…)+` 会贪婪匹配整句，是另一处漏断的原因）；
- 短标签/按钮/人名不动，只有超过预算的段落才加空格；
- 结果写在 `build/preview/engine_text/zh.toml`，可用 `python src\tools\text\engine_text.py --lang zh` 单独生成。

它解决的是「一长串汉字无法换行」，不解决控件本身太窄；后者只能靠改文案长度。

## 三、能不能自动打通游戏 / hook 数据

- **自动打游戏**：不现实。游戏是实时的，触发全部 hash 需要完整通关多条路线，
  纯输入模拟（点击/按键）既慢又脆弱，还会被随机事件打断。
- **hook 数据**：可行，而且已经在做。现有 DLL 钩了 `CScreenStrings::ResolveByHash`、
  `CStringManager::Add`，日志里能看到 hash、缓冲区容量（`zhlen`/`cap`）、原始文本。
  要真正判断「有没有撑破布局」，还需要在绘制文字处再钩一层，
  记录**控件矩形**与**实测文本宽度**，然后只在正常游玩时收集即可——不用通关，
  但每个界面至少要看一次。

  这条路的工作量：反汇编定位文字绘制函数 → 记录 `rect`/`GetTextExtent` → 落盘。
  比起改文案，这是更值得投入的方向，因为它能给出「哪条在哪个界面溢出」的事实。

## 四、已知的具体瑕疵（不计入统计的例外）

| 类型 | 例子 | 处理 |
|---|---|---|
| 原文笔误 | `D774` 日期 | 保留原样，译文按语义修正，记录在[待定](待定.md) |
| 占位符误读 | `0xfbb36ec1` 的 `%1` | 已按英法原文改回 |
| 落款格式 | `0x03fb5c6a` 的 `%1 、 %2 の副王` | 建议改括号，**本轮决定不改** |
| 语气不确定 | 海盗/酒馆桶内 111 条不是该角色的话 | 不批量改，只人工确认 53 条第1人称 |
| 短标签偏长 | 船型、人名、单位（如 `Brig` → 双桅横帆船） | 不做像素估算，进游戏遇到再看 |

## 五、结论

- **能机械保证的**：占位符、标签、字体、同模板语气一致；
- **不能机械保证的**：说话人、控件排版、原文语义细节；
- **验收建议**：以 9.4% 的实机覆盖为起点，遇到船型、人名、单位类短标签时多看一眼，
  再挑「语体拟改清单」里 A 级/副王 35 条重点看几眼，其余接受现状；
- 若要把排版验证做实，下一步应扩展 DLL 记录控件矩形与实测宽度，而不是继续改文案。
